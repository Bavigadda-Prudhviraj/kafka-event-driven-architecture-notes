1Processors: Stateless and Stateful

A topology has 3 parts — Source (Chapter 16), Processor and Sink. Processors are the business logic, where transformation happens: they receive records from their parent, process them, and forward results to their children.

💡

A stateless node processes each record independently; it does not remember anything from previous records. No state store, no changelog. The important stateless operations, each covered below:

1 · filter2 · map3 · mapValues4 · selectKey5 · split / branch6 · merge

Others include flatMap, flatMapValues, peek and foreach. Generally, stateless operations return a KStream.

  • A KStream object represents a stage in the processing pipeline. It does not contain data.
  • Holding several KStream objects lets us continue building the topology from different stages of the same pipeline, e.g. two filters both hanging off the source.

Calling filter adds a node to the topology and returns a new KStream pointing at it. Nothing runs until the application starts; then every record flows through the nodes.

2filter

filter keeps only the records that satisfy a condition: if the condition returns true, the record continues in the stream; if false, the record is dropped.

KStream.filter signaturejava
// returns KStream<K, V>; Predicate takes the key and the value
KStream<K, V> filter(Predicate<? super K, ? super V> predicate);
Predicate.java (Kafka Streams)java
public interface Predicate<K, V> {
    boolean test(K var1, V var2);
}
SourceTypesTopology.java — filterjava
@Configuration
public class SourceTypesTopology {

    @Autowired
    public void kstreamDemo(StreamsBuilder builder) {

        Serde<Order> orderSerde = new JsonSerde<>(Order.class);

        // Processing node: reading from source
        // orders KStream acts as a reference to the source processing node
        KStream<String, Order> orders = builder.stream("order-events",
                Consumed.with(Serdes.String(), orderSerde));

        // Processing node: filter amount > 1000
        // highValueOrders KStream acts as a reference to the filter processing node
        KStream<String, Order> highValueOrders =
                orders.filter((key, order) -> order.getTotalAmount() > 1000);

        highValueOrders.to("order-events-output",
                Produced.with(Serdes.String(), orderSerde));
    }
}
✎

In the notes, .to(...) is chained straight onto filter(...) and the result is assigned to highValueOrders. to() returns void, so that does not compile; the sink call is made on the variable instead, as above. @Bean void is written as @Autowired (see Chapter 16). The inverse operation, filterNot, keeps the records where the predicate is false.

3map

map transforms each record into another record. It can change only the key, only the value, or both.

KStream.map signaturejava
// returns KStream<KR, VR> (new key, new value);
// the mapper takes (old key, old value) and returns a KeyValue
<KR, VR> KStream<KR, VR> map(
    KeyValueMapper<? super K, ? super V,
                   ? extends KeyValue<? extends KR, ? extends VR>> mapper);
KeyValueMapper.java (Kafka Streams)java
public interface KeyValueMapper<K, V, VR> {
    VR apply(K var1, V var2);
}

The return type of this functional interface is VR; for map, VR is a KeyValue<KR, VR> pair holding the new key and the new value.

map — change only the keyjava
// Processing node: map, change only the key
// updatedOrders KStream acts as a reference to this map processing node
KStream<String, Order> updatedOrders =
        orders.map((key, order) -> KeyValue.pair("ORDER-" + key, order));

updatedOrders.to("order-events-output",
        Produced.with(Serdes.String(), orderSerde));

4mapValues

Like map(), but no key change is allowed — only the value can be changed.

mapValues — Order → OrderAlertjava
KStream<String, OrderAlert> alerts =
        orders.mapValues(order -> new OrderAlert(order.getOrderId(), order.getAmount()));
input
order-1Order
output
order-1OrderAlert
value type changed

Because the value type changes from Order to OrderAlert, a sink or store after this needs a SerDe for OrderAlert (e.g. new JsonSerde<>(OrderAlert.class)). The examples assume the classes have these getters (getAmount, getUserId); with Chapter 15's Order they would be getTotalAmount / getCustomerId.

5selectKey

The opposite restriction: only the key can change, no value change is allowed.

selectKey — re-key by userjava
KStream<String, Order> ordersByUser =
        orders.selectKey((orderId, order) -> order.getUserId());
input
order-1{ userId: "u1", amount: 500 }
output
u1{ userId: "u1", amount: 500 }
key changed

map vs mapValues vs selectKey

MethodCan change keyCan change valueMay require repartition later
map()YesYesYes (if the key is changed)
mapValues()NoYesNo
selectKey()YesNoYes
⚠

When the key changes, the repartition does not happen immediately. It happens when a downstream operation needs the records partitioned by the new key — generally groupByKey or a join. (Concept: repartitioning in Kafka Streams Architecture.)

Kafka Streams cannot see inside map(), so it must assume the key changed and marks the stream as needing repartitioning. If you only change the value, prefer mapValues(): it avoids an unnecessary repartition topic.

The topology source → selectKey(productId) → groupByKey → count → sink: the repartition topic is inserted right before groupByKey, not at selectKey. Without the grouping, the re-keyed records would simply go to the sink with the new key and no repartition.

6split / branch

The problem with two filters:

two independent filtersjava
// Processing node: filter amount > 1000
KStream<String, Order> highValueOrders =
        orders.filter((key, order) -> order.getTotalAmount() > 1000);

// Processing node: filter amount <= 1000
KStream<String, Order> lowValueOrders =
        orders.filter((key, order) -> order.getTotalAmount() <= 1000);

For each record, both filters are executed. That is fine when a record can go both ways; otherwise, why check every condition for every record? Use split() with branches:

split / branchjava
Map<String, KStream<String, Order>> branches = orders.split(Named.as("orders-"))
        .branch((k, o) -> o.getTotalAmount() > 2000, Branched.as("premium"))
        .branch((k, o) -> o.getTotalAmount() > 1000, Branched.as("high"))
        .defaultBranch(Branched.as("low"));

KStream<String, Order> premiumOrders = branches.get("orders-premium");
KStream<String, Order> highOrders = branches.get("orders-high");
KStream<String, Order> lowOrders = branches.get("orders-low");
An if / else-if / else chainflowchart
flowchart LR O["orders"] --> Q1{"amount > 2000?"} Q1 -- "yes" --> P["premium"] Q1 -- "no" --> Q2{"amount > 1000?"} Q2 -- "yes" --> H["high"] Q2 -- "no" --> L["low (defaultBranch)"] classDef step fill:#eef4ff,stroke:#2563eb,color:#1e3a8a,stroke-width:1.5px classDef out fill:#e8f7f5,stroke:#0f9d8f,color:#0b4f48,stroke-width:1.5px class O,Q1,Q2 step class P,H,L out

Branches are checked in order and a record goes to the first branch whose predicate matches; not every condition is evaluated. An order of 2500 goes to premium only, even though it is also > 1000. Without defaultBranch, records matching no branch are dropped.

✎

The notes call orders.split() with no name and then look up branches.get("premium"). The map keys are the split's name prefix + the branch name. With an unnamed split() the prefix is a generated name, so a lookup by just "premium" returns null. Giving the split a name with Named.as("orders-") makes the keys predictable: orders-premium, orders-high, orders-low. (Alternatively, Branched.withConsumer(...) handles each branch inline without the map.)

7merge

merge() is the opposite of split(): split() turns one stream into many; merge() turns many streams into one.

merge the branches backjava
KStream<String, Order> premiumOrders = branches.get("orders-premium");
KStream<String, Order> highOrders = branches.get("orders-high");
KStream<String, Order> lowOrders = branches.get("orders-low");

KStream<String, Order> allOrders = premiumOrders
        .merge(highOrders)
        .merge(lowOrders);
flowchart LR P["premiumOrders"] --> M["merge"] H["highOrders"] --> M L["lowOrders"] --> M M --> A["allOrders"] classDef in fill:#eef4ff,stroke:#2563eb,color:#1e3a8a,stroke-width:1.5px classDef out fill:#e8f7f5,stroke:#0f9d8f,color:#0b4f48,stroke-width:1.5px class P,H,L in class M,A out

The key and value types must be the same for all merged streams. There is no ordering guarantee between records coming from different input streams; order is only kept within each input.

💡

A typical pattern: split to treat each kind of order differently (e.g. mapValues a discount onto premium orders only), then merge to continue with a single stream and one sink.
