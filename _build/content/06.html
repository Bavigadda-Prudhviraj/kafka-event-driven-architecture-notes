Step by step

  1. Consumer starts and wants to join group group.id = "notification-service".
  2. Finds the partition number of topic __consumer_offsets: hash("notification-service-group-id") % 50 = 23 → Partition 23.
  3. Requests metadata (first time or refresh) through any broker, which asks the Active Controller. Response: __consumer_offsets partition 0 → Broker 1, partition 2 → Broker 2, partition 23 → Broker 3.
  4. Invokes Broker3 — the leader of Partition 23 acts as the Group Coordinator — and requests to join the “notification-service” group.
  5. Broker3 (Group Coordinator) records the assignment for group Notification-service, topic order-events: Consumer1 → Partition-0, Consumer2 → Partition-1, Consumer3 → Partition-2. Broker3 waits for all followers (Broker1, Broker2 — Partition 23 followers, which poll continuously) to update the events in __consumer_offsets partition 23. There is no option to provide ack=0/1/all here — internally the consumer acts like Ack=All. Once all followers have the update, the coordinator responds: Partition-2 assigned for topic “order-events”.
  6. Consumer fetches the last offset for topic “order-events”, Partition-2.
  7. Broker3 looks at __consumer_offsets, builds the key group.id_topic_Partition = "notificationGroupId_order-events_Partition-2" and finds value offset 100, which it returns.
  8. Consumer checks the metadata and invokes the leader broker of topic “order-events” Partition-2.
  9. Broker2 (leader) receives “fetch from offset 101, max bytes send me: 200 bytes” and returns the events at offsets 101 – 501.
  10. Consumer processes the events.
  11. Consumer commits the offset (manual, batch wise).
  12. Broker3 (Group Coordinator) writes to __consumer_offsets, Partition 23: (group, topic, partition) → offset processed till = 501, and sends the commit ACK.
  13. Continuous polling — move back to step 8.
ℹ

Note: consumer offset details are not cluster metadata. They are stored like normal topic data (in __consumer_offsets), not in the controller nodes. And for writes to __consumer_offsets there is no option to choose acks=0/1/all — internally the consumer acts like acks=all.

Two things that commonly trip up the demo
  • Old events are not printed. auto-offset-reset defaults to latest: a new group with no committed offset starts at the end of the partition, so only events produced after it joined are delivered. Use spring.kafka.consumer.auto-offset-reset=earliest to start from the beginning the first time.
  • “…is not in the trusted packages”. The producer's JsonSerializer adds a type header with its class name (e.g. com.eda.producer…Order), and the consumer's JsonDeserializer uses that header by default. If the consumer's package is different, either ignore the header so default.type is used — spring.kafka.consumer.properties.spring.json.use.type.headers=false — or trust that package with spring.json.trusted.packages.

6One Level Deeper: What Happens Behind the Scenes

Conceptually, this is what we would have to write without Spring Boot, using the plain Kafka client:

plain KafkaConsumer — conceptualjava
Properties props = new Properties();
props.put("bootstrap.servers", "localhost:9092,localhost:9192");
props.put("group.id", "order-consumer-group");                 // which group the consumer needs to join
props.put("key.deserializer", StringDeserializer.class);       // should be the same as
props.put("value.deserializer", JsonDeserializer.class);       // what the producer selected
props.put("auto.offset.reset", "latest");
props.put("enable.auto.commit", "true");

KafkaConsumer consumer = new KafkaConsumer<>(props);
consumer.subscribe(Arrays.asList("order-events"));            // which topic this consumer is interested in

// Connect with 1 of the brokers and fetch cluster metadata and store it

try {
    while (true) {
        ConsumerRecords records = consumer.poll();              // continuous poll inside while(true), fetches records

        // commitIntervalPassed default is 5 sec: after every 5 seconds, make an offset commit request
        // (no matter whether the fetched records were successfully processed or not)
        if (autoCommitEnabled && commitIntervalPassed) {
            commitOffsets();
        }

        for (ConsumerRecord record : records) {
            // business logic                                     // process the events
        }

        // If enable.auto.commit=false, we must call:
        //   consumer.commitSync();    // blocks until broker confirms
        //   consumer.commitAsync();   // fire-and-forget, no guarantee
    }
} finally {
    consumer.close();                                           // leaves consumer group
}
ℹ

This is conceptual code as in the source notes. In the real client API, poll takes a timeout — consumer.poll(Duration.ofMillis(100)) — and the auto-commit check happens inside poll(); the explicit if (autoCommitEnabled …) block just makes that hidden step visible.

What poll() does internally

First call

  1. Sends JoinGroupRequest to the Group Coordinator.
  2. Receives the partition assignment.
  3. Requests the last committed offset for the assigned partitions from the group coordinator.
  4. The group coordinator reads __consumer_offsets and returns the offset that needs to be read.
  5. Sends FetchRequest to the partition leaders with the offset it wants to read.

Subsequent calls

  • Sends FetchRequest for new data — new offsets in a continuous manner.
  • (And, if auto-commit is enabled and the interval has passed, commits the offsets.)
poll() — first call vs later callssequence diagram
sequenceDiagram participant C as Consumer poll() participant GC as Group Coordinator participant L as Partition Leader Note over C,L: First call C->>GC: JoinGroupRequest GC-->>C: partition assignment C->>GC: last committed offset for assigned partitions? Note over GC: reads __consumer_offsets GC-->>C: offset to read C->>L: FetchRequest (from that offset) L-->>C: records Note over C,L: Subsequent calls loop while (true) C->>L: FetchRequest (next offsets) L-->>C: records opt auto-commit enabled and 5 s passed C->>GC: commit offsets end end

Explanation

Joining the group, getting partitions and finding the start offset happen once, inside the first poll(). After that, each poll() is just a fetch of the next records. With auto-commit, every 5 seconds the consumer commits the offsets it has fetched — whether or not they were processed successfully, which is the at-most-once risk from Offset Commit Strategies.

Committing manually and closing

CallBehaviour
consumer.commitSync()Blocks until the broker confirms the commit (needed when enable.auto.commit=false).
consumer.commitAsync()Fire-and-forget, no guarantee — faster, but a failed commit is not retried.
consumer.close()Leaves the consumer group cleanly, so the coordinator can rebalance its partitions to other consumers right away.

If the consumer stops without close() (for example it crashes), no more heartbeats are sent by the consumer's background thread to the broker; the broker considers it dead and triggers a rebalance — but only after the heartbeat/session timeout has passed.

Step by step

  1. Spring Boot application starts.
  2. KafkaAutoConfiguration is triggered because spring-kafka is on the class path. It creates:
    • ConsumerFactory — reads the spring.kafka.consumer.* properties and stores them as a Map.
    • ConcurrentKafkaListenerContainerFactory — holds a reference to the ConsumerFactory. No KafkaConsumer object is created yet.
  3. @EnableKafka is added automatically by Spring Boot based on the class path; only then is Kafka listener processing enabled. It creates the KafkaListenerAnnotationBeanPostProcessor bean.
  4. The post-processor scans for @KafkaListener methods.
  5. For each @KafkaListener, it asks the ConcurrentKafkaListenerContainerFactory to create a KafkaListenerContainer bean.
  6. The KafkaListenerContainer gets a KafkaConsumer object from the ConsumerFactory…
  7. …and the poll loop starts — the first poll() joins the group, gets the partitions and the start offset, exactly as in the read flow above.

✅ Chapter Summary

  • A Spring Boot consumer needs only spring-kafka, a few spring.kafka.consumer.* properties (group id, deserializers, JSON default type) and a @KafkaListener method.
  • Deserializers must match the producer's serializers; JsonDeserializer needs the target type.
  • Behind the scenes: a KafkaConsumer is created, subscribe()s to the topic and runs while (true) { poll(); process; commit }, then close()s to leave the group.
  • The first poll() joins the group, receives partitions, fetches the committed offset and starts fetching; later polls just fetch the next records.
  • Auto-commit (default every 5 s) commits regardless of processing success; with it disabled use commitSync() (blocking) or commitAsync() (fire-and-forget).
  • Spring creates ConsumerFactory and ConcurrentKafkaListenerContainerFactory, scans @KafkaListener, builds a KafkaListenerContainer per listener and starts its poll loop.
