1The Problem: Dual Writes

Before going deep into this EDA pattern, let's first understand the problem:

OrderController.java — the naive versionjava
@PostMapping("/api/orders")
public ResponseEntity<String> createOrder(@RequestBody Order order) {

    // Step1: Save to Database
    orderRepository.save(order);

    // Step2: Publish event to Kafka
    kafkaTemplate.send("order-events", order.getOrderId(), order);

    return ResponseEntity.ok("Order created");
}
❌

Major flaw: we are writing to 2 separate, independent systems — a) the DB and b) Kafka — and there is no transaction that spans both.

Scenario 1: DB succeeds, Kafka fails

orderRepository.save(order);        // Saved to DB
kafkaTemplate.send("order-events"); // Kafka is down
  • The order exists in the DB, but no event is published.
  • The payment service is never notified.
  • Inventory is never decremented.

This is data inconsistency.

Scenario 2: Kafka succeeds, DB fails

kafkaTemplate.send("order-events"); // Kafka event published
orderRepository.save(order);        // DB connection lost
  • The event is published, but the order does not exist in the DB.
  • The payment service processes a non-existent order.
  • Inventory is decremented for an order that does not exist.

Also data inconsistency, with even more impact than scenario 1.

This is known as the DUAL WRITE problem. In interviews, two solutions are commonly suggested. Neither works.

Attempt 1: @Transactional + manual exception

rollback the DB if Kafka failsjava
@Transactional
public void createOrder(OrderRequest request) {

    // Step 1: DB write
    orderRepository.save(order);

    try {
        // Step 2: Kafka send in a try-catch; if Kafka fails, the DB is also rolled back
        kafkaTemplate.send("order-events", event).get();
    }
    catch (Exception e) {
        throw new RuntimeException("Kafka failed, rolling back!"); // rolls back DB
    }
}

This looks correct at first glance. The loophole: what if the Kafka publish succeeded, but we think it failed?

The lost-ACK timelinesequence diagram
sequenceDiagram participant App as Our app (@Transactional) participant DB as Database participant K as Kafka broker App->>DB: 10:00 DB write → success (not yet committed) App->>K: 10:05 kafkaTemplate.send() Note over K: 10:06 receives message → WRITES to partition K--xApp: 10:07 ACK sent · 10:08 NETWORK ISSUE, ACK lost Note over App: 10:09 "I never got ACK → must have failed" App->>DB: 10:10 throw RuntimeException → rollback Note over DB,K: DB: order does NOT exist (rolled back) <br/> Kafka: order event EXISTS

We end up in scenario 2 — the worse one. The application simply cannot tell “Kafka failed” apart from “Kafka succeeded but the answer got lost”.

Attempt 2: 2PC (Two-Phase Commit)

What 2PC would needsequence diagram
sequenceDiagram participant C as Coordinator participant DB as DB participant K as Kafka Note over C,K: Phase 1: PREPARE C->>DB: PREPARE DB-->>C: Yes, ready C->>K: PREPARE K-->>C: Yes, ready (✗ not supported) Note over C,K: Phase 2: COMMIT C->>DB: COMMIT C->>K: COMMIT Note over DB,K: DB: COMMITTED · KAFKA: COMMITTED

This might look like a solution. But for 2PC to work, all participants must understand the protocol, and Kafka does not support 2PC (XA): it does not understand PREPARE / COMMIT commands from an external coordinator. So its pros and cons do not even matter. Kafka's own transactions (Transactions (Producer)) are atomic only across Kafka partitions, not across a database.

2Solution: The Outbox Pattern

💡
The idea
  • Don't write directly to Kafka.
  • Write to the DB first — the business row and the event, in one local DB transaction.
  • A separate process reads the event from the DB and publishes it to Kafka.
one DB transactionjava
@Transactional

Both rows commit or roll back together, because they are in the same database. If Kafka is down, the event simply waits in the outbox table until the publisher can deliver it.

Outbox table schema

It is just a regular DB table in our application, containing the columns required to publish an event. The most common schema:

ColumnPurpose
IdUnique id of this event. The same event can be published more than once, so consumers use it for idempotency.

The outbox table is consumed in 2 ways:

  1. Polling — the Is_published column is required.
  2. CDC (Change Data Capture) — the Is_published column is not required.

OrderService.javajava
@Service
public class OrderService {

    @Autowired
    private OrderRepository orderRepository;

    @Autowired
    private OutboxRepository outboxRepository;

    @Transactional
    public Order createOrder(Order order) {

        // Step 1: save to orders table
        Order savedOrder = orderRepository.save(order);

        // Step 2: Create outbox event IN THE SAME TRANSACTION
        OutboxEvent outboxEvent = new OutboxEvent();
        outboxEvent.setAggregateType("Order");
        outboxEvent.setAggregateId(savedOrder.getOrderId());
        outboxEvent.setEventType("ORDER_CREATED");

        // Payload: JSON string of the event data
        String payload = String.format(
                "{\"orderId\":\"%s\"," +
                "\"quantity\":%d," +
                "\"totalAmount\":%.2f}",
                savedOrder.getOrderId(),
                savedOrder.getQuantity(),
                savedOrder.getTotalAmount()
        );
        outboxEvent.setPayload(payload);
        outboxRepository.save(outboxEvent);
        return savedOrder;
    }
}

No Kafka publish here: only DB tables are touched, so both writes can be part of one transaction. In real code, build the payload with an ObjectMapper instead of String.format, which does not escape quotes in values.

The poller

OutboxPoller.javajava
@Component
public class OutboxPoller {

    @Autowired
    private OutboxRepository outboxRepository;

    @Autowired
    private KafkaTemplate<String, String> kafkaTemplate;

    @Value("${outbox.polling.batch-size}")
    private int batchSize;

    @Scheduled(fixedRateString = "${outbox.polling.interval-ms}")
    @Transactional
    public void pollAndPublish() {

        // Step 1: Fetch unpublished events
        List<OutboxEvent> events = outboxRepository.findUnpublishedEvents(batchSize);
        if (events.isEmpty()) {
            return;
        }

        for (OutboxEvent event : events) {
            try {
                String topic = event.getAggregateType().toLowerCase() + "-events";
                kafkaTemplate.send(topic, event.getAggregateId(), event.getPayload())
                             .get();
                event.setPublished(true);
                event.setPublishedAt(Instant.now());
                outboxRepository.save(event);
            }
            catch (Exception e) {
                // BREAK to preserve ordering!
                // If event 1 fails, we must NOT skip to event 2
                break;
            }
        }
    }
}

  • The poller job runs every 2 seconds; the interval comes from the properties file.
  • In one go it fetches 10 records; the batch size also comes from the properties file.
  • For each event: publish to Kafka, then update the published status to true.
  • The break is important: if event 1 failed, we must not go on to publish event 2, event 3 and so on, because that would break ordering.

This scheduler is just one example of a poller. A separate application could equally keep polling the outbox table and call the publisher.

✎

With Order as the aggregate type, "Order".toLowerCase() + "-events" gives the topic order-events. @Transactional on the poller means the published = true updates are committed only when the whole batch finishes, so a crash mid-batch re-publishes those events on the next run. That is one more reason the consumer must be idempotent.

Disadvantages of polling

#ProblemDetail
1Multi-instance handlingMultiple instances mean multiple pollers, which can cause:
• Duplicate processing of rows — needs locking like SELECT … FOR UPDATE SKIP LOCKED.
• Ordering risk — two pollers picking different rows can break ordering.
• To preserve ordering across instances, use a technique like ShedLock (only one instance runs the job at a time).
2Polling gapEvent created at 10:00:00, but the poll runs at 10:00:02 → a 2 s delay.
3Constant DB loadEven with no events, the poller keeps querying the DB: extra CPU + IO overhead.
4DB clean-upThe outbox table must be cleaned up regularly, because it grows rapidly.
5Duplicate publishingThe event is published to Kafka, but the published = true update fails. On the next run the same event is published again, so the consumer must be IDEMPOTENT.

A more scalable solution is CDC (Change Data Capture).

4Approach 2: CDC with Debezium

📡

CDC says: don't ask the database for changes — the database will tell you. Debezium is a tool that implements CDC.

WAL (Write-Ahead Logging) in Postgres

  • Before an INSERT / UPDATE / DELETE, the change is first written to the WAL file and flushed to disk. Then the table is updated.
  • This helps Postgres with recovery.
  • The same WAL is used for replication to followers.

MySQL: the binlog

MySQL uses its binlog file for replication in the same way.

CDC simply reads these log files from the DB, so tables are never queried.

wal_level = replica

The WAL stores physical changes in binary form, e.g. page 5, offset 120 → changed from X to Y. That is of no use to CDC, which needs to know which table, which column, etc.

wal_level = logical

Still binary, plus extra metadata for decoding: Table = order, Row id = 1, column “Amount” changed from 100 to 200. Now CDC can publish proper events. Changing wal_level needs a restart.

Polling

  • Simple, only application code
  • Needs published column and clean-up
  • Polling delay + constant DB queries
  • Hard with multiple instances (locks, ShedLock)

CDC (Debezium)

  • Near real time, reads the WAL — no table polling
  • No published column
  • Ordering preserved by the log itself
  • Extra infrastructure: logical WAL, Kafka Connect, Debezium
⚠

Both approaches are at-least-once: after a crash, a poller or Debezium can publish an event again. Consumers must deduplicate, for example using the event id. Also, a replication slot keeps WAL on disk until Debezium confirms it, so a stopped connector makes the Postgres WAL grow; drop unused slots.
