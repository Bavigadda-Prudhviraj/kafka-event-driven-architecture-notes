1Problem 1: Duplicate Messages

A lost Ack causes a duplicate writesequence diagram
sequenceDiagram participant P as Producer participant B as Broker P->>B: Batch 1 Note right of B: .log <br/> Event1: offset1 B--xP: Ack (lost on the way) Note left of P: Didn't receive the Ack, so retried P->>B: Batch 1 (retry) Note right of B: .log <br/> Event1: offset1 <br/> Event1: offset2 B-->>P: Ack Note over P,B: Duplicate records persisted in log

What happens

  1. The producer sends Batch 1; the broker writes Event1 at offset1.
  2. The broker's Ack is lost (network issue, timeout) — the write succeeded, but the producer never learns about it.
  3. The producer didn't receive the Ack, so it retries Batch 1.
  4. The broker has no way to know it is the same data, so it writes Event1 again at offset2.

Result: duplicate records are persisted in the log — every consumer will process the same event twice.

2Problem 2: Message Reordering

A retried batch lands after a later batchsequence diagram
sequenceDiagram participant P as Producer participant B as Broker Note left of P: Sends 2 batches <br/> first: Batch1 <br/> second: Batch2 P-xB: Batch1 (network error, never reached Broker) P->>B: Batch2 Note right of B: .log <br/> Event2: offset1 B-->>P: Ack for Batch2 Note left of P: Retry for Batch1 P->>B: Batch1 (retry) Note right of B: .log <br/> Event2: offset1 <br/> Event1: offset2 B-->>P: Ack for Batch1 Note over P,B: Batch2 should be after Batch1, but the order is interchanged

What happens

  1. The producer sends two batches back to back — first Batch1, second Batch2 (possible because more than one request may be in flight).
  2. Batch1 hits a network error and never reaches the broker; Batch2 arrives and is written at offset1 (Event2).
  3. The broker acks Batch2. The producer then retries Batch1, which is written at offset2 (Event1).

Result: Batch2 should be after Batch1, but the order is interchanged. Imagine an order being PAID before it was even CREATED — a consumer would see the events in an impossible order.

3Solution: Set Idempotence = true

Producer: application.propertiesproperties
spring.kafka.producer.properties.enable.idempotence=true

“Idempotent” means that doing the same operation more than once has the same effect as doing it once. An idempotent producer can retry as often as it needs to: each event is written exactly once and in order into its partition. Let's see how.

4How It Works — Step 1: Producer Application Start-up (PID)

The producer gets a unique Producer IDsequence diagram
sequenceDiagram participant P as Producer box Kafka Cluster participant B as Broker participant C as Controller end P->>B: 1. Give me Unique ID B->>C: 2. Pass the request to Controller Note over C: 3. Pick next available PID <br/> (till 1000 is used, so it picks 1001) C-->>B: 4. PID = 1001 B-->>P: 5. PID = 1001

Step by step

  1. On start-up, the idempotent producer asks a broker: “Give me a unique ID.”
  2. The broker passes the request to the controller.
  3. The controller picks the next available PID — for example, if PIDs up to 1000 are used, it picks 1001.
  4. The controller returns PID = 1001 to the broker…
  5. …and the broker returns PID = 1001 to the producer. Every batch this producer sends from now on carries this PID.

Detail: in KRaft, brokers actually receive blocks of producer IDs from the controller and hand them out from that block, so not every request has to go to the controller — but the effect is the same: a unique, unused PID.

How the sequence numbers are assigned

  • The producer maintains a sequence number per topic-partition. Topic-A/P0, Topic-A/P1 and Topic-B/P0 each have their own counter, which is why all three batches start at BaseSequence: 0.
  • BaseSequence is the sequence of the first event in the batch; LastSequence is the sequence of the last one (Batch1: seq0 – seq2).
  • Say Batch1 is closed and a new batch is created for Topic-A, Partition P0: its sequence numbers start from 3 — the counter continues, it never restarts.
  • All batches carry the same PID: 1001, so the broker can tell which producer they belong to.

6Step 3: Batch Received by the Broker

The broker keeps an in-memory map of the last sequence number it accepted for every (PID, Topic, Partition), and checks every incoming batch against it.

If the numbers did not match (No, mismatch), the broker would reject the request.

Why this fixes both problems

Duplicate (Problem 1)

The retried Batch 1 carries the same PID and the same sequence numbers it had the first time. The broker already recorded them as its last sequence, so the base sequence is not “last + 1” — the copy is not written again.

Reordering (Problem 2)

If Batch1 (seq 0–2) is lost and Batch2 (seq 3–5) arrives first, the broker expects seq 0 but sees 3 — mismatch, rejected. The producer then retries Batch1 first and Batch2 after it, so the log keeps the original order.

ℹ

How “reject” behaves in practice: for a batch the broker has already written (a duplicate), it does not write it again but answers the producer as if the write succeeded, so the producer stops retrying. For a batch that arrives too early (a gap in the sequence), the broker returns an out-of-order-sequence error, and the producer re-sends its batches in sequence order.

With this, both the duplicate and the message-ordering issue are fixed. But there is one loophole in it.

7The Loophole: Producer Restart

If you double-check Step 1, you might find the loophole: the controller does not store the PID information in its cluster metadata. So when the producer restarts, it sends “Give me Unique ID” again, and since the controller (in the case of idempotence) does not store any producer ↔ PID mapping, it always generates a new PID and returns it.

Step by step

  1. The producer gets PID 1001 and sends Batch1 (Topic-A, P0, sequence 3–5). The broker writes it; the map holds 1001 / A / P0 → 5.
  2. The producer crashes — and may have missed the ACK from the broker too.
  3. After the restart it asks for a PID again and gets a new one: 2001.
  4. It sends the same events again — perhaps because it reads from an upstream database and doesn't see a “processed” flag yet.
  5. For the broker this is a different producer: 2001 / A / P0 is a new map entry, so the batch is accepted and the events are written a second time.

Idempotence protects against duplicates within one producer session (one PID). Across a restart, the PID changes and the protection is lost.

And that's where TRANSACTIONS come into the picture, covered after the consumer and consumer-group setup in Transactions in Kafka (Producer). One advantage of transactions: even when the producer restarts, the controller always returns the same PID.

8Last but Not Least: Required Configuration with Idempotence

  1. spring.kafka.producer.acks=all

    Why? Say acks=1: the leader persisted the event with sequence no. 1 but crashed before the followers pulled it. Now a new leader is elected for that partition. The producer retries, and the request now goes to the new leader — which does not have the event with sequence no. 1, so it writes it as new. The sequence check only works if every replica that can become leader has the data — that's why acks=all is recommended.

  2. spring.kafka.producer.retries=MAX_INT

    With idempotence, retries are safe (a retry can no longer create a duplicate or re-order), so the restriction on the number of retries is lifted.

  3. spring.kafka.producer.properties.max.in.flight.requests.per.connection <= 5

    Kafka can only guarantee idempotence for up to 5 in-flight batches (per topic, partition and PID). In other words, the broker keeps a buffer of only the last 5 batches' sequence numbers for each topic, partition and PID — so the value must be ≤ 5.

Producer: application.properties — idempotent producerproperties
# Idempotent producer: no duplicates, no re-ordering within a producer session
spring.kafka.producer.properties.enable.idempotence=true

# Required: all ISR replicas must have the event before the Ack
spring.kafka.producer.acks=all

# Retries are safe now (MAX_INT = Integer.MAX_VALUE)
spring.kafka.producer.retries=2147483647

# Must be <= 5 for idempotence
spring.kafka.producer.properties.max.in.flight.requests.per.connection=5
ℹ

Even with “unlimited” retries the producer does not retry forever: the total time for a send, including retries, is capped by delivery.timeout.ms (default 2 minutes), after which the send fails and the callback receives the error. If you explicitly set a value that conflicts with idempotence (for example acks=1 together with enable.idempotence=true), the producer fails at start-up with a configuration error instead of silently weakening the guarantee.

✅ Chapter Summary

  • With max.in.flight.requests.per.connection > 1 and retries > 0, a lost Ack causes duplicates and a lost batch causes re-ordering.
  • enable.idempotence=true fixes both (default false before Kafka 3.0, true from 3.0).
  • On start-up the producer gets a unique PID; every batch carries the PID plus a BaseSequence / LastSequence that is counted per topic-partition.
  • The broker keeps (PID, Topic, Partition) → Last Sequence and accepts a batch only if its base sequence is 0 (first batch) or Last + 1.
  • Loophole: a restarted producer gets a new PID, so re-sent data is a duplicate the broker cannot detect — solved later by transactions (stable PID).
  • Use acks=all, retries=MAX_INT and max.in.flight.requests.per.connection ≤ 5 with idempotence.
