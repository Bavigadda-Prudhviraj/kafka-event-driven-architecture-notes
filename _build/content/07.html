Where we are

In Part 1 we set up a basic consumer and saw how it reads from a topic. But what if:

  • one consumer needs to join more than one topic?
  • multiple consumers in a group need to join different topics?
  • multiple consumers in a group need to join the same topic?

How do we achieve this? This is where things get interesting.

21st: One Consumer Joins More Than One Topic

C1 reads order-events and payment-eventsarchitecture diagram

There are two approaches for turning the JSON of two different topics into two different Java types.

Approach 1: Manually taking care of JSON-to-object mapping

application.propertiesproperties
server.port=8082
spring.application.name=kafka-consumer-service
spring.kafka.bootstrap-servers=localhost:9092,localhost:9192
spring.kafka.consumer.group-id=order-consumer-group
spring.kafka.consumer.key-deserializer=org.apache.kafka.common.serialization.StringDeserializer
spring.kafka.consumer.value-deserializer=org.apache.kafka.common.serialization.StringDeserializer

Now this consumer handles more than one topic, so we handle the deserialization ourselves: if it's order-events, convert it to an Order object; if it's payment-events, convert it to a Payment object. That's why the value deserializer here is StringDeserializer — we need to control the deserialization.

OrderEventListener.javajava
@Component
public class OrderEventListener {

    @Autowired
    ObjectMapper objectMapper;

    // like this we can provide the list of topics which a consumer wants to subscribe to
    @KafkaListener(topics = {"order-events", "payment-events"})
    public void consume(ConsumerRecord<String, String> record) throws JsonProcessingException {
        // the record is accepted as it is; the deserialization task is ours
        if ("order-events".equals(record.topic())) {
            Order order = objectMapper.readValue(record.value(), Order.class);
            // business logic for order
        } else if ("payment-events".equals(record.topic())) {
            Payment payment = objectMapper.readValue(record.value(), Payment.class);
            // business logic for payment
        }
    }
}
  • topics = {"order-events", "payment-events"} — one listener (one consumer) subscribed to both topics.
  • The parameter is the raw ConsumerRecord<String, String>: we get the topic name and the JSON string, and pick the target class ourselves.
  • readValue throws a checked JsonProcessingException, so the method declares it (the source omits this).

The source notes explain it like this: we were using KafkaTemplate<String, Order> — a specific value type — so the producer did not add __TypeId__; after switching to KafkaTemplate<String, Object>, the producer added __TypeId__ to the header.

🔍
A closer look at that dump

The payload in the “empty headers” dump is {"orderId":"O-32700","productId":"PROD-3"} — only two fields. That is the output of the custom OrderSummarySerializer from Producer Setup, and a custom serializer does not add any type header. That is the reason headerKeys is empty in that record. The generic type of KafkaTemplate exists only at compile time (Java erases it at run time), so JsonSerializer cannot tell Order from Object. Whenever the value goes through JsonSerializer with add.type.headers=true (the default), the __TypeId__ header is added. Rule of thumb: check your value serializer — JsonSerializer adds the header, a custom serializer does not.

ℹ

The dump is also a nice confirmation of earlier chapters: producerId: 1000, baseSequence: 0 / lastSequence: 0 are the idempotence fields from Idempotency, compresscodec: snappy is our compression.type, and the payload {"orderId":…,"productId":…} is the output of the custom OrderSummarySerializer from Producer Setup.

That's internal logic of the producer client, but what we have to understand is: when the value uses JsonSerializer, spring.json.add.type.headers=true is the default, so the producer adds __TypeId__ = com.eda.producer.model.Order in the event header (in the cases above).

Reading the flow

  1. Is the value deserializer a JsonDeserializer? If not, this flow does not apply.
  2. spring.kafka.consumer.properties.spring.json.use.type.headers — does the consumer have to read __TypeId__ from the header or not? If false, it goes straight to the default type config.
  3. If true (default): is the __TypeId__ header present? If not, the default type is used.
  4. If it is present (say __TypeId__ = com.producer.Order): is a mapping present? With spring.json.type.mapping=com.producer.Order:com.consumer.Order (from : to), the “to” class is used.
  5. If there is no mapping, the consumer is forced to load the class the producer named (com.producer.Order). What if a hacker passed a malicious header such as com.fake.hack.Order? The consumer would try to load that class. So trusted packages are a security step before the consumer actually tries to load the class:
    • spring.kafka.consumer.properties.spring.json.trusted.packages=com.producer — trust all classes within this package.
    • spring.kafka.consumer.properties.spring.json.trusted.packages=* — trust everything.
    Not trusted → IllegalArgumentException (not in trusted package).
  6. If trusted, the class is loaded from __TypeId__; if it does not exist on the consumer's class path → ClassNotFoundException.
  7. Otherwise: deserialize JSON → object and invoke the @KafkaListener method.

How to resolve this? Why it happens

This issue comes because we have only one ConsumerFactory object, created from the properties defined in application.properties. In that ConsumerFactory, the “default type” is what we set: spring.json.value.default.type=com.eda.consumer.model.Order.

The same ConsumerFactory object is used to create both KafkaConsumers — the one for order events and the one for payment events — so both have default type = com.eda.consumer.model.Order. If we get this, the solution is very simple: have a different ConsumerFactory for each event type, with a default type specific to each event.

The fix: one ConsumerFactory and one container factory per event type

ConsumerConfig.java — Kafka consumer configjava
package com.eda.consumer.config;

import com.eda.consumer.model.Order;
import com.eda.consumer.model.Payment;
import org.springframework.boot.autoconfigure.kafka.KafkaProperties;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.kafka.config.ConcurrentKafkaListenerContainerFactory;
import org.springframework.kafka.core.ConsumerFactory;
import org.springframework.kafka.core.DefaultKafkaConsumerFactory;
import org.springframework.kafka.support.serializer.JsonDeserializer;
import java.util.Map;

@Configuration
public class ConsumerConfig {

    @Bean
    public ConsumerFactory<String, Order> orderConsumerFactory(KafkaProperties props) {
        Map<String, Object> config = props.buildConsumerProperties();
        config.put(JsonDeserializer.VALUE_DEFAULT_TYPE, Order.class.getName());
        return new DefaultKafkaConsumerFactory<>(config);
    }

    @Bean
    public ConsumerFactory<String, Payment> paymentConsumerFactory(KafkaProperties props) {
        Map<String, Object> config = props.buildConsumerProperties();
        config.put(JsonDeserializer.VALUE_DEFAULT_TYPE, Payment.class.getName());
        return new DefaultKafkaConsumerFactory<>(config);
    }

    @Bean
    public ConcurrentKafkaListenerContainerFactory<String, Order> orderKafkaListenerFactory(ConsumerFactory<String, Order> orderConsumerFactory) {
        ConcurrentKafkaListenerContainerFactory<String, Order> factory = new ConcurrentKafkaListenerContainerFactory<>();
        factory.setConsumerFactory(orderConsumerFactory);
        return factory;
    }

    @Bean
    public ConcurrentKafkaListenerContainerFactory<String, Payment> paymentKafkaListenerFactory(ConsumerFactory<String, Payment> paymentConsumerFactory) {
        ConcurrentKafkaListenerContainerFactory<String, Payment> factory = new ConcurrentKafkaListenerContainerFactory<>();
        factory.setConsumerFactory(paymentConsumerFactory);
        return factory;
    }
}

Explanation

  • The spring.kafka.listener.concurrency property is set on the ConcurrentKafkaListenerContainerFactory.
  • Then, for each @KafkaListener, it creates N KafkaListenerContainers and thus N KafkaConsumers — all in the same group, so Kafka splits the topic's partitions between them.
⚠

Concurrency vs partitions: within one group a partition is read by only one consumer (see Consumers & Consumer Groups). With concurrency=3 and the 2 partitions in the diagram above, two consumers get one partition each and the third stays idle. Set concurrency to at most the number of partitions; the topic from our cluster setup has 3 partitions, so 3 consumers each get one.

✅ Chapter Summary

  • One poll() sends one FetchRequest per leader broker and merges the responses into a ConsumerRecords object grouped by partition.
  • One consumer, many topics: @KafkaListener(topics = {"order-events", "payment-events"}) — map JSON manually (StringDeserializer + ObjectMapper) or automatically (__TypeId__ + spring.json.type.mapping).
  • The producer's JsonSerializer adds a __TypeId__ header by default (seen with KafkaTemplate<String, Object>); the consumer decides via use.type.headers → header → mapping → trusted packages → class path, or falls back to value.default.type.
  • Many consumers, different topics: separate apps, or several @KafkaListener methods (one KafkaConsumer each). With headers off, a single shared ConsumerFactory gives every listener the same default type — fix it with one ConsumerFactory + container factory per type and containerFactory = "...".
  • Many consumers, same topic: spring.kafka.listener.concurrency=N creates N containers / KafkaConsumers per listener; keep N ≤ partitions.
