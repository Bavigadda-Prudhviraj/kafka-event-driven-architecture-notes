What really happens

  • When the producer tries to send a message, it does not immediately send it to a broker.
  • Instead, the message goes through multiple internal stages inside the producer before any network call happens.

Overview

Stages 1–3 run on the application thread that called send(). Once the record is in the Record Accumulator, a separate background sender thread compresses ready batches and talks to the brokers. Let's go through each stage.

2Stage 1: Serializer

send()→1 · Serializer→2 · Partitioner→3 · Record Accumulator→4 · Compression→5 · Sender Thread
  • Our message (event) is generally a Java object, but Kafka understands only bytes. That's why a serializer is required.
  • Kafka does not know the data type of our message (Integer, String, custom POJO, JSON etc.). That's why it wants us to choose the proper SERIALIZER.
  • If the serialization stage fails, the message will not move to the next stage.

4Stage 3: Record Accumulator

send()→1 · Serializer→2 · Partitioner→3 · Record Accumulator→4 · Compression→5 · Sender Thread
  • An in-memory buffer inside the Kafka producer that collects events per topic-partition and groups them into batches.
  • Because of this, the Kafka producer achieves very high throughput (the ability to transmit a large volume of data within a given timeframe).

Explanation

The accumulator keeps one open batch for every topic-partition the producer writes to — here order-events/P0, order-events/P1 and product-events/P0. The partitioner chose P0 for E1, so E1 is appended to the order-events/P0 batch.

So the producer always maintains topic-partition wise batches, and it sends batches to the broker — not individual events.

  1. E1 comes with no key. The partitioner picks a random partition of order-events, say P1, and stores this info in memory (sticky): order-events → P1. E1 goes to the P1 batch.
  2. Similarly E2 and the other events come with no key. The partitioner checks the in-memory sticky info for order-events (→ P1) and sends them to P1 as well.
✓
Advantage of sticky partitioning

Events stick to the same partition until the current batch is closed or a new batch needs to be created. So there are fewer batches, and therefore fewer network calls. When the batch is closed, the partitioner sticks to a new partition, so over time the data is still spread across all partitions.

How to control the batch?

📦 batch.size=16384  16 KB (default)
  • Means the maximum memory allocated per partition batch.
  • For example, if 1 event = 1 KB, the batch will hold ~16 messages.
  • When the batch size reaches its limit, the batch is closed and ready for sending.
⏱ linger.ms=10
  • The maximum time the producer will wait for more records to fill the batch.
  • This makes sure the producer does not wait indefinitely for a batch to fill when traffic is low.
  • Example: batch size 16 KB, event size 1 KB → one batch can hold 16 messages. Traffic is low and only 5 events are in the batch so far. The producer waits at most 10 ms for more events; after 10 ms it closes the batch and it is ready to send.

Whichever happens first — the batch is full (batch.size) or the wait time is over (linger.ms) — makes the batch ready to send.

5Stage 4: Compression

send()→1 · Serializer→2 · Partitioner→3 · Record Accumulator→4 · Compression→5 · Sender Thread
  • Batches which are ready to send are compressed to reduce network usage and thus achieve higher throughput.
  • Kafka stores these compressed batches, which saves disk space too.
Example
Batch before compression = 64 KB
After compression = 18 KB

The whole batch is compressed (not each event separately) — the more similar records a batch holds, the better it compresses, which is another reason larger batches help. The compression type is set in properties — see compression.type in Use case 1.

6Stage 5: Sender Thread

send()→1 · Serializer→2 · Partitioner→3 · Record Accumulator→4 · Compression→5 · Sender Thread
  • The application thread never sends data to the Kafka broker.
  • A background sender thread does the actual communication.
  • The application thread's work ends at writing the record to the Record Accumulator; after that the sender thread comes into the picture.

Sender thread responsibilities

  1. Check the RecordAccumulator for ready batches
  2. Group batches by broker leader

    For example: batch for TopicA-Partition0 → leader is Broker1; batch for TopicA-Partition5 → leader is Broker1; batch for TopicB-Partition1 → leader is Broker1. So it groups the batches leader-wise, wraps them up in one ProduceRequest and sends it in one network call.

  3. Send the request using NetworkClient
  4. Process responses (acks, retries)
  5. Handle retries if needed
  6. Complete the future and invoke callbacks — this is what triggers whenComplete(...) in our code.

Explanation

Three batches for three different topic-partitions all have the same leader, Broker1, so the sender thread combines them into a single request — three batches, one round trip. The broker's response (acks) then completes the futures of all records in those batches.

Can we control the sender thread?

No — we don't have a way to control how many sender threads exist; Kafka manages it internally. But there is one thing we can control. Say we have 3 brokers: the sender thread creates 3 TCP connections (one per broker) to send messages to the respective broker.

producer configproperties
max.in.flight.requests.per.connection=5   # default

This parameter controls the maximum number of unacknowledged requests the client will send on a single connection before blocking. With 3 TCP connections, at most 15 requests can be in flight across the cluster at once.

⚠
But very important

If max.in.flight.requests.per.connection > 1 and retries > 0, there is a risk of message reordering.

How a retry re-orders two requestssequence diagram
sequenceDiagram participant S as Sender Thread participant L as Partition Leader S->>L: Request A (in-flight) S->>L: Request B (in-flight) L--xS: Request A fails L-->>S: Request B success - written in partition S->>L: Request A retried L-->>S: Request A success - written AFTER Request B Note over L: Partition log order is B, A (not A, B)

Explanation

Both requests are on the wire at the same time. A fails transiently, B succeeds and is appended, then A's retry succeeds — so A lands after B even though it was sent first. This risk is resolved by setting idempotence to true, which is covered separately in Idempotency.

spring.kafka.bootstrap-servers=localhost:9092,localhost:9192

# Metadata refresh interval, default is 5 minutes only
spring.kafka.producer.properties.metadata.max.age.ms=300000

This bootstrap info is required because initially the producer does not know which broker is the leader of which partition, and for topic creation it cannot talk to the controller directly — so it needs one starting communication point.

  • If it's a topic creation request, that broker passes the request to the active controller.
  • If it's a cluster metadata fetch, the broker sends the info if it has it; otherwise it fetches it from the controller and sends it back to the producer.
  • The producer stores the metadata in memory and refreshes it every 5 minutes (default, metadata.max.age.ms) or when an issue comes up while connecting to the leader of a partition.
ℹ

Listing both brokers is for redundancy at start-up only: after the first successful contact, the producer learns about every broker from the metadata and connects directly to partition leaders.

OrderProducerService.javajava
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.kafka.support.SendResult;
import org.springframework.stereotype.Service;
import java.util.concurrent.CompletableFuture;

@Service
public class OrderProducerService {

    @Autowired
    private KafkaTemplate<String, Order> kafkaTemplate;

    public void sendWithKey(Order order) {
        String key = order.getOrderId();

        CompletableFuture<SendResult<String, Order>> future = kafkaTemplate.send("order-events", key, order);

        future.whenComplete((result, ex) -> {
            if (ex == null) {
                System.out.println("Order event sent successfully");
                System.out.println("Partition: " + result.getRecordMetadata().partition());
                System.out.println("Offset: " + result.getRecordMetadata().offset());
            } else {
                System.out.println("Failed to send order event: " + ex.getMessage());
            }
        });
    }
}

The custom serializer

OrderSummarySerializer.javajava
import com.fasterxml.jackson.core.JsonProcessingException;
import com.fasterxml.jackson.databind.ObjectMapper;
import org.apache.kafka.common.serialization.Serializer;
import java.util.LinkedHashMap;
import java.util.Map;

public class OrderSummarySerializer implements Serializer<Order> {

    private final ObjectMapper objectMapper;

    public OrderSummarySerializer() {
        this.objectMapper = new ObjectMapper();
    }

    @Override
    public byte[] serialize(String topic, Order order) {
        if (order == null) {
            return null;
        }

        try {
            // Build a map with only the fields we want to expose, rest I removed it
            Map<String, Object> summary = new LinkedHashMap<>();
            summary.put("orderId", order.getOrderId());
            summary.put("productId", order.getProductId());
            return objectMapper.writeValueAsBytes(summary);
        } catch (JsonProcessingException e) {
            throw new RuntimeException("Failed to serialize Order summary", e);
        }
    }
}
  • It implements the same Serializer<T> interface we saw in Stage 1.
  • Only orderId and productId are written; customer, quantity, amount and status are removed before sending — the “remove sensitive fields” use case.
  • If serialization fails it throws, so — as in Stage 1 — the record never reaches the partitioner and the send fails.

12Many Producers, Different Serializers: Multiple KafkaTemplates

But what if we have many producers — some need JsonSerializer, some need a custom serializer? How do we define that in one application.properties? We can define a @Bean:

KafkaProducerConfig.java — extra KafkaTemplate beanjava
@Bean
public KafkaTemplate<String, Order> customSerializerKafkaTemplate(KafkaProperties kafkaProperties) {

    // Start with all producer properties from application.properties
    Map<String, Object> props =
            new HashMap<>(kafkaProperties.buildProducerProperties(null));

    // Override ONLY the value serializer - everything else stays the same
    props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, OrderSummarySerializer.class);

    DefaultKafkaProducerFactory<String, Order> factory =
            new DefaultKafkaProducerFactory<>(props);

    return new KafkaTemplate<>(factory);
}
OrderProducerService.java — using both templatesjava
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.kafka.support.SendResult;
import org.springframework.stereotype.Service;
import java.util.concurrent.CompletableFuture;

@Service
public class OrderProducerService {

    @Autowired
    private KafkaTemplate<String, Order> kafkaTemplate;                 // uses values from application.properties

    @Autowired
    @Qualifier("customSerializerKafkaTemplate")
    private KafkaTemplate<String, Order> customSerializerKafkaTemplate;  // picks value from the configuration @Bean

    public void sendWithoutKey(Order order) {
        String key = order.getOrderId();

        CompletableFuture<SendResult<String, Order>> future = customSerializerKafkaTemplate.send("order-events", order);

        future.whenComplete((result, ex) -> {
            if (ex == null) {
                System.out.println("Order event sent successfully");
                System.out.println("Partition: " + result.getRecordMetadata().partition());
                System.out.println("Offset: " + result.getRecordMetadata().offset());
            } else {
                System.out.println("Failed to send order event: " + ex.getMessage());
            }
        });
    }
}

Explanation

  • kafkaTemplate is Spring Boot's auto-configured template — it uses the values from application.properties (JsonSerializer).
  • customSerializerKafkaTemplate starts from the same properties (buildProducerProperties) and overrides only the value serializer, so batching, compression, acks and retries stay identical.
  • @Qualifier("customSerializerKafkaTemplate") (the bean's method name) tells Spring which of the two templates to inject. Put the @Bean method inside a @Configuration class such as KafkaProducerConfig.

13Last Part: The Re-ordering Risk

We discussed that when:

risky combinationtext
max.in.flight.requests.per.connection > 1
and
retries > 0

Then there is risk of message reordering.

Ex:
Request A -> in-flight
Request B -> in-flight

Request A -> fails
Request B -> success (written successfully in partition)

Request A -> retries and Success (written after Request B)

Our use-case configuration (max.in.flight.requests.per.connection=5, retries=3) is exactly this combination. How do we resolve this risk? With idempotence — the topic of the next chapter.

ℹ

Since Kafka 3.0 the producer has enable.idempotence=true by default, as long as the other settings are compatible with it (acks=all, retries > 0, max.in.flight.requests.per.connection ≤ 5 — all true here). Idempotency explains how it prevents both duplicates and this re-ordering.

✅ Chapter Summary

  • send() does not hit the network: the record passes through Serializer → Partitioner → Record Accumulator → Compression → Sender Thread.
  • Serializer turns key and value into byte[] (String, Integer, …, JsonSerializer, or a custom one).
  • Partitioner: explicit partition → used as-is; key → hash(keyBytes) % partitions; no key → round robin (pre 2.4) or sticky (2.4+), which creates fewer, fuller batches.
  • Record Accumulator batches per topic-partition; controlled by batch.size, linger.ms, buffer.memory, max.block.ms.
  • Compression (snappy, gzip, lz4, zstd) works on whole batches and saves network and disk.
  • The sender thread groups batches by leader into one ProduceRequest, handles acks/retries and completes the futures; max.in.flight.requests.per.connection > 1 with retries can re-order messages.
  • Spring Boot setup: spring-kafka, bootstrap-servers, TopicBuilder, KafkaTemplate.send() with whenComplete, custom Serializer<Order>, and a second KafkaTemplate bean selected with @Qualifier.
