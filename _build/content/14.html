2Stateless vs Stateful Processing

Stateless (what a consumer does)

  • Each event is processed independently — no memory of previous events or messages.
  • The output depends on the current event only.
  • Nothing needs to be remembered from previous messages.

Example

Order placed → send a confirmation email.

Stateful (what we often need)

  • The output depends on previous events / messages too.
  • We must remember (maintain state) across messages.

Example

Order placed → add its amount to the customer's running total.

⚠

Stateful processing breaks the plain Kafka consumer model, because the Consumer API is designed for stateless processing: it hands you records and offsets, but has no built-in place to keep, recover or share state.

With a plain Kafka consumer, we might try one of two approaches.

Approach 1: State in memory

RevenueConsumer.javajava
@Component
public class RevenueConsumer {

    private final Map<String, Double> revenueMap = new ConcurrentHashMap<>();

    @KafkaListener(topics = "order-events")
    public void consume(OrderEvent event) {
        revenueMap.merge(
                event.getCustomerId(),
                event.getAmount(),
                Double::sum);
    }
}
💥
1. Application crash
  • The in-memory map is gone.
  • We need to replay from offset 0 — millions of messages — to rebuild it. Meanwhile the committed offset has moved on, so the consumer must also be reset to the beginning.
🧩
2. Multiple instances
  • Each instance reads different partitions, so each holds only partial data.
  • After a rebalance, partitions move, and their state does not move with them.

Approach 2: State in MySQL

RevenueConsumer.java — DB versionjava
@KafkaListener(topics = "order-events")
public void consume(OrderEvent event) {
    CustomerRevenue revenue = repository.findById(event.getCustomerId());
    revenue.setAmount(revenue.getAmount() + event.getAmount());
    repository.save(revenue);
}
🐋

Problem: every Kafka event → SELECT → UPDATE. At 1,00,000 events / second (100,000) that is:

  • 1,00,000 SELECT queries per second
  • 1,00,000 UPDATE queries per second

The database becomes the bottleneck. On top of that, a network round trip per event adds latency, and the DB update and the offset commit are two separate writes, so a crash can count an event twice (the dual-write problem again).

✎

In Spring Data, findById returns an Optional, so real code would be repository.findById(id).orElseGet(() -> new CustomerRevenue(id, 0.0)). The first event for a new customer would otherwise fail. The notes also say “events / sections”, meaning events per second.

5Real-World Problem 3: Joining Two Topics

Use case: order-events has a customer_id; join it with customer-profile to fetch the customer name.

#Problem with a plain consumer
1We need to maintain a map of customer profiles.
2If that in-memory map is lost because of an app crash, it must be rebuilt by replaying from offset 0.
3With multiple consumer instances, each one holds only some partitions of both topics.

When an order event arrives at Consumer-A, the customer entry it needs may be maintained by Consumer-B. So we would need distributed state sharing between instances. A join only works locally if both topics are co-partitioned: the same key, the same partitioner and the same number of partitions, so that matching keys land in the same partition number. Otherwise the small table must be copied to every instance (what a GlobalKTable does).

The notes write “consumer-profile” in a couple of places; the topic is customer-profile.

6What We Would End Up Building

If we try to solve these problems by hand, we end up building a stream-processing framework ourselves, with:

✅

That framework already exists: Kafka Streams. It is a Java library (no separate cluster) that keeps state in local stores backed by Kafka changelog topics, so state survives crashes and moves with partitions. It provides KStream / KTable abstractions, windowing and joins out of the box. The following chapters cover it: architecture, KStream / KTable / GlobalKTable, SerDes, stateless and stateful processing nodes, and windows.
