1Why Windows?

Kafka streams are infinite: new events keep arriving, with no start and no end. So what if the business asks: “How many orders did we receive in the last 1 hour?”

Without a window

orders.groupByKey().count();
Ord-1 events
10:0010:1010:3011:1511:25
keycount
Ord-15

The KTable only knows “orders seen so far = 5”. It does not remember time, so it cannot answer “how many between 10:00 and 11:00?”.

With a window

orders.groupByKey().windowedBy(...).count();
keywindow start (incl.)window end (excl.)count
Ord-110:0011:003
Ord-111:0012:002

Now “how many between 10:00 and 11:00?” is a simple lookup of the right window.

💡

A window is a time-based boundary used to group records from an infinite stream into finite chunks. Window start is inclusive and window end is exclusive: [10:00, 11:00). The state store key becomes Windowed<K> = key + window.

2Three Notions of Time

Event timeKafka record timestampStream time
When the event actually happened in the real world, e.g. the createdAt field in the payload. Every Kafka record has a timestamp. By default the producer assigns it before sending (CreateTime). If the topic uses LogAppendTime, the broker assigns it when the record is appended to the log. Kafka Streams windows use this by default. The highest record timestamp observed so far (per partition/task). It only moves forward and decides when windows close.

Using event time instead: TimestampExtractor

By default, windows use the record timestamp. To use the event time instead, provide a custom implementation of the framework's TimestampExtractor interface:

TimestampExtractor (Kafka Streams)java
public interface TimestampExtractor {
    long extract(ConsumerRecord<Object, Object> record, long partitionTime);
}
OrderTimestampExtractor.javajava
public class OrderTimestampExtractor implements TimestampExtractor {

    @Override
    public long extract(ConsumerRecord<Object, Object> record, long partitionTime) {
        if (record.value() instanceof Order order && order.getCreatedAt() != null) {
            return order.getCreatedAt().toInstant().toEpochMilli();
        }
        return partitionTime;   // fall back to the partition's current stream time
    }
}
application.propertiesproperties
spring.kafka.streams.properties.default.timestamp.extractor=com.example.stream.OrderTimestampExtractor
✎

The notes cast (Order) record.value() and call .to Instant() (a typo). Two things to know: the extractor runs after deserialization, so record.value() is an Order only if the source uses an Order SerDe (otherwise it's a String and the cast throws). And it must never return a negative timestamp, so fall back to partitionTime when the field is missing, as above. A per-source extractor can also be set with Consumed.with(...).withTimestampExtractor(...). getCreatedAt() is assumed to return a ZonedDateTime/OffsetDateTime.

3Three Window Types

1 · Tumbling — fixed, non-overlapping2 · Hopping — fixed, overlapping3 · Session — activity-based, no fixed size

4Tumbling Windows

  • Fixed size, no overlap.
  • Each record belongs to exactly 1 window.
Window size = 10 mintimeline

How the data looks in the KTable (window size 5 min). Suppose events for Key-1 arrive at 10:02 and 10:13:

keywindow start (incl.)window end (excl.)count
Key-110:0010:051
Key-110:1010:151

There is no entry for 10:05–10:10, because no record belonged to that window: windows are created lazily, only when a record lands in them. Use cases: orders per 5 minutes, revenue per hour, API requests per minute.

Does a window stay open for late events?

Say stream time is 11:00 and a delayed event with record timestamp 10:32 arrives. Is window [10:30, 10:35) updated? It depends on the grace period:

Without grace period

The window is considered closed when stream time >= window end. Late events for a closed window are dropped.

With grace period

The window is not closed immediately: it closes only when stream time >= window end + grace. Late events within the grace period are still counted.

Example: window size 5 min; records arrive with timestamps 10:31, 10:32, 10:41, then 10:33 (late).

// with grace period

orders per user per 5 minutes, 1 minute gracejava
KStream<String, Order> orders = builder.stream("orders",
        Consumed.with(Serdes.String(), orderSerde));

KTable<Windowed<String>, Long> counts = orders
        .selectKey((orderId, order) -> order.getUserId())
        .groupByKey(Grouped.with(Serdes.String(), orderSerde))
        .windowedBy(TimeWindows.ofSizeAndGrace(Duration.ofMinutes(5), Duration.ofMinutes(1)))
        .count(Materialized.<String, Long, WindowStore<Bytes, byte[]>>as("order-count-store")
                .withKeySerde(Serdes.String())      // optional when defaults match
                .withValueSerde(Serdes.Long()));

The short form .count(Materialized.as("order-count-store")) also works when the default SerDes fit. Note the store type is a WindowStore, not a KeyValueStore, and the result key type is Windowed<String>. Grouped.with(...) is added because the re-keyed records go through a repartition topic with an Order value.

💡

A windowed KTable emits an update for every record (10:31 → 1, 10:32 → 2, …). To emit only one final result per window after it closes, add .suppress(Suppressed.untilWindowCloses(Suppressed.BufferConfig.unbounded())). Windowed state is also retained only for a limited time (Materialized.withRetention, at least size + grace), so old windows are cleaned up automatically.

5Hopping Windows

  • Fixed size, and advanced by a fixed interval (the hop).
  • When the hop is smaller than the size, windows overlap, so each record may belong to multiple windows.
Size = 10 min, advance by = 5 mintimeline

An event at 10:07 belongs to W1 [10:00,10:10) and W2 [10:05,10:15). Each record is counted in size ÷ advance = 2 windows. Use cases: orders in the last hour updated every x minutes, moving traffic counts, rolling revenue.

Late events in hopping windows

Size 10 min, hop 5 min; records arrive at 10:27, 10:28, 10:41, then 10:29 (late). Relevant windows: [10:20,10:30), [10:25,10:35), [10:30,10:40), [10:35,10:45), [10:40,10:50).

ArrivesStream timeWithout graceWith grace = 10 min
10:2710:27[20,30) → 1 · [25,35) → 1same
10:2810:28[20,30) → 2 · [25,35) → 2same
10:4110:41[20,30) and [25,35) closed (10:41 ≥ 10:30, ≥ 10:35) · [35,45) → 1 · [40,50) → 1[20,30) closed (10:41 ≥ 10:30 + 10) · [25,35) open till 10:45 · [35,45) → 1 · [40,50) → 1
10:29 (late)10:41discarded — both its windows are closed[20,30) closed → skipped · [25,35) open → 3 accepted

✎

In the notes' “with grace” table, the closing check for [10:25-10:35) is written as “stream time ≥ 10:35 so closed”, but with 10 min grace it closes at 10:45 — which the next step of the notes correctly uses (“Open till 10:45”) to accept the late 10:29. Window [10:30,10:40) gets no records here (10:41 is past its end), so it never appears in the store.

TimeWindows + advanceBy (hopping)java
// no grace period
TimeWindows.ofSizeWithNoGrace(Duration size).advanceBy(Duration advance)
// with grace period
TimeWindows.ofSizeAndGrace(Duration size, Duration afterWindowEnd).advanceBy(Duration advance)

KTable<Windowed<String>, Long> counts = orders
        .selectKey((orderId, order) -> order.getUserId())
        .groupByKey(Grouped.with(Serdes.String(), orderSerde))
        .windowedBy(TimeWindows.ofSizeAndGrace(Duration.ofMinutes(5), Duration.ofMinutes(1))
                .advanceBy(Duration.ofMinutes(1)))
        .count(Materialized.as("order-count-store"));

Here: 5-minute windows that start every minute, with 1 minute of grace. A tumbling window is just the special case advanceBy == size.

6Session Windows

  • Group events that occur close together in time.
  • A new session starts after a period of inactivity (the inactivity gap).
  • There is no window size: a session is as long as the activity lasts. Session start and end are the timestamps of its first and last record (both inclusive).

Example: inactivity gap 5 min; records arrive at 10:27, 10:29, 10:41, then 10:32 (late).

ArrivesStream timeWithout graceWith grace = 14 min
10:2710:27no existing session → [10:27–10:27] → 1same
10:2910:2910:29 − 10:27 = 2 min < 5 → same session → [10:27–10:29] → 2same
10:4110:4110:41 − 10:29 = 12 min > 5 → new session [10:41–10:41] → 1. The old session is closed (10:41 > 10:29 + 5).new session [10:41] → 1. Old session open till 10:29 + 5 + 14 = 10:48
10:32 (late)10:413 min after the 1st session's end, but that session is closed; 9 min before 10:41 → too far. discardedjoins the 1st session, still open → [10:27–10:32] → 3. 10:41 − 10:32 = 9 min > 5, so no merge with the 2nd. accepted
✎

When does a session close? A session ending at t can still grow while a new record within the gap could arrive, so Kafka Streams closes it when stream time > session end + inactivity gap + grace. The notes compute the closing time as session end + grace (10:29 + 14 = 10:43 and 10:32 + 14 = 10:46); including the 5-minute gap gives 10:48 and 10:51. Without grace the notes' conclusion holds either way: 10:41 is past 10:29 + 5 = 10:34, so the first session is closed and 10:32 is dropped.

Interesting case: a late event merges two sessions

Gap 5 min, grace 14 min; records arrive at 10:27, 10:29, 10:36, then 10:32 (late).

  1. 10:27 → no session → [10:27–10:27], count 1.
  2. 10:29 → 2 min after 10:27 → same session [10:27–10:29], count 2.
  3. 10:36 → 7 min after 10:29 > 5 → new session [10:36], count 1. The first session is still within its grace period.
  4. 10:32 (late) → 3 min after the first session's end and 4 min before the second session's start. It connects both, so Kafka Streams merges them into [10:27–10:36], count 4.
Session mergetimeline

Merging is why session windows need a mergeable aggregation: count() handles it automatically, while aggregate() on a session window takes an extra Merger function that combines two partial aggregates. Use cases: user login sessions, how long a user browses, average session duration.

// no grace period

// with grace period

        .windowedBy(SessionWindows.ofInactivityGapAndGrace(Duration.ofMinutes(10), Duration.ofMinutes(2)))
