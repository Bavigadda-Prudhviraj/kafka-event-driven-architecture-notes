1The Problem: JSON Has No Contract

But here is how 5 production use-cases can break this.

Use caseProducer (Order.java V2)Consumer (Order.java V1)What happens
1. Add a fieldadds String shippingAddresshas no knowledge of shippingAddressJackson may ignore the unknown field. In strict mode it throws a runtime exception instead.
2. Remove a fieldremoves totalAmountexpects totalAmountJackson assigns a default: primitive → default value (0, 0.0), object → null. Business logic silently runs on a 0 — too risky.
3. Rename a fieldtotalAmount → amountexpects totalAmountThe producer sends the amount, but the consumer looks for the old name and gets 0.0: silent loss of data.
4. Change a typequantity becomes Stringexpects int quantityJackson throws JsonMappingException (a value like "two" cannot become an int).
5. Many consumersConsumer1 wants all fields · Consumer2 only orderId + totalAmount · Consumer3 only orderId + shippingAddressChaos: the producer keeps changing fields for one consumer without knowing whether it breaks another.
use case 1 — strict modejava
ObjectMapper mapper = new ObjectMapper();
mapper.configure(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES, true);
⚠

The root cause in all 5 cases: JSON is schema-less. The producer can send any JSON — without any version, validation or compatibility check — and there is no contract between producer and consumer about the event schema.

✎

The notes' use case 2 still lists totalAmount in the producer's Version2 class — a copy slip; in that use case the field is removed. Plain new ObjectMapper() already defaults FAIL_ON_UNKNOWN_PROPERTIES to true; Spring Boot's auto-configured mapper and Spring Kafka's JsonDeserializer turn it off, which is why unknown fields are usually ignored.

2Solution: Schema Registry

Schema

A formal definition of the structure of your data. Common formats:

  • Avro (most popular with Kafka)
  • Protobuf
  • JSON Schema

Schema Registry

  • Maintains schemas and their versions.
  • On any change to a schema, it performs a compatibility check.

At a very high level, a Schema Registry brings validation before the producer sends (publishes) an event:

KafkaAvroSerializer on the first sendarchitecture diagram
  1. orderObj.getSchema() → the serializer generates a hash of the schema.
  2. It looks in its cache: do I already have a Schema ID for this schema hash?
  3. No → it makes an HTTP call to the registry, passing the subject order-events-value and the schema. The subject is not present yet, so the registry adds it to the _schemas topic.
  4. The registry returns Schema ID 1001.
  5. The serializer puts schema hash → Schema ID into its cache. Next time it skips steps 3–5.
  6. It serializes the value into the Avro wire format.
  7. After the remaining stages (partitioner etc.), the record is published to Kafka.
Schema IDSubjectVersionSchemaCompatibility
1001order-events-value1orderId: string, customerId: string, productId: string, quantity: int, totalAmount: doubleBACKWARD

Wire format: [magic byte][schema ID][payload]

bytes
01 byte · magic10014 bytes · schema idO-1 · C-1 · 5 · 55.0N bytes · Avro binary payload
  • 1 byte, magic byte — always 0. It tells the deserializer the version of the wire protocol, so it knows how to interpret the rest of the bytes.
  • 4 bytes, Schema ID.
  • N bytes, Avro payload — contains only the values in binary form, no field names. [0][1001][O-1 C-1 5 55.0] is just a representation of that.

Why does this work? With the Schema ID, the consumer can fetch the schema and learn the fields. The values are stored in the same order as the fields.

The subject name comes from the default TopicNameStrategy: <topic>-value for values (and <topic>-key for keys). The notes mix order-event and order-events; the topic used in the code and in the error below is order-events, so the subject is order-events-value. How the payload is decoded

The payload only contains values, in the same order as the fields of the registry schema: [O-1 C-1 5 55.0] (conceptually). The deserializer knows, for a string, how many bytes to read; for an int, how many bytes; and so on:

Schema fieldValue read
1st: orderIdO-1
2nd: customerIdC-1
3rd: quantity5
4th: totalAmount55.0

Default: GenericRecord

Fields are accessed by name:

GenericRecord accessjava
GenericRecord record = consumerRecord.value();
String orderId = record.get("orderId").toString(); // O-1

With specific.avro.reader=true

The deserializer sees name: Order and namespace: com.eda.schema in the registry schema and looks for the class com.eda.schema.Order (auto-generated from the consumer's .avsc). If found, it maps each registry field to the consumer's field — orderId → orderId, customerId → customerId, … — and returns an Order object.

The consumer uses the same dependencies and Avro plugin as the producer (kafka-avro-serializer also brings the deserializer) and the same order.avsc.

Avro decodes with two schemas: the writer's schema (fetched from the registry by id) and the reader's schema (the consumer's generated class). Fields are matched by name, so a consumer on an older or newer version still works as long as the two are compatible — which is exactly what the registry's compatibility check guarantees.

8Compatibility Levels

Back to the open question: how does the registry decide whether the schema the producer is about to publish is compatible? Every subject has a compatibility level (we saw BACKWARD in the _schemas table):

BACKWARD (default)FORWARDFULLBACKWARD_TRANSITIVEFORWARD_TRANSITIVEFULL_TRANSITIVENONE

BACKWARD (default) — new consumer reads old events

The registry thinks from this perspective: if a consumer on V2 pulls a message written with V1, it must not crash.

Change V1 → V2V2 schemaAllowed?Why
Add a field with default{ "name": "orderId", "type": "int" }, { "name": "status", "type": "string", "default": "PENDING" }SAFEOld messages have no status, so the default is used.
Add a field without default{ "name": "orderId", "type": "int" }, { "name": "status", "type": "string" }NOT ALLOWEDstatus is missing in old messages and there is no default.
Remove a field{ "name": "orderId", "type": "int" } (V1 also had status)SAFEstatus in old messages is extra and is ignored.

FORWARD — old consumer reads new events

Here the perspective is reversed: if a consumer on V1 pulls a message written with V2, it must not crash.

Change V1 → V2SchemasAllowed?Why
Add a fieldV2 adds { "name": "status", "type": "string" }SAFEstatus in new messages is extra; the old consumer ignores it.
Remove a field with defaultV1 had { "name": "status", "type": "string", "default": "PENDING" }; V2 removes itSAFEThe old consumer expects status; it is missing, so its default is used.
Remove a field without defaultV1 had { "name": "status", "type": "string" }; V2 removes itNOT ALLOWEDThe old consumer expects status and has no default.

FULL and the TRANSITIVE variants

LevelChecksAgainst
BACKWARDnew schema can read data written with the old schemathe latest version
FORWARDold schema can read data written with the new schemathe latest version
FULLboth BACKWARD and FORWARD rulesthe latest version
BACKWARD_TRANSITIVEBACKWARD rulesall previous versions
FORWARD_TRANSITIVEFORWARD rulesall previous versions
FULL_TRANSITIVEbothall previous versions
NONEno check—
✎

In the notes, “do not just compare with the last version, but all previous versions” is written next to FULL; it actually describes the _TRANSITIVE levels. FULL (non-transitive) compares only with the latest version. “TRASITIVE” is spelled TRANSITIVE. Under FULL, only adding or removing fields that have defaults is allowed.

💡

Which to pick? With BACKWARD, upgrade consumers first, then producers. With FORWARD, upgrade producers first. With FULL, either order works. Always giving new fields a default keeps most changes legal under every level.

Summary
  • Plain JSON has no contract: added, removed, renamed or retyped fields fail silently or at runtime on the consumer.
  • Schema Registry stores versioned schemas per subject (order-events-value) in the _schemas topic and checks every new version.
  • The producer's serializer registers the schema once, caches the id and writes [0][schema id][Avro values].
  • Incompatible changes are rejected before publishing (error 40901).
  • The consumer fetches the writer schema by id, decodes the values in order, and returns a GenericRecord or the generated class.
  • The compatibility level (BACKWARD default, FORWARD, FULL, *_TRANSITIVE, NONE) decides which changes are legal.
