1What is Event Driven Architecture (EDA)?

Event Driven Architecture can be considered as a system design style where:

✗

Services do not call each other directly

There is no service-to-service REST call where one service waits for another one to answer.

✓

Services emit events, others react

Instead, a service emits an event (a fact that something happened) and the other services that are interested react to those events.

In other words, the producer of the information no longer needs to know who needs the information or how to reach them. It simply announces what happened, and every interested service decides on its own what to do about it.

2What is an Event?

📌
Definition

An event is a fact that something happened in the past.

Every event has three properties:

PropertyDescriptionExample
ImmutableCan not be changed once created.OrderCreated at 10:30 PM
Past TenseDescribes what happened, not what to do.OrderCreated, not Place Order
Self-ContainedHas all info needed to understand it.Contains orderId, amount, timestamp.
🔒

Immutable

Because the event records something that already happened at 10:30 PM, that fact can never be edited — a correction would be a new event.

↺

Past Tense

OrderCreated states a fact. Place Order would be a command telling someone what to do — that is not an event.

📦

Self-Contained

A consumer can act on the event without calling back the producer, because orderId, amount and timestamp travel inside it.

3Order Flow in REST Distributed Microservices

To see why EDA is needed, first look at a typical order flow built with synchronous REST calls. The OrderService orchestrates every step and calls each downstream service one after another, waiting for each response before moving on.

REST (synchronous) order flowsequence diagram
sequenceDiagram participant U as User participant O as OrderService participant P as PaymentService participant I as InventoryService participant N as NotificationService U->>O: Place order O->>I: Check Real time Inventory I-->>O: response O->>P: Process Payment P-->>O: response O->>I: Reserve Inventory I-->>O: response O->>N: Send Notification N-->>O: response O-->>U: Order Placed

How this flow works

Participants: the User and four microservices — OrderService, PaymentService, InventoryService and NotificationService. Solid arrows are requests; dashed arrows are the responses OrderService must wait for.

  1. Place order — the user sends the order request to OrderService and keeps waiting.
  2. Check Real time Inventory — OrderService calls InventoryService and blocks until it replies.
  3. Process Payment — only after inventory answers, OrderService calls PaymentService and blocks again.
  4. Reserve Inventory — another blocking call to InventoryService.
  5. Send Notification — a final blocking call to NotificationService.
  6. Order Placed — only when every call has succeeded does the user get the response.

The whole chain is synchronous: the user's request is held open across four network hops, and OrderService has to know the address, invocation style and response structure of every other service.

4Problems with the Synchronous Chain

  1. AvailabilityAll services must be available at the same time. If any one service is down, the request will fail.
  2. Latency Accumulation

    Total Latency = Sum of all service latencies. Each hop adds its own response time to what the user experiences.

  3. Cascading FailureOne slow service can bring down other services and the entire flow, because callers keep waiting (and holding resources) on it.
  4. Tight CouplingIn the example above, OrderService knows about Payment, Inventory and Notification service — their endpoints, how to invoke them, their response structure, etc. Any change in them forces a change in OrderService.
  5. Scaling issueWe can not scale one service independently based on load — the chain is only as fast as all of its parts together.
⏱ Latency accumulation — illustrated

If the user's request passes through four sequential calls, the user waits for all of them:

latency formulatext
Total Latency = latency(Check Inventory) + latency(Process Payment)
              + latency(Reserve Inventory) + latency(Send Notification)

Event Driven Architecture removes the non-critical steps from this path, which is why improvement in latency appears among its advantages below.

5Order Flow in Event Driven Architecture (EDA) Distributed Microservices

⚠

Note: It's just an example to understand EDA.

The same order flow is now rebuilt around an Event Router. Only the steps the user must wait for remain synchronous; everything else happens through events.

EDA order flow — three processing phasessequence diagram
Real time Processing Async & Parallel Processing Async Processing
sequenceDiagram participant U as User participant O as OrderService participant R as Event Router participant P as PaymentService participant I as InventoryService participant N as NotificationService rect rgba(239, 68, 68, 0.10) Note over U,I: (Real time Processing) U->>O: Place order O->>I: Check Real time Inventory I-->>O: response O->>O: Save Order (status = PENDING) O->>R: Publish: OrderCreated O-->>U: Order Accepted end rect rgba(34, 197, 94, 0.10) Note over R,I: Async & Parallel Processing R->>P: Push OrderCreated Event R->>I: Push OrderCreated Event P->>P: Process Payment I->>I: Reserve Inventory P->>R: Publish: PaymentSuccess I->>R: Publish: ReservationSuccess end rect rgba(59, 130, 246, 0.10) Note over O,N: Async Processing R->>N: Push PaymentSuccess Event R->>O: Push PaymentSuccess Event N->>N: Send email and SMS O->>O: Update Order (status = Completed) end

Phase 1 — Real time Processing (red)

  1. Place order — the user sends the order to OrderService.
  2. Check Real time Inventory — the only synchronous call that is kept, because the user must know immediately whether the item is available.
  3. Save Order (status = PENDING) — OrderService stores the order locally in a PENDING state.
  4. Publish: OrderCreated — OrderService publishes an OrderCreated event to the Event Router. It does not call Payment, Inventory or Notification itself.
  5. Order Accepted — the user gets a response right away; they do not wait for payment, reservation or notification.

Phase 2 — Async & Parallel Processing (green)

  1. The Event Router pushes the OrderCreated event to both PaymentService and InventoryService.
  2. Both services work in parallel: PaymentService runs Process Payment while InventoryService runs Reserve Inventory.
  3. Each publishes its own result back to the router: PaymentSuccess and ReservationSuccess.

Phase 3 — Async Processing (blue)

  1. The Event Router pushes the PaymentSuccess event to NotificationService and to OrderService.
  2. NotificationService sends email and SMS.
  3. OrderService updates the order (status = Completed).

Key insight: OrderService only knows the Event Router. Payment, Inventory and Notification can be added, removed or scaled without changing OrderService, and a slow NotificationService no longer delays the user.

7Key Event Driven Architecture Components

From the above understanding, the key EDA components are:

Producer → Event Router / Broker → Consumersflowchart
flowchart LR P["Producer"] --> B["Event Router / Broker"] B --> C1["Consumer1"] B --> C2["Consumer2"] classDef prod fill:#111a2e,stroke:#ea580c,color:#fff,stroke-width:2px classDef brok fill:#ea580c,stroke:#9a3412,color:#fff,stroke-width:2px classDef cons fill:#e8f7f5,stroke:#0f9d8f,color:#0b4f48,stroke-width:2px class P prod class B brok class C1,C2 cons

Components

  • Producer — the service that emits events. In the order example, OrderService is a producer of OrderCreated; PaymentService and InventoryService produce PaymentSuccess and ReservationSuccess.
  • Event Router / Broker — the middle layer that receives events from producers and delivers them to consumers. Producers and consumers never talk to each other directly; they only talk to the broker.
  • Consumers (Consumer1, Consumer2) — the services that react to events. A single event can reach many consumers, e.g. both PaymentService and InventoryService receive OrderCreated.

A service can be a producer and a consumer at the same time — PaymentService consumes OrderCreated and produces PaymentSuccess.

8How Do Events Move Through EDA? Push vs Pull

Once the broker has an event, there are two ways it can reach the consumer.

Push

Push modelsequence diagram
sequenceDiagram participant Pr as Producer participant B as Broker participant C as Consumer Pr->>B: Publish Message B->>C: Push Messages (Immediately) B->>C: Push Messages B->>C: Push Messages Note right of C: Consumer must handle whatever rate broker sends Note right of C: Consumer can get overwhelmed

How push works

  1. The producer publishes a message to the broker.
  2. The broker pushes messages to the consumer immediately, one after another, as soon as they arrive.
  3. The broker decides the rate. The consumer must handle whatever rate the broker sends.
  4. If messages arrive faster than the consumer can process them, the consumer can get overwhelmed.

Pull

Pull modelsequence diagram
sequenceDiagram participant Pr as Producer participant B as Broker participant C as Consumer Pr->>B: Publish Message Pr->>B: Publish Message Note over B: Messages stored C->>B: Give me messages B-->>C: Take 1 message Note right of C: Process at own pace C->>B: Give me more messages Note over B,C: ... and so on

How pull works

  1. The producer publishes messages; the broker stores them instead of forwarding them immediately.
  2. The consumer asks the broker: “Give me messages.”
  3. The broker answers with what the consumer asked for (“Take 1 message”).
  4. The consumer processes at its own pace.
  5. When ready, it asks again: “Give me more messages” — and the cycle repeats.

Because the consumer controls the rate, it cannot be overwhelmed — messages simply wait in the broker until it asks for them.

Push

  • Broker sends messages immediately.
  • Broker controls the rate.
  • Consumer must keep up — it can get overwhelmed.

Pull

  • Broker stores messages.
  • Consumer requests messages when ready.
  • Consumer processes at its own pace.

9EDA Models: Pub/Sub vs Streaming

Pub/Sub

  • Events are published to active consumers and then forgotten.
  • If a new consumer joined, say, tomorrow, it won't get yesterday's messages.
Used when
  • We care about just delivery.
  • Not about storing history.
Example
  • RabbitMQ Exchange

Streaming

  • Events are appended in logs forever or retention based.
  • If a new consumer joined, say, tomorrow, it can read from the latest offset or read from day 1 (if retention allows).
Used when
  • We want replay.
  • We want multiple consumers.
Example
  • Kafka

Reading the visualisation

  • Pub/Sub: E1–E3 were published yesterday to the consumers that were active then, and then forgotten (shown struck-through). A consumer that joins today only receives the new events E4 and E5.
  • Streaming: every event is appended to a log and keeps its position (offset). Nothing is removed on delivery — only when the retention period expires. A consumer that joins today chooses where to start: from the latest offset (only new events) or from day 1 (replay everything still retained). Because the log is not consumed destructively, many consumers can read the same events independently.

This is exactly the model Apache Kafka follows, which is why replay and multiple consumers come naturally with Kafka. The next chapter explains how Kafka stores this log.

10Challenges of Event Driven Architecture

EDA is not free. These are the problems that come with it — many of the following chapters show how Kafka addresses them.

  1. Eventual ConsistencyAs events are processed in an async manner, a GET call might return stale data, but subsequent calls might give up-to-date information. (In the example, the order stays PENDING until the PaymentSuccess event is processed.)
  2. Duplicate eventsMost event routers guarantee “at-least once delivery”. So duplicates are normal, and consumers must be prepared for them.
  3. Ordering problemsEvents might reach the consumer out-of-order.
  4. Schema evolutionIf the event schema breaks, all consumers will crash.
  5. Debugging complexityDistributed tracing across async hops is a little difficult.
  6. Poison messagesOne bad message can block the Event Router.
  7. Operational overheadWe must monitor for:
    • Consumer lag
    • Throughput
    • Partition, queue etc.

11Use-cases of EDA — When to Go for It

  1. 1 event → N consumersWhen one action must trigger multiple independent actions. For example, when OrderPlaced happens, then:
    • Inventory reserves
    • Payment charges
    • Email sent
    • Loyalty points added
    • Analytics updated
  2. Long running business workflowExample: order → payment → shipment → delivery. These flows take time and can fail midway. Since the flow is not in the critical path, it can be broken into multiple steps, which handles this failure-prone nature better.
  3. Eventual consistency is acceptableThe business can tolerate data being up-to-date a little later rather than instantly.
  4. Real time analyticsData needs to be continuously processed.

Explanation

  • Left — 1 event → N consumers: a single OrderPlaced event fans out to five independent reactions. With REST, OrderService would have to call all five; with EDA it publishes once and each consumer reacts on its own.
  • Right — long running business workflow: a long-running workflow broken into steps. Each step is triggered by the event of the previous one, so a failure in shipment does not undo the order and payment that already happened — the failing step can be handled on its own.

✅ Chapter Summary

  • EDA: services don't call each other; they emit events and others react.
  • An event is an immutable, past-tense, self-contained fact (e.g. OrderCreated).
  • Synchronous REST chains suffer from availability, latency accumulation, cascading failure, tight coupling and scaling problems.
  • EDA keeps only the real-time part synchronous and moves the rest to async & parallel processing through an Event Router.
  • Key components: Producer → Event Router / Broker → Consumers.
  • Push can overwhelm consumers; with Pull consumers process at their own pace.
  • Pub/Sub (RabbitMQ Exchange) delivers and forgets; Streaming (Kafka) appends to a log, enabling replay and multiple consumers.
  • Challenges: eventual consistency, duplicates, ordering, schema evolution, debugging, poison messages, operational overhead.
