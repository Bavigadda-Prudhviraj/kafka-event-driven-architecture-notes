1Stream, Stream Processing and Kafka Streams

Stream

In simple terms, a stream has no start and no end: events keep arriving.

order-events
Order1Order2Order3Order4…
never ends

Stream processing

Processing events as they arrive, continuously, in real time.

📦

Kafka Streams is just a client library for building stream-processing applications on top of Kafka. It is not a separate cluster or infrastructure — it is a JAR file we add to our application.

2Topology

  • A logical flow of how data moves and gets processed, from source topics to sink topics.
  • The flow is a DAG (Directed Acyclic Graph): data flows in one direction, with no loops or cycles.
  • We define it once, during application start-up. After that, Kafka Streams executes it forever.

NodeRole
SourceEntry point: reads records from 1 or more Kafka topics. No parent processor. Deserializes bytes to key-value pairs. Forwards records to its child processors.
ProcessorBusiness logic, where the transformation happens. Receives records from its parent processor, processes them, forwards results to its child processors.
SinkExit point: writes records to a Kafka topic. No child processor. Serializes key-value to bytes and writes to the output topic.

For stateful processing, Kafka Streams stores data locally in RocksDB and keeps it fault-tolerant through changelog topics.

3Task — The Unit of Parallelism

  • A task is the unit of parallelism.
  • Each task has the complete topology.
  • Number of tasks = number of partitions; each task handles 1 partition.

4Sub-Topologies and Repartitioning

Sometimes the data needs to be re-partitioned. In that case one big topology is internally divided into multiple sub-topologies. What does re-partition mean? Use case:

  • Read order events: key = orderId, value = Order { "orderId", "customerId", "productId" }.
  • Find the product-wise order count, e.g. P1: 50 orders, P2: 100 orders.

The problem without repartitioning

Events are distributed across partitions by their key (orderId). So product P-1's orders end up in both partitions of order-events:

order-events P0json
{ "orderId": "O-1", "customerId": "C-1", "productId": "P-1" }
{ "orderId": "O-3", "customerId": "C-3", "productId": "P-1" }
order-events P1json
{ "orderId": "O-2", "customerId": "C-2", "productId": "P-1" }
The count for P-1 is split across two tasksarchitecture diagram

Task1 says P-1 = 2, Task2 says P-1 = 1. The true answer, 3, exists nowhere. We need to re-partition by productId, so all orders of the same product go to the same partition and therefore to the same task.

With repartitioning: two sub-topologies

We only write the topology: source → selectKey → groupByKey → count → sink. Based on the processors (when a repartition is required), the framework automatically creates a repartition topic and splits the topology into sub-topologies at that topic. The repartition topic gets the same partition count as the source topic.

Task, corrected

  • A task is still the unit of parallelism.
  • Each task runs one sub-topology for one specific partition.
  • Number of tasks = for each sub-topology, one task per partition of its source topic.

Here, 2 sub-topologies × 2 partitions = 4 tasks, named <sub-topology>_<partition>:

Each stream thread runs its own consumer and executes its tasks one after another. Tasks are the fixed unit; threads and instances just host them. To scale out, add threads or start another instance with the same application.id, up to the number of tasks.

5Changelog Topics — Fault-Tolerant State

❓

Doubt: RocksDB is just a key-value file store on local disk, and each task keeps its own RocksDB state. What happens when the machine dies or a rebalance occurs? The task may be assigned to another instance that does not have that local state. Then what?

That's where the changelog topic comes in:

  1. Whenever a task updates its RocksDB store, it also publishes the change to a changelog topic. The Kafka Streams framework creates this topic itself.
  2. When the task moves to another instance (rebalance) or the original machine is lost, Kafka Streams creates a new RocksDB store and restores its state by replaying the changelog.
Write path and restore pathsequence diagram
sequenceDiagram participant T as Task 1_0 (instance A) participant R as RocksDB (A's disk) participant CL as count-store-changelog P0 participant N as Task 1_0 (instance B) T->>R: put(P-1, 3) T->>CL: send(P-1, 3) Note over T: instance A dies Note over N: task 1_0 reassigned to B N->>CL: read changelog P0 from the start CL-->>N: P-1 → 3, ... Note over N: new RocksDB rebuilt, processing resumes

Changelog topics are compacted: only the latest value per key is kept, so a restore replays roughly one record per key instead of the whole history. Changelog partition N belongs to the task for partition N. The Kafka cluster for the example holds four topics:

6Complete Flow (Same as a Consumer)

Now that we know the architecture, the runtime flow is exactly the consumer flow from Consumer Setup Part 1, with three Streams-specific twists:

sequenceDiagram participant S as Stream app (S1, S2) participant AB as Any broker participant GC as Broker3 (Group Coordinator) participant L as Partition leader (Broker2) Note over S: Step1: start, join group.id = application.id ("stream-analytics") Note over S: Step2: hash("stream-analytics") % 50 = 23 → __consumer_offsets P23 S->>AB: Step3: metadata request (first time or refresh) AB-->>S: brokers vs partition leaders S->>GC: Step4: JoinGroup Note over GC: Step5: waits for members (group.initial.rebalance.delay.ms = 3000) <br/> picks one instance as group leader Note over S: group leader runs StreamsPartitionAssignor: <br/> discover topology → sub-topologies → tasks <br/> create internal topics (repartition, changelog) <br/> distribute tasks, e.g. S1: Task0_0, Task0_1 · S2: Task0_2 S->>GC: assignment GC-->>S: each member gets its tasks S->>GC: Step6: fetch committed offset (order-events P2) GC-->>S: Step7: P2 → 100 Note over S: Step8: restore state stores from changelog topics S->>L: Step9: fetch from offset 101 (max bytes ...) L-->>S: Step10: records 101 - 501 Note over S: Step11: process the records through the task's sub-topology S->>GC: Step12: commit offset Note over GC: Step13: write __consumer_offsets P23 · offset = 501 GC-->>S: ACK Note over S: Step14: keep polling, back to Step9
  • Group id = application.id.
  • Step 5: instead of a simple partition assignor, the group leader runs StreamsPartitionAssignor, which assigns tasks (and creates the internal topics).
  • Step 8: before processing, each stateful task restores its RocksDB store from the changelog topic.

Kafka Streams commits every commit.interval.ms (default 30 s with at-least-once) rather than after each record. group.initial.rebalance.delay.ms is a broker setting.

OrderStreamTopology.java — define the topologyjava
package com.eda.streams.config;

import com.eda.streams.model.Order;
import com.fasterxml.jackson.databind.ObjectMapper;
import org.apache.kafka.common.serialization.Serdes;
import org.apache.kafka.streams.StreamsBuilder;
import org.apache.kafka.streams.kstream.*;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class OrderStreamTopology {

    private static final ObjectMapper objectMapper = new ObjectMapper();

    @Bean
    public KStream<String, String> orderCountTopology(StreamsBuilder builder) {

        // SOURCE: read from "order-events" as raw JSON strings
        KStream<String, String> orderStream =
                builder.stream("order-events",
                        Consumed.with(Serdes.String(), Serdes.String()));

        // FILTER: only orders with totalAmount > 100
        KStream<String, String> highValueOrders =
                orderStream.filter((key, value) -> {
                    try {
                        Order order = objectMapper.readValue(value, Order.class);
                        return order.getTotalAmount() != null
                                && order.getTotalAmount() > 100;
                    } catch (Exception e) {
                        return false;
                    }
                });

        // Re-key by productId
        // This will trigger a REPARTITION topic
        KStream<String, String> productKeyedOrders =
                highValueOrders.selectKey((oldKey, value) -> {
                    try {
                        Order order = objectMapper.readValue(value, Order.class);
                        return order.getProductId();
                    } catch (Exception e) {
                        return "UNKNOWN";
                    }
                });

        // RocksDB store name
        KTable<String, Long> productCounts =
                productKeyedOrders
                        .groupByKey(Grouped.with(Serdes.String(), Serdes.String()))
                        .count(Materialized.as("product-count-store"));

        // output topic
        productCounts
                .toStream()
                .mapValues(String::valueOf)
                .to("product-counts",
                        Produced.with(Serdes.String(), Serdes.String()));

        return orderStream;
    }
}

Summary
  • Kafka Streams is a library; the app is a group of stream threads that are Kafka consumers + producers.
  • A topology (DAG of source → processors → sink) is defined once and runs forever.
  • Re-keying before a grouping or join creates a repartition topic and splits the topology into sub-topologies.
  • Tasks = sub-topologies × partitions; tasks are spread over threads and instances.
  • State lives in RocksDB per task and is backed up to compacted changelog topics for recovery.
