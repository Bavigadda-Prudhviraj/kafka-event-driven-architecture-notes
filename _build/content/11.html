The data record is physically in the log in all three cases. What the consumer gets to see depends on its isolation level and on the LSO.

2LSO — Last Stable Offset

📌

LSO = the offset of the first message that belongs to an OPEN (ongoing) transaction.

A read_committed consumer cannot read past the LSO, even if there are committed or non-transactional records after it. The LSO is maintained by the broker and kept in memory.

Example — topic order-events, partition P2:

order-events P2 logtext
Offset0: [PID=5, epoch=0, isTransactional=true]                 {record-1}   TXN-1
Offset1: [PID=5, epoch=0, isTransactional=true]                 {record-2}   TXN-1
Offset2: [PID=8, epoch=1, isTransactional=true]                 {record-1}   TXN-2 (open)
Offset3: [PID=5, epoch=0, isTransactional=true, isControl=true] {COMMIT}     TXN-1 committed
Offset4: [PID=9, epoch=0, isTransactional=true]                 {record-1}   TXN-3
Offset5: [PID=9, epoch=0, isTransactional=true, isControl=true] {COMMIT}     TXN-3 committed

3Consumer Isolation Level

application.propertiesproperties
# read_uncommitted (default) | read_committed
spring.kafka.consumer.properties.isolation.level=read_committed

read_uncommitted (default)

Reads everything except control records (isControl=true):

  • Ongoing transactional records
  • Committed transactional records
  • Aborted transactional records
  • Non-transactional records

For the example above, the consumer reads

  • Offset0 — part of committed TXN-1
  • Offset1 — part of committed TXN-1
  • Offset2 — open (ongoing) TXN-2
  • Offset4 — part of committed TXN-3

Skips

  • Offset3 — control record for TXN-1
  • Offset5 — control record for TXN-3

read_committed

  • Reads committed transactional records
  • Reads non-transactional records
  • Skips aborted transactional records
  • Stops at the LSO
  • Skips control records (isControl=true)

For the example above, the consumer reads

  • Offset0 — part of committed TXN-1
  • Offset1 — part of committed TXN-1

LSO = 2, so the consumer cannot read Offset2, because that transaction is still open.

Notice: even though TXN-3 is committed, the consumer cannot read it because of the LSO. This ensures the consumer never sees partially completed transactions, preserving both ordering and atomicity.

ℹ

For read_committed, the broker only returns data up to the LSO. Control records do come back inside the fetched batches, but the consumer client uses them and drops them, so your listener never receives them under either isolation level.

4How read_committed Skips ABORTED Records

How the aborted list reaches the consumersequence diagram
sequenceDiagram participant C as Consumer (read_committed) participant B as Broker (leader order-events P2) C->>B: FetchRequest (isolation = read_committed) Note over B: read records up to the LSO <br/> look up .txnindex for aborted txns in this range B-->>C: FetchResponse: records 0-7 + abortedTransactions [PID 8 from offset 2] Note over C: batch of PID 8 at offset 2 is inside an aborted range: drop <br/> ABORT marker at offset 6 closes the range <br/> PID 8 at offset 7 is after it: keep Note over C: return offsets 0, 1, 4, 7 to poll()

Strictly, the consumer does not open the file itself. The broker reads .txnindex and sends the aborted transactions list (producer id + first offset) in the FetchResponse. The consumer then drops that producer's records from the first offset until it meets the matching ABORT control record.

5Exactly-Once Semantics (EOS) for Read-Process-Write

Remember the consumer-side problem from Transactions (Producer):

Duplicate processing (read-process-write)sequence diagram
sequenceDiagram participant B as Broker participant C as Consumer C->>B: poll() B-->>C: Record (offset 50) Note over C: Processed record C->>B: Publish another event send() C--xB: Offset commit (crash before it lands) C->>B: poll() B-->>C: Record (offset 50) again Note over C: Processed record again C->>B: Publish another event send() → duplicate
🎯

This is the core EOS (Exactly-Once Semantics) problem: read → process → write → commit offset. It happens because write and commit offset are separate steps, so a crash between them causes duplicate writes. “Exactly once” means no duplicates.

EOS = read_committed consumer + idempotency + transaction. In simple terms, EOS makes the write and the offset-commit step atomic: on any failure, neither the write nor the offset commit happens.

Write and offset commit inside one transactionflowchart
flowchart LR R["Read · poll() order-events"] --> P["Process · business logic"] subgraph TX["One Kafka transaction"] W["Write · send to payment-events"] O["Commit offset · sendOffsetsToTransaction"] end P --> W --> O O --> Q{"Commit OK?"} Q -- "Yes" --> Y["Output visible and offset saved together"] Q -- "No" --> N["Abort: output discarded, offset not moved · record re-read"] classDef step fill:#eef4ff,stroke:#2563eb,color:#1e3a8a,stroke-width:1.5px classDef ok fill:#e8f7f5,stroke:#0f9d8f,color:#0b4f48,stroke-width:1.5px classDef bad fill:#fdecea,stroke:#dc2626,color:#7f1d1d,stroke-width:1.5px class R,P,W,O,Q step class Y ok class N bad

The consumed offset is written to __consumer_offsets as part of the producer's transaction. If the transaction aborts, the payment event is never visible to read_committed consumers, and the offset is not committed, so the record is simply processed again. Downstream consumers must use read_committed, otherwise they could still see the aborted output.

The notes write the last line as spring.kafka.producer.enable-idempotence=true; the pass-through form above works on any Spring Boot version. Setting transaction-id-prefix already forces idempotence and acks=all, so those two lines mostly document the intent.

OrderEventListener.javajava
@Component
public class OrderEventListener {

    @Autowired
    private KafkaTemplate<String, Object> kafkaTemplate;

    @KafkaListener(topics = "order-events", groupId = "order-group")
    public void process(ConsumerRecord<String, Object> record, Consumer<?, ?> consumer) {

        kafkaTemplate.executeInTransaction(ops -> {

            // 1. READ happened and a record is received in this method
            String key = record.key();
            Object value = record.value();

            // 2. PROCESS, any business logic here if you want
            Object result = value;

            // 3. WRITE (to another topic)
            ops.send("payment-events", key, result);

            // 4. SEND OFFSET TO TRANSACTION: we are just buffering the offsets
            //    which need to be committed when this txn is committed
            Map<TopicPartition, OffsetAndMetadata> offsets = new HashMap<>();
            offsets.put(
                    new TopicPartition(record.topic(), record.partition()),
                    new OffsetAndMetadata(record.offset() + 1)
            );

            ops.sendOffsetsToTransaction(offsets, consumer.groupMetadata());

            return null;
        });
    }
}
✎
Changes from the notes
  • result was used without being declared; it is now set in the PROCESS step.
  • record.offset() + 1 is correct: the committed offset is always the next offset to read.
  • The notes call sendOffsetsToTransaction(offsets, "order-group"). The String group-id overload is deprecated; passing consumer.groupMetadata() (Spring injects the Consumer parameter) also lets the broker fence zombie consumers. The group id must match the listener's group.
💡

Alternative: instead of calling executeInTransaction yourself, configure the listener container with a KafkaTransactionManager. The container then starts the transaction before calling your listener, any kafkaTemplate.send() inside joins it, and the container sends the offsets to the transaction automatically. Your listener contains only business code.

✅
Summary
  • Transactional records are always written to the log; COMMIT or ABORT control records close each transaction.
  • The LSO is the first offset of the oldest open transaction; read_committed consumers never read past it.
  • read_uncommitted (default) sees everything except control records; read_committed sees only committed and non-transactional data.
  • Aborted records are filtered in the consumer, using the aborted ranges the broker keeps in .txnindex.
  • EOS = read_committed + idempotence + transaction, with sendOffsetsToTransaction making write + commit atomic.
