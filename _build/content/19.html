  • A stateful processing node must remember information from previous records to produce correct output.
  • Stateful operations use state stores (RocksDB) to keep intermediate state, backed by changelog topics (Kafka Streams Architecture).
  • Common examples: count records per key, sum amounts per user.

2groupByKey and groupBy

groupByKey and groupBy are not stateful operations themselves: they store no intermediate state. They are the entry point to stateful processing and have 2 major responsibilities:

  1. Convert KStream → KGroupedStream. This tells the downstream stateful operation which key to aggregate by — the existing key or a new one.
  2. Repartition if required. When the key has changed, they initiate the repartition.

groupByKey

  • Tells downstream stateful operations to use the existing key for aggregation.
  • Use it when the current key is already the key you want to aggregate by.
groupByKeyjava
// optional: only if you want to change the key; otherwise skip selectKey
KStream<String, Order> ordersByUser = orders.selectKey((orderId, order) -> order.getUserId());

KGroupedStream<String, Order> groupedOrders = ordersByUser.groupByKey();

A KGroupedStream is not a normal stream: it has the aggregation methods — count, aggregate, reduce, and windowedBy for windows.

groupBy

groupBy says: “I don't want the current key — I'll tell you a new key (which can even be a different type).”

groupByjava
KGroupedStream<String, Order> groupedOrders =
        orders.groupBy((orderId, order) -> order.getUserId());
⚠

For both, if the key has changed, Kafka Streams must redistribute records (repartition) by the new key. groupBy(f) is effectively selectKey(f).groupByKey(). Plain groupByKey() on an unchanged key needs no repartition at all. Pass Grouped.with(keySerde, valueSerde) when the default SerDes don't match the types written to the repartition topic.

3count

count counts the number of records for each key.

KGroupedStream.count signaturesjava

KTable<K, Long> count(Materialized<K, Long, KeyValueStore<Bytes, byte[]>> materialized);
count with a named storejava
KTable<String, Long> orderCount = orders
        .groupByKey()
        .count(
                Materialized.<String, Long, KeyValueStore<Bytes, byte[]>>as("order-count-store")
                        .withKeySerde(Serdes.String())

SerDes are covered in Chapter 17; note the value SerDe is Serdes.Long() because a count is a Long.

aggregate — total amount per keyjava
KGroupedStream<String, Order> groupedOrders = orders.groupByKey();

KTable<String, Double> totalAmount = groupedOrders.aggregate(
        () -> 0.0,                                                    // initializer
        (key, order, totalFromRocksDB) -> totalFromRocksDB + order.getAmount(),   // aggregator
        Materialized.<String, Double, KeyValueStore<Bytes, byte[]>>as("total-amount-store")
                .withKeySerde(Serdes.String())
                .withValueSerde(Serdes.Double())
);
Step by step for key Alicearchitecture diagram

When Alice arrives the first time, RocksDB has no key Alice, so the initializer provides the starting value 0. Every record then calls the aggregator with the value currently in RocksDB, and the result is stored back. Bob follows the same path: 0 + 200 = 200, then 200 + 300 = 500.

✎

The notes call aggregate(initializer, aggregator) without a Materialized. That compiles, but the store then uses the default value SerDe; with String defaults (as in Chapter 17) writing a Double fails at runtime. So the example above adds Materialized...withValueSerde(Serdes.Double()). A simpler alternative for “same type in, same type out” is reduce().

5KStream–KTable Join

A KStream–KTable join enriches each stream event with the latest value for its key from a table.

KStream.join(KTable) signaturejava
// joiner receives (stream value, latest table value for the key)
// and returns the enriched output
<VT, VR> KStream<K, VR> join(KTable<K, VT> table,
        ValueJoiner<? super V, ? super VT, ? extends VR> joiner);
ValueJoiner.javajava
public interface ValueJoiner<V1, V2, VR> {
    VR apply(V1 var1, V2 var2);
}
enrich orders with the user profilejava
KStream<String, Order> ordersByUser = orders.selectKey((orderId, order) -> order.getUserId());

KTable<String, UserProfile> users = builder.table("users",
        Consumed.with(Serdes.String(), userProfileSerde),
        Materialized.<String, UserProfile, KeyValueStore<Bytes, byte[]>>as("users-store")
                .withKeySerde(Serdes.String())
                .withValueSerde(userProfileSerde)
);

KStream<String, EnrichedOrder> enrichedOrders = ordersByUser.join(
        users,
        (order, user) -> new EnrichedOrder(order, user)
);

  • The key of the KStream and the KTable must be the same (here the user id), which is why the orders are re-keyed with selectKey first. That re-keying causes a repartition before the join, and the topics must be co-partitioned.
  • Only stream records trigger output: a new order looks up the table. A profile update does not re-emit old orders.
  • With join, an order whose user is not in the table produces nothing; leftJoin emits it with a null user.

KTable–KTable join

combine two tables by keyjava
KTable<String, UserProfile> profiles = builder.table("user-profiles");
KTable<String, UserPreference> preferences = builder.table("user-preferences");

KTable<String, CompleteUser> completeUsers = profiles.join(
        preferences,
        (profile, preference) -> new CompleteUser(profile, preference)
);

Unlike the stream–table join, a KTable–KTable join produces a table, and it is updated when either side changes. These two builder.table(...) calls rely on default SerDes, which must therefore match UserProfile and UserPreference. Otherwise pass Consumed.with(...) as above.

KTable–KStream: not possible

❌

A KTable cannot look up into a KStream. A KStream is an unbounded sequence of events; it has no store and cannot be randomly looked up by key. The join must always be started from the stream side (stream.join(table)). Joining two streams is possible, but only inside a time window (KStream.join(KStream, …, JoinWindows)), because Kafka Streams can buffer events only for a bounded time — see Kafka Streams Window.

Summary
  • Stateful nodes remember earlier records in RocksDB stores, backed by changelog topics.
  • groupByKey / groupBy produce a KGroupedStream and repartition when the key changed.
  • count → KTable<K, Long>; aggregate → your own logic with an initializer and an aggregator.
  • KStream–KTable joins enrich events with the latest table value (same key, co-partitioned); KTable–KTable joins combine tables; KTable–KStream is not possible.
