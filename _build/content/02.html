1What is Kafka?

Kafka is a distributed event streaming platform that allows us to:

📤

Publish events

Producers write events into Kafka.

💾

Store events

Events are kept durably in logs (forever or retention based).

📥

Subscribe to events

Consumers read the events they are interested in.

  • A producer is an application that publishes events to Kafka.
  • A producer does not care who will consume this event.

4Partition

📌

A partition is a physical, ordered and append-only log that is part of a topic. A topic can have many partitions.

Topic order-events with 3 partitionsflowchart
flowchart LR PR["Producer1"] --> T subgraph T["Topic name = order-events"] direction TB p0["P0"] p1["P1"] p2["P2"] end classDef prod fill:#111a2e,stroke:#ea580c,color:#fff,stroke-width:2px classDef part fill:#eef4ff,stroke:#2563eb,color:#1e3a8a,stroke-width:1.5px class PR prod class p0,p1,p2 part

Explanation

The topic order-events is split into three partitions P0, P1 and P2. Each partition is its own independent log; the producer's events are spread across them. Let's understand each word of the definition: physical, ordered and append-only.

Physical

Events are actually stored on disk inside the partition. Each partition is a log file on disk named <topic>-<partition>:

on-disk layouttext
Topic: order-events
 ├── Partition0: order-events-0   (partition0 log file)
 ├── Partition1: order-events-1   (partition1 log file)
 └── Partition2: order-events-2   (partition2 log file)

Ordered

Events are written sequentially and assigned incrementing offsets. Consumers read them in offset order.

How offsets are assigned

  • Each partition maintains its own next offset counter.
  • When a new event arrives, Kafka assigns the next offset to that event and appends the event to the log.
  • Here Producer1 sent E0…E4. E0 and E3 landed in P0 (Offset1, Offset2), E1 and E4 in P1, and E2 in P2. Offsets restart in every partition because each partition has its own counter.
✓

Within a single partition — order is guaranteed

Events are written sequentially and read in increasing offset manner. Kafka does not re-order events in a partition.

✗

No global order across partitions

Kafka does not guarantee ORDER globally (across multiple partitions of the topic).

⚠
Example

In Partition0 (P0) we know that Event3 happened after Event0, because Offset2 comes after Offset1 in that partition.

But we cannot guarantee that Event4 in Partition1 happened after (or before) Event0 in Partition0 — because an offset belongs to a partition, not to the whole topic.

5Going One Level Deeper: Segments and Index Files

Segment files

The partition log file is further divided into segments:

Partition log divided into segmentsflowchart
flowchart LR T["Topic: order-events"] --> P["Partition0: order-events-0"] P --> S1["Segment1: 000000.log"] -.-> D1["Stores events with offset 0 – 499"] P --> S2["Segment2: 000500.log"] -.-> D2["Stores events with offset 500 – 999"] P --> S3["Segment3: 001000.log"] -.-> D3["Stores events with offset starting from 1000"] classDef seg fill:#eef4ff,stroke:#2563eb,color:#1e3a8a classDef txt fill:#ffffff,stroke:#cbd5e1,color:#3f4859 class S1,S2,S3 seg class D1,D2,D3 txt

Why segments?

  1. A consumer can say: “I want to read from Partition0 of order-events, offset 550 to 800.”
  2. If, instead of one big log file, the log is divided into multiple small segment files, searching can happen faster.
  3. Each segment file is named by the first offset it contains, so Kafka can directly jump to Segment2: 000500.log.

Retention is applied per segment (7 days / 1 GB)

Segments are also the unit Kafka uses when it cleans up old data. With the delete policy configured as retention.ms=604800000 (7 days) and retention.bytes=1073741824 (1 GB), Kafka never removes individual events from the middle of a file — it deletes whole old segment files.

Which segments of Partition0 survive retentionHTML visualisation

Segment1 DELETED
Size based (1 GB)

total 1.2 GB > 1 GB → oldest segment deleted

Key points

  • Retention works on whole segments. A segment is deleted only when the entire segment is older than retention.ms (e.g. 7 days) — or, for size-based retention, when the partition's total size goes above retention.bytes (e.g. 1 GB) and the oldest segment is removed first.
  • The active segment is never deleted. Kafka always writes to the newest (active) segment; only closed (older) segments are eligible for deletion.
  • Segment size affects how precise retention is. Because cleanup removes a whole segment at a time, some events can be kept a little longer than 7 days until the whole segment they are in has expired.
  • Deletion is cheap. Removing a whole file (its .log plus its .index) is much faster than rewriting a big log, and it is done by an async background job, so writes are not blocked.
  • Retention is per partition. retention.bytes applies to each partition's log separately, not to the whole topic.

The full cleanup policies (delete vs compact) are explained in Log Compaction (Cleanup) Strategies below.

Index file per segment

We can control the segment size too. Say we keep the segment size as 1 GB — then a sequential search inside a 1 GB segment file will also take time. That's why Kafka further maintains an index file per segment:

Not every offset is indexed. Instead, Kafka indexes every N bytes: after N bytes have been written to the log file, it creates one index row. This saves memory and also helps in faster lookup — Kafka finds the nearest indexed offset, jumps to that byte position, and scans forward only a little.

Worked example — when does an index row get created?

  • Offset4 — event size 500 bytes
Configuration
  • Segment size: 1 GB
  • Index interval bytes: 4096 bytes — after this many bytes are written to the log file, one index record is created in the .index file.

Each file position is simply the sum of the sizes of all earlier events (e.g. offset 3 starts at 300 + 500 + 1000 = 1800). The index row maps offset 4 straight to byte 3800, so a read of offset 4 does not need to scan the first 3800 bytes.

6Partitioning Strategies — Which Partition Does an Event Go To?

The producer can pick one of different algorithms to decide which partition of a topic an event should be sent to.

1. Key-based Partitioning

🔑

All events for the same KEY go to the same partition (ordering guaranteed).

publish (topic, key, event)text
Publish:
{
  "order-events",   <-- topic
  orderId,          <-- key
  orderJson         <-- event
}

partition = hash(orderId) % num_partitions

Example:
E0 : hash("123") % 3 = Partition 1
E1 : hash("456") % 3 = Partition 2
E2 : hash("789") % 3 = Partition 0

Because the hash of a given orderId is always the same, every future event for order 123 will also land in Partition 1 — so all events of one order are read in the exact order they were written.

7Broker

  • A broker is a single Kafka server instance.
  • A broker is the one which actually stores data and serves clients (producer and consumer).
  • A broker stores some partitions of some topics.
❗
Important note

Topics and partitions are distributed across multiple brokers. That's why we say one broker stores only some partitions of some topics: it does not hold all topics, and it does not hold all partitions of a topic. We will understand the multiple-broker scenario when we see the Kafka cluster below.

Single broker hosting topic order-eventsarchitecture diagram

Explanation

The broker is the server process; the topic and its partitions live inside it as files on its disk. The producer connects to the broker to write, and consumers will connect to the broker to read.

8Consumers and Consumer Groups

Explanation

  • Two independent applications — notification and analytics — each form a consumer group with Consumer 1 … Consumer N.
  • Inside one group, each partition goes to exactly one consumer (P0 → notification Consumer 1, P1 → notification Consumer N).
  • P1 is read by a consumer of both groups: different groups read the same data independently.

9Committed Offsets and the __consumer_offsets Topic

Each consumer group maintains partition-wise offsets independently:

what is trackedtext
(Consumer group, topic, partition) -> Offset consumed till now

For example:

Consumer GroupTopicPartitionCommitted Offset (processed up to this offset)
notificationorder-events0105
notificationorder-events198
analyticsorder-events060
analyticsorder-events145

The same partition (order-events / 0) is at offset 105 for notification but only at 60 for analytics — each group moves at its own pace.

This consumer-group offset information is stored in Kafka's internal __consumer_offsets topic. In a Kafka UI the topic list shows it like this:

Topic NamePartitions
IN __consumer_offsets50
  • “IN” means INTERNAL — this topic is created internally by Kafka.
  • 50 is the default number of partitions of the __consumer_offsets topic.
ℹ

The source notes write the name as _consumer_offsets; the actual internal topic name (as shown in the UI) starts with two underscores: __consumer_offsets.

How a group's offset is written

Offset commit goes to one partition of __consumer_offsetsarchitecture diagram

Explanation

offset commit messagetext
Publish:
{
  "__consumer_offsets",
  notification_group_id,
  message: (notification_group_id, topic, partition, committed_offset)
}

partition = hash(notification_group_id) % 50 = 23

The group id is the key, so — exactly like key-based partitioning — all offset updates for consumer group notification go to Partition 23 of __consumer_offsets.

Why committed offsets matter

This committed-offset strategy helps when a consumer crashes and, say, a new consumer comes up:

  1. It finds the partition number of topic __consumer_offsets: hash(notification_group_id) % 50 = 23.
  2. The consumer asks the broker which holds Partition 23 of __consumer_offsets: “Till what point are events processed for, say, TopicA-Partition2?”
  3. The broker internally maintains a key-value map built from the __consumer_offsets data — key: (topic, partition), value: committed offset.
  4. The broker checks the map and returns the committed offset value, and the new consumer continues from there.

10Offset Commit Strategies

Strategy 1: Auto-Commit

consumer configproperties
auto.commit.interval.ms=5000

Means: auto commit every 5 seconds. But this strategy is risky. Let's see an example:

Auto-commit losing eventssequence diagram
sequenceDiagram participant C as Consumer participant K as Kafka Note over C,K: Time 0s C->>K: poll K-->>C: events 0-99 Note over C: Time 1s: processing events... Note over C,K: Time 5s: auto-commit triggers C->>K: commit offset 99 Note over C: Time 6s: CRASH (only 50 events processed) Note over C,K: Time 7s: consumer restarts C->>K: where do I start? K-->>C: offset 100 Note over C: Events 51-99 are LOST (at-most-once delivery)

Why events are lost

The commit happened on a timer, not when processing finished. Kafka was told “processed up to 99” while only ~50 events were actually done. After the restart the consumer resumes from offset 100, so the unprocessed events are never seen again — at-most-once delivery.

Strategy 2: Manual Commit

  1. Step 1Poll events 0-99.
  2. Step 2Process ALL events.
  3. Step 3Commit offset 99 (wait for confirmation).
  4. Step 4Kafka confirms the commit.
  5. Step 5Continue to the next batch.

Crash before commit

Events are reprocessed → at-least-once delivery (duplicates possible, but nothing lost).

Crash after commit

Events are not reprocessed — the batch is already recorded as done.

Now the question is: how? How does this multi-broker architecture achieve scalability, availability and fault tolerance? The answer starts with leader–follower partitions.

12Leader–Follower Partitions (Replication)

For each partition, one broker is the Leader and the others are Followers.

Example
  • Topic: order-events — Partitions: 3 (P0, P1, P2) — Replication Factor: 2
  • Each partition has 2 replicas: P0 (one leader and one follower), P1 (one leader and one follower), P2 (one leader and one follower).
  • All these replicas are distributed among the brokers.

  • P2: leader on Broker-3, follower on Broker-2.

Every broker is leader for one partition and follower for another, so the write/read load is spread out (scalability), and every partition has a copy on a second broker (fault tolerance).

Leader responsibility

  • Handle all producer writes
  • Handle all consumer reads
  • Maintain partition logs
  • Coordinate with followers

Follower responsibility

  • Replicate data from leader
  • Stay in sync with leader
  • Be ready to become leader if the current leader fails
  • Do not serve client (producer or consumer) requests

13The Controller

Now one question might have come to your mind. Who decides which broker hosts which partition replica, which partition replica becomes leader, and which partition replica stays a follower?

🧠

Answer: the Controller. It is a special broker whose responsibilities are:

  • Creation of topics
  • Electing partition leaders and followers
  • Detecting broker failures (using heartbeats)
  • Notifying all brokers about the changes

In short, the Controller manages the cluster metadata (info about topics, partitions, brokers etc.), which it records in _cluster_metadata.log.

A Controller node can either have a dual responsibility (normal broker + controller role) or just one responsibility (controller role). For simplicity, the examples use a controller node that only has the controller role.

Step by step

  1. A producer or the admin CLI asks any broker to create topic order-events with 3 partitions and replication factor 2.
  2. That broker does not decide on its own — it passes the request to the Controller.
  3. The Controller creates the topic/partitions, decides leaders and followers and updates _cluster_metadata.log.
  4. The Controller then notifies all brokers (Broker1 … Broker N) of the new layout.

14Who Coordinates the Controllers? KRaft vs ZooKeeper

Knowing about the Controller, a few things come to mind:

  • What if this controller fails? It seems like the brain of the cluster itself.
  • Even if the answer is “we can have multiple controllers”, who will control them? Brokers are coordinated by the controller — but with multiple controllers, who brings coordination among them? Do we need another controller for the controllers? It would become a loop!

KRaft (Modern)

  • KRaft (Kafka Raft) is inbuilt in Kafka.
  • So there is less overhead — no external system to manage.
  • Uses the Raft consensus algorithm.

ZooKeeper (Legacy)

  • An external distributed system which Kafka has to deploy, monitor and maintain separately.
  • Deprecated in the latest versions of Kafka (≥ 3.x) and replaced with KRaft.
  • Uses the Zab consensus algorithm.

Both help Kafka manage cluster metadata (topics, partitions, brokers, controller election). This documentation does not cover ZooKeeper, as it is deprecated.

15Consensus, Quorum and the KRaft Flow

Problem: one Controller is a bottleneck

The Controller is the one that:

  • Stores the cluster metadata.
  • Creates / deletes topics.
  • Decides partition leaders and followers.
  • Keeps track of broker heartbeats and detects any broker failure in time.
  • If any broker fails, redistributes its topic partitions to other brokers.
  • Keeps other brokers up to date about the cluster information.
💥

So, if this Controller fails, the cluster is unavailable: we cannot create new topics; if any broker is down, no one will take over its partition responsibility; and all cluster metadata information is lost. So we need multiple Controllers.

Explanation

Only one controller is Active (Leader) in a cluster; the others act as Followers (Stand By). Brokers exchange heartbeats with the controllers and receive metadata updates; the controllers exchange heartbeats among themselves.

Now: who decides which controller is leader and which is follower? We cannot have another controller to control these controllers (that would become a loop). That's where KRaft, which implements the Raft consensus algorithm, comes into the picture.

Quorum

In this consensus algorithm, all decisions are taken by QUORUM. Quorum means the majority of the nodes.

quorum for 3 controllerstext
Quorum = (N / 2) + 1
       = (3 / 2) + 1      (integer division)
       = 2

So at least 2 controller nodes must agree on any decision before it can be final. For example, quorum happens on: which controller node should become the leader (Active) controller, any change in the cluster metadata information, etc.

Step by step

  1. The producer / admin CLI sends Create Topic “order-events”, 3 partitions, Replication_Factor=2 to any broker.
  2. The broker passes the request to the Active (Leader) Controller.
  3. Controller1 passes it to its KRaft layer, which creates the topic/partitions, decides leader and follower partitions and creates a metadata record — say with offset 100. It updates its local cluster_metadata.log: offset 99 record, offset 100 record (no commit yet), last committed offset: 99.
  4. KRaft initiates the quorum: it asks Controller2 and Controller3 to append the new metadata (offset 100 record). Each stand-by updates its local log: offset 100 record (not committed), last committed offset: 99.
  5. The stand-bys Ack: written successfully in the local file, but not yet committed.
  6. Since the majority was able to write successfully, the active controller commits: its local log now shows last committed offset: 100.
  7. The committed metadata is sent to Broker1, Broker2 … Broker N.

sequenceDiagram participant C1 as Controller1 Raft (Active) participant C2 as Controller2 Raft (Stand By) participant C3 as Controller3 Raft (Stand By) C1->>C2: heartbeat, last committed offset: 100 C1->>C3: heartbeat, last committed offset: 100 Note over C2: offset 100 record (committed), last committed offset 100 Note over C3: offset 100 record (committed), last committed offset 100

Explanation

When the Active Controller sends its heartbeat to the stand-by controllers, it also sends the last committed offset. The stand-bys then mark offset 100 as committed in their local cluster metadata logs, so all three controllers end up with identical, committed metadata — and any of them can take over as leader.

16ISR (In-Sync Replicas)

The Controller also maintains one more important piece of cluster metadata: the ISR.

📌

ISR: for each partition, ISR represents the list of replicas which are fully caught up with the leader.

Example

Topic: order-events, Partition: 1, Replication factor = 3. Leader: Broker 1. Followers: Broker 2, Broker 3.

Possible ISR: ISR = {Broker 1, Broker 2, Broker 3}

Say Broker 3 lags too much:

Result

ISR = {Broker1, Broker2} — Broker 3 is temporarily removed from ISR because it is 3 offsets behind the leader's latest offset 9.

How does the leader decide a follower is out of sync?

✓

A follower is in-sync if

Its replica offset is close enough to the leader's log end offset, and it stays within replica.lag.time.max.ms.

✗

Removed from ISR if it

Stops fetching, or is too slow.

Once the leader identifies that a particular follower broker is out of sync, it requests the Controller to alter the ISR.

17What is the Use of ISR? Producer acks

Producer writes to the partition leaderflowchart
flowchart LR P["Producer · Publish order-events, null, orderJson · ack = 0 or 1 or all"] --> L["Broker (Leader) · Topic: order-events · Partition-2"] L -.- N["Persist the event in Partition-2 logs (one of its segment files)"] classDef prod fill:#111a2e,stroke:#ea580c,color:#fff,stroke-width:2px classDef lead fill:#ea580c,stroke:#9a3412,color:#fff,stroke-width:2px classDef note fill:#fff8e6,stroke:#d97706,color:#78350f class P prod class L lead class N note

Explanation

Along with the event, the producer sets an ack config. If the producer used ack=all, the broker (leader) waits for all ISR replicas to update the event; only then does it send “successfully published” to the producer. This is where ISR is used.

ack valueNameBehaviour
0Fire and ForgetProducer sends record to leader. Producer does not wait for any response and immediately considers the send successful.
1Wait for LeaderProducer sends record. Leader writes the record to its local log and sends ACK back. Producer waits for that ACK.
allWait for all ISR replicasLeader waits until all replicas in the ISR have written the record, then sends ACK.

What if the ISR list becomes empty?

It cannot happen: there is one more piece of cluster metadata —

topic / broker configproperties
min.insync.replicas=2

It tells the minimum number of replicas that should be present in the ISR. If the count goes below this, the partition is UNAVAILABLE (for acks=all writes, the leader refuses the write instead of accepting it with too few copies).

Step by step

  1. Producer creates the event (order-events, key order-123, value orderJson).
  2. Producer requests metadata (first time or on refresh) from any broker, e.g. Broker-1. Broker-1 gets it from the Active Controller and returns: partition 0 → Broker 1, partition 1 → Broker 2, partition 2 → Broker 3.
  3. Producer calculates the partition: hash(order-123) % 3 = 1.
  4. Looks up the broker details: who is leader of Partition 1? → Broker2.
  5. Producer sends the event directly to Broker 2 (no hop through other brokers).
  6. Broker2 writes the event to the Partition 1 log: Segment_00000.log [0][1][2]…[100][101] — new event at offset 101.

  8. The followers (Broker1 and Broker3, Partition 1 followers) do continuous polling and ack when they have updated their partition logs.
  9. When all ISR replicas have acked, Broker2 sends the response back to the producer: “Event Published”.

  2. Finds the partition number of topic __consumer_offsets: hash("notification-service-group-id") % 50 = 23 → Partition 23.
  3. Requests metadata (first time or refresh) through any broker, which asks the Active Controller. Response: __consumer_offsets partition 0 → Broker 1, partition 2 → Broker 2, partition 23 → Broker 3.
  4. Invokes Broker3 — the leader of Partition 23 acts as the Group Coordinator — and requests to join the “notification-service” group.

20Log Compaction (Cleanup) Strategies

Policy 1: Delete (default)

Delete old segments based on time or size. It is an async job.

Policy 2: Compact

Keep only the latest value for each key.

Policy 1: Delete

topic configproperties
cleanup.policy=delete
retention.ms=604800000      # 7 days
retention.bytes=1073741824  # 1GB
⏱ Time based
  • Segment1: created 8 days ago → DELETED
  • Segment2: created 6 days ago → KEPT

Anything older than retention.ms (7 days) is removed.

💾 Size based

Total partition log size becomes more than 1 GB:

  • Segment1: 1 GB
  • Segment2: 200 MB
  • Total: 1.2 GB

So Kafka deletes the old segment, Segment1.

Policy 2: Compact

topic configproperties
cleanup.policy=compact

102user1v2
103user3v1
104user2v2

After cleanup

user1 and user2 each had an older value (v1 at offsets 100 and 101) that was replaced by a newer one, so the old records are dropped. user3 only ever had one value, so it stays. Offsets of the surviving records do not change. Compaction:

  • Happens at segment level
  • Is asynchronous
  • Does not block writes
  • Does not guarantee immediate cleanup

21Kafka Reads and Writes to Disk — So Why Is It So Fast?

One doubt might come to your mind: Kafka is reading from and writing to DISK, and disk reads and writes are slow. Then how come Kafka is so fast?

Page Cache Optimization for event writes

Kafka trusts the OS for caching the log files efficiently.

Writes land in RAM firstflowchart
flowchart LR L["Leader Broker · writes to disk"] --> PC["OS Page Cache (RAM)"] -->|"Asynchronously flush"| D[("Disk")] classDef lead fill:#fff4ec,stroke:#dc2626,color:#7c2d12,stroke-width:2px classDef ram fill:#eef4ff,stroke:#2563eb,color:#1e3a8a,stroke-width:2px class L lead class PC ram

Why this is fast

  • No blocking disk wait — the write returns once it is in the OS page cache; the OS flushes to disk asynchronously.
  • Sequential write (the best case for disks), because Kafka is append-only: no insert in the middle, never modifies old data, never updates a record in place — it only writes at the end. So the disk keeps moving forward.

Zero-Copy Optimization for event reads

Normal read vs Kafka zero-copy readflowchart
flowchart LR subgraph N["Normal read"] direction LR a1[("Disk")] --> a2["OS Page Cache"] --> a3["User Space"] --> a4["Network"] end subgraph Z["Kafka zero-copy · sendfile()"] direction LR b1[("Disk")] --> b2["OS Page Cache"] --> b4["Network"] end classDef us fill:#fef1f1,stroke:#dc2626,color:#7f1d1d classDef net fill:#e8f7f5,stroke:#0f9d8f,color:#0b4f48 class a3 us class a4,b4 net

Explanation

Normally, reading something from disk goes Disk → OS Page Cache → User Space → Network. Kafka says: do not bring the data to my space, send it directly to the network, using the sendfile() system call. The flow becomes Disk → OS Page Cache → Network, and no copy is kept in the Kafka JVM.

Advantages: data copy time and memory saved, CPU cycles saved, high throughput.

22Edge Cases and Failure Scenarios

What happens when the Active Controller fails?

Controller leader electionsequence diagram
sequenceDiagram participant C1 as Controller1 (Leader) participant C2 as Controller2 (Follower) participant C3 as Controller3 (Follower) Note over C1: Controller1 crashes Note over C2,C3: No heartbeat from leader C2->>C3: Election starts - request vote C3-->>C2: Vote for Controller2 Note over C2: Controller2 becomes new leader (2/3 majority) Note over C3: Controller3 remains follower

Impact

Initial state: Controller1 leader, Controller2 and Controller3 followers. When Controller1 crashes, the followers stop receiving heartbeats; Controller2 starts an election and requests votes; Controller3 votes for it, giving a 2/3 majority (the quorum). New leader elected, cluster continues.

What happens when a Leader Partition fails?

Setup: Partition 0 (RF=3) — Leader: Broker1, Followers: Broker2, Broker3.

  1. Step 1Broker 1 (leader) crashes.
  2. Step 2The Controller detects the leader failure, as there is no heartbeat from the leader.
  3. Step 3The Controller triggers leader election. Candidates: Broker 2, Broker 3 (both in ISR). New leader: Broker 2 (selected from ISR).
  4. Step 4The Controller updates metadata — Leader: Broker 1 → Broker 2; ISR: {Broker 2, Broker 3}.
  5. Step 5Clients receive the metadata update; producers/consumers reconnect to Broker 2.
  6. Step 6The system resumes normal operation.
✅

Impact: NO data loss (the new leader has all committed data, because it was in the ISR). Automatic recovery.

What happens when a Follower Partition fails?

Setup: Partition 0 (RF=3) — Leader: Broker 1, Followers: Broker 2, Broker 3.

  1. Step 1Broker 3 crashes.
  2. Step 2The leader (Broker 1) detects that Broker 3 is unresponsive — no timely fetch calls.
  3. Step 3The Controller removes Broker 3 from ISR: {Broker 1, Broker 2, Broker 3} → {Broker 1, Broker 2}.
  4. Step 4The system continues normally — producers still write (acks=all waits for 2 replicas), consumers still read, NO downtime.
  5. Step 5Broker 3 recovers.
  6. Step 6Broker 3 catches up with the leader.
  7. Step 7Broker 3 is added back to ISR: {Broker 1, Broker 2} → {Broker 1, Broker 2, Broker 3}.
✅

Impact: NO data loss, NO downtime.

What happens when a Topic fails?

🎓

When an interviewer asks this question, the answer is: a topic never fails, as it is just a logical category or folder. Partitions fail, which we have seen above.

What happens when a Consumer fails?

Scenario 1: Consumer crashes before committing the offset (manual commit, batch wise)

Crash before commit → duplicatessequence diagram
sequenceDiagram participant C as Consumer participant K as Kafka C->>K: Step 1 - poll K-->>C: offsets 100-199 Note over C: Step 2 - process events 100-150 Note over C: Step 3 - CRASH (before commit) Note over C: Step 4 - consumer restarts C->>K: Step 5 - what is my last offset? K-->>C: Step 6 - offset 99 (last committed) Note over C: Step 7 - reprocess events 100-150 (DUPLICATES)

Result

At-least-once delivery (duplicates possible). Events 100-150 were processed once before the crash and are processed again after the restart, because the last committed offset was still 99.

Scenario 2: Consumer heartbeat timeout — long processing time

  1. Step 1Consumer polls events.
  2. Step 2Consumer starts processing (takes 6 minutes).
  3. Step 3max.poll.interval.ms (5 minutes) is exceeded.
  4. Step 4The Group Coordinator considers the consumer DEAD, as it did not get the expected signal from it (the consumer is busy processing).
  5. Step 5Rebalance is triggered.
  6. Step 6Partitions are reassigned to other consumers.
  7. Step 7The original consumer finishes processing.
  8. Step 8The original consumer tries to commit.
  9. Step 9The Group Coordinator rejects the commit (consumer not in group).
🗑

Result: wasted processing.

🔧 Solutions
  1. Increase max.poll.interval.ms.
  2. Reduce max.poll.records (process smaller batches).
  3. Optimize the processing logic (faster processing).
  4. Use a separate thread pool for processing.
ℹ

In current Kafka clients, heartbeats are sent from a background thread, so a busy consumer can still be heartbeating. What removes it from the group in this scenario is the gap between two poll() calls exceeding max.poll.interval.ms. The outcome — rebalance, reassignment and rejected commit — is the same. (Covered in detail in the consumer chapters.)

What happens when a Broker fails?

Setup: Cluster: 3 brokers. Topic: order-events (6 partitions, RF=3).

  1. Step 1Broker 1 crashes.
  2. Step 2The Controller detects the failure, as it did not receive any heartbeat.
  3. Step 3For each partition where Broker 1 was leader: a new leader is elected from ISR and metadata is updated.
  4. Step 4For each partition where Broker 1 was follower: it is removed from ISR and the partition continues with the remaining replicas.
  5. Step 5Clients receive the metadata update.
  6. Step 6The system continues normally.
✅

Impact: NO data loss. Automatic recovery.

✅ Chapter Summary

  • Kafka = distributed event streaming platform: publish, store, subscribe.
  • Topic = logical category; partition = physical, ordered, append-only log. Order is guaranteed only within a partition.
  • Partition logs are split into segments, each with a sparse index (one row every index interval bytes).
  • Partitioning: key-based (same key → same partition), round robin (no key), or custom.
  • In one consumer group a partition is read by only one consumer; different groups read independently. Committed offsets live in __consumer_offsets (50 partitions, keyed by group id).
  • Auto-commit risks at-most-once; manual commit after processing gives at-least-once.
  • Each partition has one leader and followers; the Controller manages metadata, and multiple controllers agree through KRaft (Raft) quorum.
  • ISR + acks=all + min.insync.replicas give durable writes; failures are handled by electing new leaders from the ISR.
  • Kafka consumers pull. Kafka is fast thanks to the OS page cache, sequential writes and zero-copy reads.
