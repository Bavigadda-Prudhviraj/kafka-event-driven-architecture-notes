Prerequisite

If Kafka Streams Architecture is clear, you know the major part of a Kafka Streams app is writing the topology; the rest is managed by the framework. A topology has 3 parts — Source, Processor, Sink. Today we focus on the SOURCE.

1The Source Node

  • The source is the entry point of a Kafka Streams topology.
  • It reads records from one or more Kafka topics and forwards them to the stream-processing pipeline.

2KStream

Each record read from the source topic partitions is treated as an independent event. Say these events arrive:

order-events
offset 0001 · CREATEDoffset 1001 · SHIPPEDoffset 2001 · DELIVERED
KStream forwards all 3

All 3 events belong to the same orderId = "001", but KStream sees them as 3 separate events and forwards each one down the pipeline. So: use KStream when each record matters.

SourceTypesTopology.java — KStreamjava
@Configuration
public class SourceTypesTopology {

    @Autowired
    public void kstreamDemo(StreamsBuilder builder) {

        KStream<String, String> orders = builder.stream("order-events",
                Consumed.with(Serdes.String(), Serdes.String()));

        orders.peek((key, value) ->
                System.out.println("key=" + key + " value=" + value));

        orders.to("order-events-output",
                Produced.with(Serdes.String(), Serdes.String()));
    }
}
  • StreamsBuilder helps create the topology. Because of @EnableKafkaStreams, Spring Boot injects it into our method.
  • .stream() creates a KStream. Parameters: the source topic(s), and the key and value SerDes — data in Kafka is stored as bytes, so it must be converted into Java objects.
  • peek and to are a processor node and a sink node; we'll see them later.
reading multiple topicsjava

        List.of("order-events", "payment-events"),
        Consumed.with(Serdes.String(), Serdes.String())

Spring does not allow void @Bean methods, so the examples here use @Autowired on a void method, which Spring calls once with the injected StreamsBuilder — the topology code itself is unchanged. Returning the stream from a @Bean also works (see Chapter 15).

3KTable

  • A KTable represents the latest state of each key.
  • It stores the topic in RocksDB and continuously updates the value associated with each key.
Same 3 events, read as a KTablesequence diagram
sequenceDiagram participant T as order-events participant K as KTable participant R as RocksDB (order-events-store) participant P as Pipeline T->>K: offset 0 · 001 · CREATED K->>R: put(001, CREATED) K->>P: forward T->>K: offset 1 · 001 · SHIPPED K->>R: put(001, SHIPPED) — overwrites K->>P: forward T->>K: offset 2 · 001 · DELIVERED K->>R: put(001, DELIVERED) — overwrites K->>P: forward Note over R: key 001 → DELIVERED (only the latest)

The KTable reads events one by one; for each it updates RocksDB and forwards the update downstream. Downstream sees each change as an update to key 001, not as a new independent event. Forwarding may be batched by the record cache (statestore.cache.max.bytes), so quick consecutive updates to one key can collapse into one.

SourceTypesTopology.java — KTablejava
@Configuration
public class SourceTypesTopology {

    @Autowired
    public void kTableDemo(StreamsBuilder builder) {

        KTable<String, String> orders = builder.table("order-events",
                Consumed.with(Serdes.String(), Serdes.String()),
                Materialized
                        .<String, String, KeyValueStore<Bytes, byte[]>>as("order-events-store")
                        .withKeySerde(Serdes.String())
                        .withValueSerde(Serdes.String())
        );

        orders.toStream()
              .peek((key, value) ->
                      System.out.println("key=" + key + " value=" + value))
              .to("order-events-output",
                      Produced.with(Serdes.String(), Serdes.String()));
    }
}

.table() creates a KTable. Parameters:

  • The source topic.
  • The key and value SerDes to deserialize the bytes.
  • A Materialized object: the RocksDB store name, plus key and value SerDes, because RocksDB also stores data as bytes.

Doubt 1: Why keep state if KTable forwards every event anyway?

There are 2 major advantages.

#1 — Another operation in the pipeline needs to look something up. Example: join each order with the customer's current city.

Without KTable (two KStreams)

  • T1: customer record SJ → Delhi
  • T2: customer record SJ → Bangalore
  • T3: order SJ → laptop — needs SJ's current city

Without RocksDB, where would it look? The customer records have already flowed past. They're gone; there is nothing to look up.

With KTable (customers as a table)

after T1
SJDelhi
after T2
SJBangalore

At T3, the join looks up SJ in RocksDB, finds Bangalore and enriches the order.

#2 — Interactive queries. We can expose a REST endpoint that queries this local state store and returns the current state, without querying an external database.

interactive query (sketch)java
@GetMapping("/orders/{id}/status")
public String status(@PathVariable String id) {
    KafkaStreams streams = factoryBean.getKafkaStreams();   // StreamsBuilderFactoryBean
    ReadOnlyKeyValueStore<String, String> store = streams.store(
            StoreQueryParameters.fromNameAndType("order-events-store",
                    QueryableStoreTypes.keyValueStore()));
    return store.get(id);   // latest value for this key, from local RocksDB
}

With several instances, each one holds only its own partitions, so a key may live on another instance. Kafka Streams' metadata API (queryMetadataForKey) tells you which instance has it.

Doubt 2: Does the KTable get priority over the KStream?

The order event needs the customer data in RocksDB. What if the order event arrives before the customer's state exists?

Fresh start-up (no changelog, first-ever start)

  • KStream and KTable source records arrive in parallel.
  • They are processed record by record, in the order they arrive.
  • No priority is given to the KTable.
  • If an order arrives before its customer, the join finds nothing (an inner join drops it; a left join emits it with null).

Restoration or rebalance (RocksDB gone, changelog present)

  • Before processing any new record, the task reads the changelog topic (not the source topic).
  • It rebuilds RocksDB from the changelog.
  • Only then does it process new records from the source topics.

This is not “read the KTable source first” — it is “rebuild the state store from its backup”.

💡

Kafka Streams does try to process records across its input partitions roughly in timestamp order, and max.task.idle.ms lets a task wait briefly for data on all its inputs. That reduces, but does not remove, the “order before customer” race on a fresh start.

Doubt 3: Can a KStream–KTable join even work across partitions?

Say the customers topic has 2 partitions. Customer P0 goes to Task1 on StreamThread-1, customer P1 to Task2 on StreamThread-2. What if an order in Task1 needs customer SJ, who is in Task2?

A KStream–KTable join works seamlessly only with co-partitioning:

  • The same number of partitions in both the orders and the customers topic.
  • The same partitioning strategy (the same key, here customerId, and the same partitioner) for both.

Then orders for SJ and the customer record for SJ always land in the same partition number, and therefore in the same task. Without co-partitioning, a KStream–KTable join does not work. Kafka Streams checks the partition counts at start-up and fails if they differ. If the key is different, re-key with selectKey first, which creates a repartition topic.

The notes write “CONSUMER topic” in the co-partitioning rules; it means the customers topic.

4GlobalKTable

The problem with KTable for reference data

A Kafka Streams app with 2 stream threads, an orders topic with 2 partitions and a countries topic with 2 partitions. Each order has a country id, and we need the country name.

Orders are keyed by order id, countries by country id, so they are not co-partitioned. Task1 sees some countries and Task2 sees others, so an order in Task1 may need a country held by Task2, and the join fails. (IN / US are just example codes.)

The solution: every instance gets all partitions

Global stream thread + global state store per instancearchitecture diagram
  • Each Kafka Streams application instance gets the data of all partitions of the GlobalKTable topic.
  • A separate Global Stream Thread consumes it into a global state store (RocksDB).
  • All tasks running in that instance can query the shared global store, so the join works without co-partitioning and without repartitioning the orders.

In the notes' picture, instance 2 shows Task3 and Task4. With only 2 orders partitions there are only 2 tasks, so instance 2's threads would actually sit idle. The drawing shows that, which is also a reminder that adding threads beyond the partition count does not add parallelism.

⚠

Always use a GlobalKTable for relatively small or reference datasets: every instance keeps a complete local copy of the topic.

Start-up order

  1. On start-up, the global stream thread reads all partitions of the GlobalKTable topics (e.g. countries).
  2. It builds the global RocksDB store.
  3. No changelog is kept for the global store: the source topic itself is the backup, and since the dataset is small, it is simply read in full.
  4. Only after this is complete do the stream threads start.
flowchart TD A["Application start"] --> B["Restore or create GlobalKTable first"] --> C["Start StreamThreads"] classDef step fill:#eef4ff,stroke:#2563eb,color:#1e3a8a,stroke-width:1.5px classDef g fill:#f4efff,stroke:#7c3aed,color:#4c1d95,stroke-width:1.5px class A,C step class B g

This is a “read first” behaviour — but only for GlobalKTable, not for a regular KTable. It also means the GlobalKTable topic should be compacted, so a full read stays small. Global state is read-only from the topology's point of view: updates come only from the topic.

Code

SourceTypesTopology.java — GlobalKTable joinjava
@Configuration
public class SourceTypesTopology {

    private static final ObjectMapper objectMapper = new ObjectMapper();

    @Autowired
    public void globalKTableDemo(StreamsBuilder builder) {

        GlobalKTable<String, String> countries = builder.globalTable("countries",
                Consumed.with(Serdes.String(), Serdes.String()),
                Materialized
                        .<String, String, KeyValueStore<Bytes, byte[]>>as("countries-store")
                        .withKeySerde(Serdes.String())
                        .withValueSerde(Serdes.String())
        );

        KStream<String, String> ordersWithCountry = builder.stream("order-events",
                Consumed.with(Serdes.String(), Serdes.String()));

        KStream<String, String> enriched = ordersWithCountry.join(
                countries,
                // which key to look up in the GlobalKTable
                (orderId, orderJson) -> {
                    try {
                        JsonNode order = objectMapper.readTree(orderJson);
                        return order.get("countryCode").asText();
                    } catch (Exception e) {
                        return null;   // exception handling: null key → record is skipped
                    }
                },
                // how to combine the order with the country name
                (orderJson, countryName) ->
                        orderJson + " | country=" + countryName
        );

        enriched.peek((key, value) ->
                        System.out.println("key=" + key + " value=" + value))
                .to("order-enriched-with-country",
                        Produced.with(Serdes.String(), Serdes.String()));
    }
}

.globalTable() takes the same parameters as .table(): the source topic, key/value SerDes, and a Materialized object with the store name and SerDes.

Join argumentPurpose
countriesthe GlobalKTable to look into
KeyValueMapper (orderId, orderJson) -> countryCodepicks the lookup key from each order. Unlike a KTable join, the stream does not need to be keyed by it — no repartition.
ValueJoiner (orderJson, countryName) -> …builds the output value from both sides
✎

The notes leave the catch block as “exception handling” with no return value, which would not compile; returning null is the simplest fix. With an inner join, an order whose lookup key is null or not found is dropped; use leftJoin to keep it with a null country. Joins are processor nodes, covered in Stateful Processing Nodes.

Summary
  • KStream — every record is an event; no state.
  • KTable — latest value per key in a per-task RocksDB store, backed by a changelog; enables lookups, joins and interactive queries; joins need co-partitioning.
  • GlobalKTable — the whole (small) topic on every instance, loaded before stream threads start; joins with any key, no co-partitioning, no changelog.
