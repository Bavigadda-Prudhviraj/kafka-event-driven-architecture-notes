1Where Exceptions Happen in a Consumer

A consumer processes events in a loop. There are 2 places where an exception can come:

  1. During deserialization of the key or the value.
  2. During processing of the record (the event) inside the listener.
High-level consumer flow and the two failure pointsflowchart
flowchart TD A["poll()"] --> B["deserialize() each record"] B --> C["For each record, invoke the listener and process the record"] C --> D["Commit offset"] D --> A B -.- X1["1st place: exception during deserialization of key or value"] C -.- X2["2nd place: exception while processing the record (event)"] classDef step fill:#eef4ff,stroke:#2563eb,color:#1e3a8a,stroke-width:1.5px classDef bad fill:#fdecea,stroke:#dc2626,color:#7f1d1d,stroke-width:1.5px class A,B,C,D step class X1,X2 bad

Explanation

Every poll() returns a batch of raw records. Each one is deserialized (bytes → key/value objects), then handed to the listener, and finally the offset is committed. A failure in either of the first two stages stops the record from reaching the commit step. Let's first look at the 1st place: deserialization.

2Problem: Deserialization Error Causes an Infinite Loop

The producer sends a plain String value to order-events, but the consumer expects JSON (an Order). The bad record sits at offset 2.

Problem: a poison record at offset 2flowchart
flowchart TD P["Producer · Value = String"] --> B["Broker · next offset to read: 2"] B -- "Poll() fetches event at offset 2" --> C["Consumer · expecting value = JSON"] C --> E["Deserialization exception"] E --> L["Print the error stack trace"] L -- "offset never committed" --> B classDef node1 fill:#eef4ff,stroke:#2563eb,color:#1e3a8a,stroke-width:1.5px classDef bad fill:#fdecea,stroke:#dc2626,color:#7f1d1d,stroke-width:1.5px class P,B,C node1 class E,L bad

Why it never ends

The exception is thrown before the listener runs, so the offset of record 2 is never committed. The next poll() asks for offset 2 again, fails again, and so on: an infinite loop.

Even if we stop the consumer and restart it, it will again start from offset 2 (the last committed position) and again get stuck in the infinite loop.

3Solution: ErrorHandlingDeserializer + Error Handler

Put a wrapper above the deserialization logic. The wrapper catches the exception, so poll() succeeds and the failed record can be passed to an ErrorHandler.

Default behaviour

  • 0 retry, as it is a fatal exception — no matter how many times you retry, the same bytes will fail again.
  • No failure event stored in a DLT.
  • Just error logging, then the offset is committed and the consumer moves on.

4Error Handler Bean: Retry Strategies

1. FixedBackOff

KafkaConsumerConfig.javajava
@Bean
public DefaultErrorHandler errorHandler() {

    DefaultErrorHandler handler = new DefaultErrorHandler(
            new FixedBackOff(1000L, 2));

    return handler;
}

Wait 1000 ms (1 s) before retrying again, and do at most 2 retries:

FixedBackOff(1000L, 2) timelineflowchart
flowchart LR A1["Attempt 1 · fail"] -- "wait 1 s" --> A2["Attempt 2 (Retry-1) · fail"] -- "wait 1 s" --> A3["Attempt 3 (Retry-2) · fail"] --> R["Retries exhausted"] classDef bad fill:#fdecea,stroke:#dc2626,color:#7f1d1d,stroke-width:1.5px classDef end1 fill:#111a2e,stroke:#ea580c,color:#fff,stroke-width:2px class A1,A2,A3 bad class R end1

The second argument counts retries, not attempts: FixedBackOff(1000L, 2) means 1 original attempt + 2 retries = 3 attempts in total.

ℹ

Spring Kafka classifies DeserializationException as not retryable by default (the same bytes can never succeed), which is why the log above showed maxAttempts=0. The retry settings on this page take effect for retryable failures such as processing exceptions; a deserialization failure goes straight to the recoverer.

2. ExponentialBackOffWithMaxRetries

KafkaConsumerConfig.javajava
@Bean
public DefaultErrorHandler errorHandler() {

    ExponentialBackOffWithMaxRetries backOff = new ExponentialBackOffWithMaxRetries(5);
    backOff.setInitialInterval(1000L);
    backOff.setMultiplier(2.0);
    backOff.setMaxInterval(10000L);
    DefaultErrorHandler handler = new DefaultErrorHandler(backOff);
    return handler;
}
  • The first retry happens after a 1 s delay.
  • Each subsequent retry doubles the wait time (×2).
  • The max delay is 10 s: if the doubled delay goes above 10 s, 10 s is used.
  • At most 5 retries.

5Recoverer: What to Do After All Retries

Retry is now part of the error handler — but if all the retries finish, what then? That's where the Recoverer comes into the picture.

Recoverer type hierarchyclass diagram
classDiagram class ConsumerRecordRecoverer { <<functional interface>> +accept(T t, U u) void } class ConsumerAwareRecordRecoverer { <<functional interface>> +accept(ConsumerRecord record, Exception exception) void } class DeadLetterPublishingRecoverer { +accept(ConsumerRecord record, Exception exception) void } ConsumerRecordRecoverer <|-- ConsumerAwareRecordRecoverer : extends ConsumerAwareRecordRecoverer <|.. DeadLetterPublishingRecoverer : implements

Explanation

ConsumerRecordRecoverer is a functional interface (a BiConsumer: void accept(T t, U u)). ConsumerAwareRecordRecoverer extends it with accept(ConsumerRecord<?, ?> record, Exception exception). One implementation, DeadLetterPublishingRecoverer, is already provided by the framework, and its accept method takes care of inserting the failed event into the DLT.

If we want our own recoverer, we can write one too — for example to insert the failed record in a DB instead of a DLT, or to send an alert. We will see that below.

To set both a recoverer and a retry strategy we use this constructor of the error handler:

DefaultErrorHandler (Spring Kafka)java
public DefaultErrorHandler(ConsumerRecordRecoverer recoverer, BackOff backOff) {
    ...
}

6Add the DLT to the Error Handler

KafkaConsumerConfig.javajava
@Bean
public NewTopic orderDltEventsTopic() {
    return TopicBuilder.name("order-events-dlt").build();
}

@Bean
public DeadLetterPublishingRecoverer deadLetterPublishingRecoverer(KafkaTemplate<Object, Object> template) {
    return new DeadLetterPublishingRecoverer(template);
}

@Bean
public DefaultErrorHandler errorHandler(DeadLetterPublishingRecoverer recoverer) {

    DefaultErrorHandler handler = new DefaultErrorHandler(recoverer,
            new FixedBackOff(1000L, 2));

    return handler;
}
BeanWhat it does
orderDltEventsTopicCreates the DLT, order-events-dlt, in which failed events will be stored.
deadLetterPublishingRecovererThis framework class has all the code to push records whose deserialization failed to the DLT. All we need to provide is a KafkaTemplate object, built from the spring.kafka.producer.* properties in application.properties (key serializer, value serializer, etc.).
errorHandlerNow has both the retry feature and the DLT. After all retries finish, it invokes the DeadLetterPublishingRecoverer accept method and passes the ConsumerRecord and Exception objects.

How the DLT works internally

From poison record to order-events-dltarchitecture diagram

Explanation

  1. The broker returns the record as topic, partition, raw key bytes[] and raw value bytes[].
  2. Deserialization fails. The wrapper intercepts it and creates a DeserializationException object with the complete exception details.
  3. A ConsumerRecord is still created: Value = null if the value failed (else the data), Key = null if the key failed (else the data). The headers carry the exception and the raw bytes — springDeserializerExceptionKey for the key, springDeserializerExceptionValue for the value. Whichever part failed (key, value or both), its raw bytes go into its header.
  4. The ErrorHandler calls accept(ConsumerRecord, exception).
  5. DeadLetterPublishingRecoverer inserts the record into the <topicName>-dlt topic.
The same flow as a sequencesequence diagram
sequenceDiagram participant B as Broker (order-events) participant W as ErrorHandlingDeserializer participant D as Delegate (JsonDeserializer) participant EH as DefaultErrorHandler participant R as DeadLetterPublishingRecoverer participant DLT as order-events-dlt B->>W: poll() returns raw key bytes[] + raw value bytes[] W->>D: deserialize(value bytes) D--xW: exception Note over W: create DeserializationException <br/> value = null <br/> header springDeserializerExceptionValue = raw bytes W->>EH: ConsumerRecord (value null) + exception Note over EH: retries per BackOff <br/> (skipped: not retryable) EH->>R: accept(record, exception) R->>DLT: send ProducerRecord via KafkaTemplate EH-->>B: commit offset, move on

The listener is never called for the failed record. The offset is committed only after the recoverer has handled it, so the event is kept in the DLT instead of being lost.

Conceptual internal working of accept

DeadLetterPublishingRecoverer.accept (conceptual)java
public void accept(ConsumerRecord<?, ?> record, Exception exception) {

    // 1. Find the raw bytes from the exception
    byte[] rawKeyBytes = ((DeserializationException) exception).getHeader("springDeserializerExceptionKey");
    byte[] rawValueBytes = ((DeserializationException) exception).getHeader("springDeserializerExceptionValue");

    // 2. Create a NEW record for the DLT topic
    ProducerRecord<Object, Object> dltRecord = new ProducerRecord<>(
            record.topic() + "-dlt",                               // destination topic
            record.key() != null ? record.key() : rawKeyBytes,     // key could be null: if key deserialization failed, add raw bytes
            record.value() != null ? record.value() : rawValueBytes); // value could be null: if value deserialization failed, add raw bytes

    // 3. send it
    kafkaTemplate.send(dltRecord);
}
✎

This is a simplified model, not the framework source. The notes had small typos (DeserializationExceptionexception, record.getTopic()-"dlt"); they are fixed above to valid Java: a cast (DeserializationException) exception and record.topic() + "-dlt". By default the real recoverer also publishes to <topic>-dlt on the same partition number as the original record, so the DLT should have at least as many partitions as the source topic.

7Brainstorming: Which Serializer Does the DLT Producer Need?

The DLT record is sent with the producer's serializers. Whether the key or value is raw bytes depends on which part failed.

Use case 1: value deserialization failed

ConsumerRecord: Value = null, Key = O-111, header springDeserializerExceptionValue : value bytes[]

new ProducerRecord<>("order-events-dlt", "O-111", valueBytes);

Serializers needed:

# for Key
spring.kafka.producer.key-serializer=org.apache.kafka.common.serialization.StringSerializer
# for value
spring.kafka.producer.value-serializer=org.apache.kafka.common.serialization.ByteArraySerializer

Use case 2: key deserialization failed

ConsumerRecord: Value = Order object, Key = null, header springDeserializerExceptionKey : key bytes[]

new ProducerRecord<>("order-events-dlt", keyBytes, order);

Serializers needed:

# for Key
spring.kafka.producer.key-serializer=org.apache.kafka.common.serialization.ByteArraySerializer
# for value
spring.kafka.producer.value-serializer=org.springframework.kafka.support.serializer.JsonSerializer

The two use cases need opposite serializers — that's challenging.

💡
My take

In most scenarios the key is a String, so there is very little chance of a key deserialization issue. Deserialization issues mostly come with the value (JSON serialization and deserialization), and when they do, raw bytes[] are published. So this works fine:

application.properties — common case (String key)properties
# for Key
spring.kafka.producer.key-serializer=org.apache.kafka.common.serialization.StringSerializer
# for value
spring.kafka.producer.value-serializer=org.apache.kafka.common.serialization.ByteArraySerializer

But if your key is also an object, the deserialization issue could be with only the key, only the value, or both. Then it is hard to choose between ByteArraySerializer and JsonSerializer.

Answer: override the createProducerRecord method so that key and value are always bytes, and use ByteArraySerializer for both:

application.properties — object keysproperties
# for Key
spring.kafka.producer.key-serializer=org.apache.kafka.common.serialization.ByteArraySerializer
# for value
spring.kafka.producer.value-serializer=org.apache.kafka.common.serialization.ByteArraySerializer
KafkaConsumerConfig.java — key and value always bytesjava
@Bean
public DeadLetterPublishingRecoverer deadLetterPublishingRecoverer(KafkaTemplate<Object, Object> template,
                                                                   ObjectMapper objectMapper) {

    DeadLetterPublishingRecoverer recoverer = new DeadLetterPublishingRecoverer(template) {
        @Override
        protected ProducerRecord<Object, Object> createProducerRecord(ConsumerRecord<?, ?> record,
                TopicPartition tp, Headers headers, byte[] key, byte[] value) {
            try {
                // key / value are the raw bytes when that part failed to deserialize, otherwise null
                Object finalKey = (key != null) ? key : objectMapper.writeValueAsBytes(record.key());
                Object finalValue = (value != null) ? value : objectMapper.writeValueAsBytes(record.value());
                return new ProducerRecord<>(tp.topic(), tp.partition(), finalKey, finalValue, headers);
            } catch (JsonProcessingException e) {
                throw new IllegalStateException("Could not convert record to bytes for the DLT", e);
            }
        }
    };
    return recoverer;
}

@Bean
public DefaultErrorHandler errorHandler(DeadLetterPublishingRecoverer recoverer) {
    DefaultErrorHandler handler = new DefaultErrorHandler(recoverer, new FixedBackOff(1000L, 2));
    return handler;
}
✎

Compared with the notes: the extra ) after record.key() is removed, objectMapper is injected as a bean parameter, and writeValueAsBytes is wrapped in try/catch because it throws the checked JsonProcessingException, which an overriding method cannot declare. tp is the destination partition the recoverer already resolved (order-events-dlt, same partition number).

9Exceptions While Processing the Record

What if the exception comes during processing of the record, for example a NullPointerException inside the listener?

Explanation

  • For deserialization issues we have to add the wrapper, so that the error reaches the Default Error Handler.
  • For exceptions during processing, the default error handler is provided by default: it logs the error and commits the offset.
ℹ

Unlike deserialization errors, a processing exception is retryable. Spring Kafka's default DefaultErrorHandler uses FixedBackOff(0, 9): up to 9 immediate retries (10 delivery attempts) before it logs the failure and commits.

Now, if we want retry and, after all retries finish, a recoverer (like the DLT), everything is the same as what we did for deserialization: the same DefaultErrorHandler(recoverer, backOff) bean handles both kinds of failure.

✅
Summary
  • A record that can't be deserialized blocks its partition forever unless ErrorHandlingDeserializer wraps the real deserializer.
  • The default error handler skips and commits, and the event is lost — so define your own DefaultErrorHandler.
  • Choose a BackOff: FixedBackOff or ExponentialBackOffWithMaxRetries.
  • Choose a recoverer: DeadLetterPublishingRecoverer to <topic>-dlt, or your own lambda (DB, alert).
  • Make the DLT producer's serializers match what is published (raw bytes for the failed part).
