1Why Do We Need Transactions in Kafka?

There are three problems that the idempotent producer from Idempotency cannot solve:

#ProblemSide
1Idempotency breaks when the producer restartsProducer
2Partial writes across topicsProducer
3Duplicate processing in read-process-writeConsumer

Problem 1: Idempotency — a restarted producer gets a new PID

Recall how an idempotent producer gets its Producer ID (PID):

Recap: how a producer gets a PID (idempotency)sequence diagram
sequenceDiagram participant P as Producer participant B as Broker participant C as Controller P->>B: 1. Give me Unique ID B->>C: 2. Pass the request to Controller Note over C: 3. Pick next available PID <br/> (e.g. till 1000 is used, so pick 1001) C-->>B: 4. PID = 1001 B-->>P: 5. PID = 1001

The controller only hands out the next free number. It does not store any producer → PID mapping. So when the producer restarts and asks again, it always gets a new PID.

Restart with a new PID → duplicate batchsequence diagram
sequenceDiagram participant P as Producer participant B as Broker (Topic-A, P0) P->>B: Give me PID B-->>P: PID: 1001 P->>B: Batch1 · PID 1001 · baseSequence 3 · lastSequence 5 (E1, E2, E3) Note over B: .log: Header baseSequence-3, lastSequence-5, PID-1001 <br/> E1 offset1, E2 offset2, E3 offset3 <br/> state: PID 1001 · A · P0 · last seq 5 Note over P: Producer crashed <br/> and might have missed the ACK P->>B: Give me PID B-->>P: PID: 2001 P->>B: Batch1 again · PID 2001 · baseSequence 3 · lastSequence 5 Note over B: PID 2001 is new, so the sequence check passes <br/> E1, E2, E3 written AGAIN → DUPLICATE <br/> state: 1001 · A · P0 · 5 and 2001 · A · P0 · 5

Explanation

The producer re-sends the same batch after restarting — perhaps because it is reading from an upstream database and does not see a “processed” flag yet. The broker deduplicates per (PID, partition, sequence). Because the PID changed from 1001 to 2001, the broker sees a brand-new producer at sequence 3 and writes the events a second time. Idempotency only protects retries within one producer session.

Problem 2: Partial writes

three independent sendsjava
// success
kafkaTemplate.send("order-events", order);

// success
kafkaTemplate.send("payment-events", payment);

// Fails (broker down or network issue)
kafkaTemplate.send("inventory-events", stock);
❌

Outcome: order-events and payment-events have records, but inventory-events does not. Consumers see partial data, which can lead to an inconsistent state: the payment was made, but the stock was not reserved.

Problem 3: Duplicate processing (read-process-write)

Crash between publishing and committingsequence diagram
sequenceDiagram participant B as Broker participant C as Consumer C->>B: poll() B-->>C: Record (offset 50) Note over C: Processed record C->>B: Publish another event send() C--xB: Offset commit (lost / crashed) C->>B: poll() B-->>C: Record (offset 50) again Note over C: Processed record again C->>B: Publish another event send() → DUPLICATE

The output event and the offset commit are two separate writes. If the consumer dies after send() but before the commit, offset 50 is delivered again, processed again, and the output event is published twice. The cure is to make the output event and the offset commit part of one transaction; the consumer side is covered in Transactions (Consumer).

✅

Solution: Transactions in Kafka. All writes in a transaction become visible together or not at all (atomic), and the PID survives restarts. The rest of this chapter walks the protocol step by step.

2Step 1: Transaction Id

  • Each producer assigns itself a unique transaction id.
  • If the producer application has multiple instances, each instance must have a different unique id.
  • The id must be stable: when the application restarts, it must not change.
application.properties — choosing the prefixproperties
# Good: Kubernetes injects HOSTNAME (stable per pod, e.g. StatefulSet order-serv-0)
spring.kafka.producer.transaction-id-prefix=order-serv-${HOSTNAME}-

# Good: if each instance has a different port
spring.kafka.producer.transaction-id-prefix=order-serv-${server.port}-

# Don't do this for uniqueness: the id changes on every restart
spring.kafka.producer.transaction-id-prefix=order-serv-${random.uuid}-
⚠

Why not ${random.uuid}? With every restart the id changes, which breaks the transaction guarantees: the coordinator can no longer link the new instance to its old, unfinished transaction. ${HOSTNAME} is stable only when the pod name is stable (a StatefulSet); a Deployment gives each new pod a random name.

Why does each instance need its own unique id? To avoid zombies, using Zombie Fencing. We cover that after Step 3, once the PID and epoch are in place. Spring adds a suffix to the prefix (for example order-serv-0, order-serv-1) for each producer it creates.

  • __transaction_state has 50 partitions, divided among the brokers.
  • A given producer's transactions always go to one specific partition.

4Step 3: Get the Producer ID and Epoch

  • Using transactions in Kafka also enables idempotency internally, and idempotency needs a PID.
  • In short, the idempotent producer ensures no duplicates (even with retries) and ordering per partition (via sequence numbers). Transactions need idempotency so that retries are safe.
InitProducerId (done once)sequence diagram
sequenceDiagram participant P as Producer (txn-id order-serv-0) participant TC as Transaction Coordinator participant TS as __transaction_state P23 P->>TC: InitProducerIdRequest (Transaction id = "order-serv-0") TC->>TS: Write: id "order-serv-0" · PID 5 · Epoch 0 · State Empty · Partitions [] TC-->>P: Response: { PID = 5, Epoch = 0 }

Recall the idempotency problem: the controller did not store any producer → PID mapping, so a restarted producer always got a new PID. This is resolved with transactions, because __transaction_state holds the mapping.

Transaction statesstate diagram
stateDiagram-v2 direction LR [*] --> EMPTY EMPTY --> ONGOING: first send ONGOING --> PREPARE_COMMIT: commit ONGOING --> PREPARE_ABORT: abort or timeout PREPARE_COMMIT --> COMMIT PREPARE_ABORT --> ABORT COMMIT --> ONGOING: next transaction ABORT --> ONGOING: next transaction

The final states appear in the broker as COMPLETE_COMMIT and COMPLETE_ABORT (the notes write them as COMMIT / COMMIT_COMPLETED and ABORT / COMPLETED_ABORT).

💡
Advantages of keeping this mapping
  1. A producer with the same transaction id always gets the same PID, even after a restart. The duplicate problem from Problem 1 is solved.
  2. PID + Epoch enables Zombie Fencing.

Zombie fencing

Old producer (epoch 0) is fenced by the new one (epoch 1)architecture diagram

Explanation

  1. Producer1 (txn.id T1) initialises and gets PID 5, Epoch 0. The coordinator stores T1 as EMPTY.
  2. Producer1 begins a transaction and sends to order-events P0 and payment-events P2. T1 becomes ONGOING with those two partitions.
  3. Producer1 hits a network pause. It is considered inactive, and a new Producer2 with the same transaction id T1 takes its place.
  4. Producer2 sends InitProducerId for T1. The coordinator finds the mapping, ABORTs the ongoing transaction, increases the epoch to 1 and returns PID 5, Epoch 1.
  5. Somehow the old Producer1 becomes active again and sends COMMIT with epoch 0. The latest version for T1 is epoch 1, so the coordinator rejects it with ProducerFencedException. The request came from a zombie.

This is why every instance needs its own stable transaction id: the id is how the coordinator recognises “the same producer, restarted” and fences off the old copy.

5Step 4: Begin the Transaction and Send Events

AddPartitionsToTxn before the first write to each partitionsequence diagram
sequenceDiagram participant P as Producer (order-serv-0) participant TC as Transaction Coordinator participant TS as __transaction_state P23 participant B1 as Broker-1 (leader order-events P2) participant B2 as Broker-2 (leader payment-events P1) Note over P: begin_transaction Note over P: First: send("order-events", key, order) P->>TC: AddPartitionsToTxnRequest {order-serv-0, PID 5, Epoch 0} · order-events P2 TC->>TS: State ONGOING · Partitions [{order-events, P2}] TC-->>P: OK P->>B1: send("order-events", key, order) · header has PID + Epoch B1-->>P: ACK Note over P: Second: send("payment-events", key, payment) P->>TC: AddPartitionsToTxnRequest {order-serv-0, PID 5, Epoch 0} · payment-events P1 TC->>TS: Partitions [{order-events, P2}, {payment-events, P1}] TC-->>P: OK P->>B2: send("payment-events", key, payment) · header has PID + Epoch B2-->>P: ACK

beginTransaction() itself makes no network call. Each send() to a partition that is new to this transaction is intercepted: the producer first registers that partition with the coordinator, so the coordinator knows exactly where to write the commit/abort markers later. Every record carries the PID and epoch in its batch header.

6Step 5: Two-Phase Commit Protocol

Phase 1: PREPARE · Phase 2: write markers and finalisesequence diagram
sequenceDiagram participant P as Producer (order-serv-0) participant TC as Transaction Coordinator participant TS as __transaction_state P23 participant B1 as Broker-1 (order-events P2) participant B2 as Broker-2 (payment-events P1) Note over P: commit transaction P->>TC: EndTxnRequest (order-serv-0, PID 5, Epoch 0) TC->>TS: PREPARE (point of no return) · State PREPARE_COMMIT Note over TS: wait for replication to all ISR of P23 TC->>B1: Commit marker · PID 5, Epoch 0 Note over B1: adds CONTROL record COMMIT B1-->>TC: done TC->>B2: Commit marker · PID 5, Epoch 0 Note over B2: adds CONTROL record COMMIT B2-->>TC: done TC->>TS: FINALIZE · State COMMIT_COMPLETED TC-->>P: Return: Success

Explanation

  • PREPARE_COMMIT is the point of no return. The coordinator waits until it is replicated to all ISRs of __transaction_state P23. After that, whatever happens (even a broker failure), the commit will ultimately be retried and completed.
  • The coordinator then writes a COMMIT control record (marker) into every partition involved: order-events P2 on Broker-1 and payment-events P1 on Broker-2.
  • When all markers are written, it records the final state and returns success to the producer.

In the real protocol the producer gets its response once PREPARE_COMMIT is durable; the markers are written asynchronously after that.

Abort works the same way, with no other difference: first PREPARE_ABORT is written, then every partition in the transaction gets an ABORT control record, and finally the completed-abort state is stored. When a new transaction starts, the whole process repeats from Step 4.

Setting transaction-id-prefix is all it takes for Spring Boot to create a transactional producer factory (which also turns on idempotence).

OrderController.java — just a controller methodjava
@PostMapping("/txn-commit")
public ResponseEntity<String> txnCommit(@RequestBody Order order) {
    Payment payment = new Payment("PAY-" + order.getOrderId(), order.getCustomerId(), order.getTotalAmount(), "PAID");
    String result = orderProducerService.sendTransactionalCommit(order, payment);
    return ResponseEntity.ok(result);
}
OrderProducerService.javajava
@Autowired
KafkaTemplate<String, Object> kafkaTemplate;

public String sendTransactionalCommit(Order order, Payment payment) {

    return kafkaTemplate.executeInTransaction(ops -> {

        // Send 1: order-events
        SendResult<String, Object> orderResult = ops.send("order-events", order.getOrderId(), order).join();

        // Send 2: payment-events (same transaction)
        SendResult<String, Object> paymentResult = ops.send("payment-events", payment.getPaymentId(), payment).join();

        return "COMMITTED";
    });
}

All the send() calls that need to be atomic must happen within the same transaction, i.e. inside executeInTransaction. A simplified sketch of what that method does:

KafkaTemplate.executeInTransaction (simplified)java
public <T> T executeInTransaction(OperationsCallback<K, V, T> callback) {
    producer = producerFactory.createProducer(this.transactionIdPrefix);
    producer.beginTransaction();
    try {
        T result = callback.doInOperations(this);
        producer.commitTransaction();
        return result;
    }
    catch (Exception ex) {
        producer.abortTransaction();
        throw ex;
    }
}
⏳
Why join() matters

Recall from Producer Setup that send() is asynchronous: the application thread's work ends once the record is handed to the pipeline, and it is free to take other requests. The rest happens in the background.

send()→1 · Serializer→2 · Partitioner→3 · Record Accumulator→4 · Compression→5 · Sender Thread

With join() the application thread waits for the ACK. If any send fails, the exception is thrown inside the callback and the transaction is aborted. Note that commitTransaction() also flushes pending sends, so the transaction stays atomic either way; join() makes the failure surface right at the failing send.
