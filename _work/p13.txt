                                   Above code has one MAJOR FLAW:

                                 We are writing to 2 separate independent systems:
                                      a. DB
                                      b. Kafka

                                 There is no Transactions that spans both.

                                 Failure Scenarios:
                                  1. DB succeeds, Kafka Fails

                                          orderRepository.save(order); //Saved to DB
                                          kafkaTemplate.send("order-events"); //Kafka is down
                                  Result:
                                   · Order exists in DB, but NO event published.
                                   · Payment service never gets notified
                                   · Inventory never decremented
                                  This is DATA INCONSISTENCY.

                                  2. Kafka succeeds, DB Fails
                                      kafkaTemplate.send("order-events"); //Kafka event published
                                      orderRepository.save(order); //DB connection lost

                                  Result:
                               · Event published but order doesn't exist in DB
                               · Payment service processes a non existent order.
                               · Inventory decremented for order which does not exist in DB.

                                  This is DATA INCONSISTENCY and more impact than Use-case#1

                                                                        Outbox Table Schema:

           · Its just a regular DB table in our application.
           · Contains columns which are required to successfully publish an event.
          Most Common Schema Sample:

             Id Aggregate_type Event_type Aggregate_id payload Created_At Is_published

             101  Order             ORDER_CREATED ORD-1                  {...}                false

             Id: Unique Id for this event. As producer can publish multiple time same event. So this can be used for Idempotency.
             Aggregate_type: What entity this event is about like "ORDER" or "PAYMENT" etc. Used to determine which Kafka topic to publish to.
             Event_type: Tells what happened with entity like ORDER_CREATED, ORDER_CANCELLED etc.
             Aggregate_id: This is used as message Key. As all related events should goes to the same partition, so this played a major role in
             maintaining order.
             Payload: the actual data.
             Created_At: when the event was created.
             Optional field:
                                     Is_published: False -> not yet sent to Kafka.
                                                      True -> sent to kafka. Can be cleaned later.

                                                                   Disadvantages of Polling:

       1. Multi-Instance handling:
       When we have multiple instance, means multiple POLLERS, which could lead to:
        · Duplicate processing of Rows:

           So need locking mechanism like "SELECT ... FOR UPDATE SKIP LOCKED"
        · Ordering Risk:

           what if 2 POLLERS pick different rows which could lead to break ordering.
        · ShedLock:

           To preserve ordering in multiple instance scenario, we need something like ShedLock technique.

       2. Polling Gap:
               Event created at 10:00:00 but Poll runs at 10:00:02
               -> 2 sec delay

       3. Constant DB load:
           Even when there is no events, Poller has to continuously query DB.
           This cause an extra CPU+IO overhead.

       4. DB clean up:
           Outbox Event table need to be clean up regularly, as its size will grow rapidly.

       5. Duplicate processing:
           Event published to kafka, but processed=True update failed.
           So during next run, again same event might get published, so Consumer must be IDEMPOTENT.

 WAL file     Before INSERT/UPDATE/DELETE first WAL file is written and flushed to disk.

Postgres      This help Postgres in case recovery.

              Also the same WAL file is used for Replication to followers.

              Similarly,
              In MySQL its Binlog file which is use for replication to followers

              CDC reads get these log files only from DB.

                                      Need to change from Replica to Logical for CDC to work.
                                      Replica: in WAL data is stored in Binary form
                                      page5, offset 120 -> changed from X to Y
                                      But this is of no use for CDC.
                                      CDC need more info like which table, column etc.
                                      Logical: in WAL data is still in Binary form + some extra metadata for decoding.
                                      Table = order
                                      Row id = 1
                                      Column "Amount" changed from 100 to 200
                                      Now CDC can publish event properly.
