                                                           Pre-requisite:

If we are clear with Kafka Stream Architecture, then we already know that the major part in Kafka Stream is
writing TOPOLOGY.
Rest is all managed by framework.

                                    TOPOLOGY has 3 parts:

                                    · Source
                                    · Processor
                                    · Sink

                                    Today, lets focus on "SOURCE".

· Source is the entry point of a Kafka Streams topology.
· It reads records from one or more Kafka topics and forwards them to the stream processing pipeline.

like raw material                   Source:                       · Entry point, read records from 1 or more Kafka Topics

                                    Topic "order-events"          · Deserialize bytes to Key-value pairs

Each record read from the source topic partitions, is treated as an independent event.

                                         Example:
           Lets say below are the events coming from the source partitions:

                   offset 0: { orderId: "001", status: "CREATED" }
                   offset 1: { orderId: "001", status: "SHIPPED" }
                   offset 2: { orderId: "001", status: "DELIVERED" }

Notice that all 3 events belongs to 1 orderId ="001" only. But KStream sees them as 3 separate events and
forwards each event to stream pipeline.
So,
Use KStream, when each record matters.

Now couple of doubt might come:

1st doubt:
What's the point of storing the event latest state in RocksDB, when KTable also send each event forwards to stream pipeline like
KStream.

                          There are 2 major advantages:

#1. When some other operation in the stream pipeline need to look up.

                          Example:

Use-case: without KTable

KStream: Order topic
KStream: Customer topic

T1: Customer record arrives:
                  key="SJ", value="Delhi"

T2: Customer record arrives:
                  key="SJ", value="Bangalore"

T3: Order arrives:
                  key="SJ", value="laptop"

   and join with Customer record, so that we can have customer city too along with order details.
At T3, the join needs SJ's CURRENT city.
Without RocksDB, where would it look? The customer records already flowed past. They're gone. There's nothing to look up.

Use-case: with KTable
KStream: Order topic
KTable: Customer topic

T1: Customer record arrives:                                  RocksDB
                  key="SJ", value="Delhi"
                                                              Key Valu
T2: Customer record arrives:                                        e
                  key="SJ", value="Bangalore"
                                                              SJ Delhi
                                                              RocksDB

T3: Order arrives:                                            Key Value
                  key="SJ", value="laptop"
                                                              SJ Delhi
                                                                    Bangalore

and join with Customer record, so that we can have customer city too along with order details.

At T3, the join needs SJ's CURRENT city.

With RocksDB, we can easily find the city "Bangalore" and enriched our order details with it.

                   #2. Interactive Queries:
                One big advantage of RocksDB is that, we can expose REST API endpoint, that query this local state store and
                return the current state without querying external database.

2nd doubt:
   Say, in example which we have taken above:
                                       Use-case: with KTable
                                       KStream: Order topic
                                       KTable: Customer topic

    Does KTable partition events is given priority over KStream? Because Order event need to do join with
    Customer data stored in RocksDB?
    So what if Order event comes before Customer RocksDB state is created?

                          Fresh Startup:                                          Restoration or Rebalance:
   (No changelog present, first ever startup)
                                                                (RocksDB files on disk are gone but changelog topic present)
KStream and KTable source records arrive in parallel
 Processed record by record in the order they arrive          Before processing ANY new records:
 NO priority given to KTable over KStream                       Task reads the CHANGELOG topic (not the source topic)
 If an order arrives BEFORE its customer, the join gets null    Rebuilds RocksDB from changelog
                                                                Only THEN starts processing new records from source topics

                                                              This is NOT "read KTable source first" -- it's "rebuild state store from backup"

                                             GlobalKTable:

Problem with KTable:

Imagine in a kafka Stream Application, we have 2 stream Thread and we have
- orders topic with 2 partitions
- countries topic with 2 partitions

And each order event has country-id from that I need to join the countries and find the country name.

Stream Thread 1                                        Stream Thread 2

       Task1                                              Task2

Topology:                                             Topology:
KStream: Order: P0                                    KStream: Order: P1
KTable: Countries: P0                                 KTable: Countries: P1

Notice that, Countries partitions are divided among multiple tasks.

So Task1 -> gets Countries Partition P0 -> sees SOME countries
    Task2 -> gets Countries Partition P1 -> sees OTHER countries
     So possible that, order event in TASK-1 might need a country that's on TASK-2, which cause JOIN
     FAILS

                        That's where GlobalKTable comes into picture

· Each Kafka Stream Application gets all partitions data of GlobalKTable topic

· Always use GlobalKTable for relatively small or reference datasets, because every Kafka Streams application instance
  maintains a complete local copy of the topic in its Global State Store.

Good candidates for GlobalKTable
· Countries
· Currency codes
· Configuration

   etc.

                                              Note:

On startup:
 1. Global Stream Thread reads ALL partitions of "countries" topic (GlobalKTable topics)
 2. Builds the global RocksDB store.
 3. There is no changelog maintained for global RocksDB Store. Reason GlobalKTable is meant to hold small dataset only. So during
startup, it read full topic (all partitions) itself.
 4. ONLY AFTER this is complete, stream threads start

This is a "read first" behavior - but only for GlobalKTable, not for regular KTable.

                                   Application Start

                                   Restore or create GlobalKTable first

                     Start StreamThreads
