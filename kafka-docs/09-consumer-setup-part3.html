Consumer Setup – Part 3 (Other Configurations)

The consumer read flow again, step by step, but this time answering the doubts at each step with the configuration that controls it: metadata refresh, partition assignment strategies and rebalancing (Range, RoundRobin, Sticky, CooperativeSticky), auto-offset-reset, poll timeout and fetch size limits, max.poll.records and the internal buffer, heartbeats and liveness, and auto vs manual offset commit with every ack-mode.

How this chapter is organised

We walk the same consumer read flow from Kafka Architecture and Consumer Setup Part 1. At every step there is a doubt, and each doubt is answered with the configuration that controls that behaviour.

Roadmap: the consumer read flowarchitecture diagram

The step numbers in the headings below match the boxes in this diagram (Steps 1 → 11).

1Step 1: Consumer Starts and Wants to Join a Group

❓

Doubt: can a consumer join more than 1 group?
Answer: No — 1 consumer can join only 1 group. A consumer has exactly one group.id. To read the same data for two groups, run two consumers (for example two @KafkaListeners with different groupIds).

2Step 2: Find the __consumer_offsets Partition

The consumer works out which partition of the internal topic __consumer_offsets stores its group's data:

coordinator partitiontext
partition = hash(group.id) % N        // N = partitions of __consumer_offsets (50 by default)

The leader broker of that partition becomes the group's Group Coordinator (Step 4).

3Step 3: Consumer Requests Metadata

The consumer invokes one of the bootstrap servers (any broker), asks for metadata (which broker leads which partition) and caches it.

❓

Doubt: how frequently is this metadata refreshed?
Answer: multiple factors make the consumer start a metadata refresh — on a timer, or on demand.

Periodic refresh

Even when nothing goes wrong, the cache is refreshed after a maximum age:

# default 5 minutes
spring.kafka.consumer.properties.metadata.max.age.ms=300000

On-demand refresh

  • The consumer invoked a broker, but the broker returned NOT_LEADER_FOR_PARTITION (named NOT_LEADER_OR_FOLLOWER in newer Kafka versions) — leadership moved.
  • Information is missing from the cache (for example a new topic or partition).
  • etc.

4Step 4: Find the Group Coordinator and Send JoinGroupRequest

The request contains:

  • The consumer group it needs to join.
  • The topics it wants to subscribe to.
❓

Doubt 1: can 1 consumer request to join more than 1 topic?
Doubt 2: can multiple consumers in a group request to join different topics?
Doubt 3: can multiple consumers in a group request to join the same topic?

All three are covered in Consumer Setup Part 2.

5Step 5: Partition Assignment

Broker3 (Group Coordinator)text
Group: order-consumer-group
  Topic: order-events
    Consumer1 : handle Partition-0
    Consumer2 : handle Partition-1
    Consumer3 : handle Partition-2
❓

Doubt: how are partitions divided among the consumers in the group? That is decided by the partition assignment strategy. All the examples below use consumers C1, C2, C3 on topic order-events with partitions P0 – P5.

Range Assignor

  • Lays out the partitions in numeric order.
  • Lays out the consumers in alphabetical order.
  • Logic: partitions / consumers = 6 / 3 = 2 consecutive partitions each.
C1
P0P1
C2
P2P3
C3
P4P5

Round Robin Assignor

Just distributes the partitions 1 by 1 to all consumers.

C1
P0P3
C2
P1P4
C3
P2P5

Sticky Assignor

Starts with the same result as Round Robin (C1: P0, P3 · C2: P1, P4 · C3: P2, P5). Its main advantage comes during a rebalance — when a new consumer is added to the group or an existing consumer is removed.

What happens on a rebalance: say C3 crashed

Starting point: C1: P0, P3 · C2: P1, P4 · C3: P2, P5.

Range / Round Robin: full recalculation

  • Every consumer (C1, C2) drops the partitions it was allotted.
  • Every consumer stops reading.
  • The algorithm runs a full recalculation from the start for the remaining 2 consumers.
C1
P0P3P2P4
C2
P1P4P3P5

Problem: earlier C1 had P0 and P3; after rebalancing P3 is removed and P2 and P4 are added. So C1 has to do all the clean-up, like clearing its cache for P3, and maintain new offsets for P2 and P4 — even though only C3's partitions really needed a new owner.

Sticky: keep what you already have

  • It is smarter: during a rebalance it tries to achieve an even distribution (as much as possible).
  • It also tries to keep each consumer attached to the partitions it already had.
C1
P0P3P2
C2
P1P4P5
C3
P2P5
crashed

It picks only the partitions allotted to C3 and distributes them evenly to the available consumers. C1 and C2 still hold the partitions they had before.

✎

The round-robin result is shown on the left (C1: P0, P2, P4 · C2: P1, P3, P5). With the Range assignor the recalculation gives consecutive blocks instead (C1: P0, P1, P2 · C2: P3, P4, P5) — still a full reshuffle.

Cooperative Sticky Assignor

Range, Round Robin and Sticky are all eager rebalancers: when a rebalance happens, consumers stop reading from all their partitions until the new assignments are made (“stop the world”). With the cooperative protocol:

  1. The algorithm decides which old partitions each consumer will still hold.
  2. Consumers continue reading from those partitions. Only the partitions being removed from them, or newly added to them, are updated later.
Eager vs cooperative rebalance after C3 crashessequence diagram
sequenceDiagram participant GC as Group Coordinator participant C1 as C1 (P0, P3) participant C2 as C2 (P1, P4) Note over GC: C3 is gone, rebalance starts rect rgb(253, 236, 234) Note over GC,C2: Eager (Range / RoundRobin / Sticky) GC->>C1: rebalance GC->>C2: rebalance Note over C1,C2: revoke ALL partitions <br/> nobody reads GC-->>C1: new assignment GC-->>C2: new assignment Note over C1,C2: resume reading end rect rgb(232, 247, 245) Note over GC,C2: Cooperative Sticky GC->>C1: rebalance (keep P0, P3) GC->>C2: rebalance (keep P1, P4) Note over C1,C2: keep reading owned partitions GC-->>C1: add P2 GC-->>C2: add P5 end

In the eager case there is a window where no partition is being read. In the cooperative case C1 and C2 never stop reading P0, P3, P1 and P4; only the orphaned partitions P2 and P5 are handed over, possibly in a follow-up round.

Choosing the strategy

# or
spring.kafka.consumer.properties.partition.assignment.strategy=org.apache.kafka.clients.consumer.StickyAssignor
# or

ℹ

The notes label Range as the default. In Kafka 3.x/4.x clients the default value of partition.assignment.strategy is the list [RangeAssignor, CooperativeStickyAssignor]: Range is used, and the cooperative assignor is listed so a group can later be upgraded to it with rolling restarts.

6Steps 6 & 7: Fetch the Committed Offset

The consumer is assigned P0 of topic order-events. It asks the Group Coordinator how far P0 has been read, and the coordinator looks it up in the __consumer_offsets topic.

❓

Doubt: what if there is no offset info present (a brand-new group, or the saved offset was deleted)?

Where does the consumer start reading?flowchart
flowchart TD A["Consumer receives partition assignment · (order-events, P0)"] --> B["Consumer asks Group Coordinator for offset details · coordinator reads __consumer_offsets"] B --> Q{"Offset exists?"} Q -- "YES" --> Y["Fetch the saved offset and return it"] Q -- "NO" --> R["Look at spring.kafka.consumer.auto-offset-reset"] R -- "latest (default)" --> L["Read only new records produced after the partition assignment"] R -- "none" --> N["Throw an exception"] R -- "earliest" --> E["Start from the earliest available offset (after clean-up)"] classDef step fill:#eef4ff,stroke:#2563eb,color:#1e3a8a,stroke-width:1.5px classDef ok fill:#e8f7f5,stroke:#0f9d8f,color:#0b4f48,stroke-width:1.5px classDef bad fill:#fdecea,stroke:#dc2626,color:#7f1d1d,stroke-width:1.5px class A,B,Q,R step class Y,L,E ok class N bad

Explanation

  • latest (default) — skips everything already in the partition; only records produced after the assignment are read.
  • none — throws an exception, so you decide in code what to do.
  • earliest — starts from the oldest offset still available. Older data may already be gone because of retention clean-up.

This setting is used only when there is no committed offset. Once the group has committed, it always resumes from the committed offset.

application.propertiesproperties
# latest (default) | earliest | none
spring.kafka.consumer.auto-offset-reset=latest

7Steps 8 & 9: Fetch Records from the Leader

The consumer checks the metadata and invokes the leader broker of topic order-events, Partition-0, to fetch from the offset found in the previous step.

If there is no event, how long does the consumer wait?

  • A Kafka consumer is single threaded; it processes the records one by one.
  • poll(timeout) takes a timeout: the consumer waits at most this long for the brokers to respond. Otherwise it proceeds with whatever it received, or an empty list.
application.propertiesproperties
# 5 seconds
spring.kafka.listener.poll-timeout=5000
poll loop (conceptual)java
while (true) {
    ConsumerRecords records = consumer.poll(timeout);
    for (ConsumerRecord record : records) {
        // business logic
    }
}

In one poll(), how much data is sent?

A consumer can ask a broker for multiple partitions and topics in 1 single request. But how much data will the broker send for 1 FetchRequest?

application.properties — fetch limits (defaults)properties
# Max data the Broker returns PER partition (1MB)
spring.kafka.consumer.properties.max.partition.fetch.bytes=1048576

# Maximum data (total) the Broker can return in one request (52MB)
spring.kafka.consumer.properties.fetch.max.bytes=52428800

# Minimum data (in bytes) the Broker must have before responding
spring.kafka.consumer.properties.fetch.min.bytes=1

# How long the Broker can hold the request to meet fetch.min.bytes (0.5sec)
spring.kafka.consumer.properties.fetch.max.wait.ms=500

# Max number of records returned in a single poll() call
spring.kafka.consumer.properties.max.poll.records=500
Byte limits of one FetchRequestarchitecture diagram
  • max.partition.fetch.bytes — the max number of bytes fetched from each partition.
  • fetch.max.bytes — the combined total fetched from all partitions; the per-partition amounts together must stay ≤ 52 MB.

52428800 bytes is exactly 50 × 1024 × 1024 (50 MiB), which is about 52 MB in decimal units. Also, if the first record batch of a partition is bigger than these limits it is still returned, so the consumer can always make progress.

With the default fetch.min.bytes=1 the broker answers as soon as any data exists. Raising it trades latency for fewer, larger responses; fetch.max.wait.ms caps how long the broker may hold the request.

max.poll.records and the internal buffer

The response from the broker is limited by bytes, not by the number of records. So the broker may send up to 52 MB that contains, say, 2000 records. Then what does max.poll.records=500 do?

Records beyond max.poll.records stay in the bufferflowchart
flowchart TD A["Consumer receives data · internal buffer contains more than 500 records"] --> B["Consumer applies max.poll.records=500"] B --> C["poll() returns at most 500 records"] B --> D["Remaining records stay in the buffer"] E["Next poll()"] --> Q{"Records in buffer?"} Q -- "Yes" --> F["Return them · no network call to the broker"] Q -- "No" --> G["Send a new FetchRequest"] D -.-> Q classDef step fill:#eef4ff,stroke:#2563eb,color:#1e3a8a,stroke-width:1.5px classDef ok fill:#e8f7f5,stroke:#0f9d8f,color:#0b4f48,stroke-width:1.5px class A,B,E,Q step class C,D,F,G ok

max.poll.records is applied on the consumer side. It does not change what the broker sends; it only limits how many records one poll() hands to your code. The rest are served from memory on the next poll.

Can there be a gap between polls?

application.propertiesproperties
# Sleep time between two poll() calls (0ms is default, means as soon as possible)
spring.kafka.listener.idle-between-polls=0

How do we know if a consumer is stuck or dead?

application.properties — liveness (defaults)properties
# with this consumer sends Heartbeat Pulse to Group coordinator every 3 Seconds
spring.kafka.consumer.properties.heartbeat.interval.ms=3000
# Max time Group coordinator will wait for the heartbeat (generally its higher than heartbeat.interval.ms)
# after this say 45s it will consider Consumer as dead and initiate rebalance
spring.kafka.consumer.properties.session.timeout.ms=45000

# Group Coordinator expects 1 poll() call every 5 mins,
# if say consumer took 6 minutes to process records
# group coordinator will think that Consumer got stuck
# initiates rebalance
spring.kafka.consumer.properties.max.poll.interval.ms=300000
SettingDetectsWhat happens
heartbeat.interval.ms = 3 s—A background thread sends a heartbeat to the Group Coordinator every 3 s.
session.timeout.ms = 45 sDead consumer (crash, network loss)No heartbeat for 45 s → consumer considered dead → rebalance.
max.poll.interval.ms = 5 minStuck consumer (alive, but processing too long)No poll() for 5 min → consumer considered stuck → it leaves the group → rebalance.
💡

Heartbeats come from a separate thread, so a consumer busy processing a huge batch keeps heartbeating — that is why max.poll.interval.ms exists as a second check. If processing is slow, lower max.poll.records or raise max.poll.interval.ms. Keep heartbeat.interval.ms at about one third of session.timeout.ms or less.

9Step 11: Offset Commit

❓

Doubt: how do we manage commits — automatic or manual?

Auto-commit

# Kafka commits offsets every 5 seconds (background thread)
spring.kafka.consumer.enable-auto-commit=true
spring.kafka.consumer.properties.auto.commit.interval.ms=5000

The Kafka client itself commits the latest polled offsets on a timer. Simple, but a crash between commits can cause re-reads, and a commit can happen before processing finishes.

Manual commit (Spring listener container)

spring.kafka.consumer.enable-auto-commit=false
spring.kafka.listener.ack-mode=   # see the modes below

Spring's listener container commits for you, according to the ack-mode.

ℹ

If enable-auto-commit is not set at all, Spring Kafka sets enable.auto.commit=false on the consumer and uses the container ack-mode (BATCH) — the opposite of the plain Kafka client default (true).

ack-mode options

ack-modeHow it commitsTrade-off
batch (default)poll() gets 500 records → process all 500 → commit once.If, say, the last record of the batch fails, the entire batch is retried.
recordProcess record1 → commit; process record2 → commit …More commit overhead.
timeCommit every 5 s: ack-mode=time, ack-time=5000Records processed since the last commit may be re-read after a crash.
countCommit after every 10 records: ack-mode=count, ack-count=10Up to 10 records may be re-read after a crash.
manualYour code calls ack.acknowledge().Even if you acknowledge after each record, the commits are queued and sent as one commit request when the records of the poll are finished.
manual_immediateYour code calls ack.acknowledge().Each call sends a commit request immediately.
time / countproperties
spring.kafka.listener.ack-mode=time
spring.kafka.listener.ack-time=5000

spring.kafka.listener.ack-mode=count
spring.kafka.listener.ack-count=10
manual / manual_immediate listenerjava
@KafkaListener(topics = "order-events")
public void process(ConsumerRecord<String, Order> rec,
                    Acknowledgment ack) {
    process(rec);       // business logic
    ack.acknowledge();  // commit
}
manual vs manual_immediatesequence diagram
sequenceDiagram participant L as Listener participant K as Container participant GC as Group Coordinator Note over L,GC: ack-mode = manual L->>K: ack.acknowledge() (record 1) L->>K: ack.acknowledge() (record 2) L->>K: ack.acknowledge() (record 3) K->>GC: one commit after the poll's records are processed Note over L,GC: ack-mode = manual_immediate L->>K: ack.acknowledge() (record 1) K->>GC: commit L->>K: ack.acknowledge() (record 2) K->>GC: commit

Both modes let your code decide when a record counts as done. manual batches the commits for less overhead; manual_immediate commits right away for the smallest re-read window. (The notes spell it “manual_immdediate”; the correct value is manual_immediate.)

Test Yourself

5 quick interview-style questions on this chapter. Try to answer before revealing.

1
How do session.timeout.ms and max.poll.interval.ms differ? SDE2

The session timeout detects a dead consumer (no heartbeats from the background thread). The max poll interval detects a stuck one (alive, but not calling poll() in time). Both trigger a rebalance.

2
What is the advantage of the CooperativeSticky assignor? SDE3

Rebalances are incremental: consumers keep reading the partitions they retain and only the moved partitions pause, instead of every consumer stopping (“stop the world”).

3
The broker returns 2000 records but max.poll.records=500. What happens? SDE2

poll() returns 500 records; the rest stay in the consumer’s internal buffer and are returned by the next polls without a new fetch.

4
What is the difference between ack-mode manual and manual_immediate? SDE2

Both commit when you call ack.acknowledge(). manual queues the commits and sends them after the poll’s records are processed; manual_immediate commits right away.

5
What does fetch.min.bytes together with fetch.max.wait.ms control? SDE2

The broker replies once at least fetch.min.bytes are available or fetch.max.wait.ms has passed, trading latency for fewer, larger responses.
