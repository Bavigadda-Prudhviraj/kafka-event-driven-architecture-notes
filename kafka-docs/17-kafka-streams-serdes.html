Kafka Streams: SerDes (Serializer / Deserializer)

SerDes — a serializer and a deserializer in one object — and the five places in a topology where Kafka Streams needs them. Built-in SerDes, default versus explicit SerDes and their priority, how to build a JsonSerde for your own classes, and what happens when serialization or deserialization fails: the default handlers, LogAndContinue, and writing custom deserialization and production exception handlers.

✎ Author: Bavigadda Prudhviraj 📅 Source notes: Monday, 29 June 2026 ⏱ ~8 min read 📄 Source: 17.Kafka Stream_SerDes (Serializer Deserializer).pdf

1Recap: Source Syntax

the three source types (Chapter 16)java

        Consumed.with(Serdes.String(), Serdes.String()));

// KTable
KTable<String, String> orders = builder.table("source-topic-name",

                .withValueSerde(Serdes.String()));

// GlobalKTable

        Consumed.with(Serdes.String(), Serdes.String()),

                .withKeySerde(Serdes.String())
                .withValueSerde(Serdes.String()));

Every Serdes.String() in there is a SerDe. Let's see what that is.

2What Is a SerDe?

SerDe = Serializer + Deserializer, combined into 1 object:

  • Serializer: Java object → bytes
  • Deserializer: bytes → Java object
  • SerDe: both in one package
flowchart LR O["Java object"] -- "Serializer" --> B["bytes"] B -- "Deserializer" --> O classDef o fill:#eef4ff,stroke:#2563eb,color:#1e3a8a,stroke-width:1.5px classDef b fill:#fff4ec,stroke:#ea580c,color:#7c2d12,stroke-width:1.5px class O o class B b

Why we need it: Kafka stores data as bytes, and so does RocksDB. Whenever we read from a Kafka topic or RocksDB we need deserialization (bytes → Java object); whenever we write to a Kafka topic or RocksDB we need serialization (Java object → bytes). Kafka Streams both reads and writes, so a plain consumer's deserializer or a producer's serializer is not enough: it needs both directions, often for the same type.

3Built-in SerDes

Kafka Streams provides these out of the box:

This is why the changelog value in Chapter 15 was 8 unreadable bytes: count() stores its result with Serdes.Long().

4SerDes Priority: Default vs Explicit

Lowest priority — default SerDes

Set once in application.properties; applied everywhere no SerDe is given.

spring.kafka.streams.properties.default.key.serde=org.apache.kafka.common.serialization.Serdes$StringSerde
spring.kafka.streams.properties.default.value.serde=org.apache.kafka.common.serialization.Serdes$StringSerde

Highest priority — explicit SerDes

Passed in the code: Consumed.with, Produced.with, Grouped.with, Materialized.withKeySerde/withValueSerde. These always override the default for that one step.

Without default SerDes, we must specify the key and value SerDes everywhere (as in the recap). With them, the same source types become:

relying on the default SerDesjava
// KStream
KStream<String, String> orders = builder.stream("source-topic-name");

// KTable
KTable<String, String> orders = builder.table("source-topic-name",
        Materialized.<String, String, KeyValueStore<Bytes, byte[]>>as("RocksDB-store-name"));

// GlobalKTable
GlobalKTable<String, String> countries = builder.globalTable("source-topic-name",
        Materialized.<String, String, KeyValueStore<Bytes, byte[]>>as("RocksDB-store-name"));

Explicit SerDes at each of the places:

💡

Setting a default is convenient when most of the topology uses one type. But operators that change the type (e.g. count() turns values into Long, mapValues into anything) still need an explicit SerDe downstream, or the default String SerDe will fail at runtime with a ClassCastException. Using @Bean + void as in the notes is not allowed by Spring; @Autowired is used here as in Chapter 16.

5Custom Java Objects: JsonSerde

How do we handle our own classes like Order or Payment? Use a JsonSerde. Spring Kafka already ships one (org.springframework.kafka.support.serializer.JsonSerde), but here is how we would write it ourselves.

1 · JsonSerializer.javajava
import com.fasterxml.jackson.databind.ObjectMapper;
import org.apache.kafka.common.serialization.Serializer;

public class JsonSerializer<T> implements Serializer<T> {

    private final ObjectMapper objectMapper = new ObjectMapper();

    @Override
    public byte[] serialize(String topic, T data) {
        if (data == null) {
            return null;
        }
        try {
            return objectMapper.writeValueAsBytes(data);
        }
        catch (Exception e) {
            throw new RuntimeException("Error serializing", e);
        }
    }
}
2 · JsonDeserializer.javajava
import com.fasterxml.jackson.databind.ObjectMapper;
import org.apache.kafka.common.serialization.Deserializer;

public class JsonDeserializer<T> implements Deserializer<T> {

    private final ObjectMapper objectMapper = new ObjectMapper();
    private final Class<T> targetType;

    public JsonDeserializer(Class<T> targetType) {
        this.targetType = targetType;
    }

    @Override
    public T deserialize(String topic, byte[] data) {
        if (data == null) {
            return null;
        }
        try {
            return objectMapper.readValue(data, targetType);
        } catch (Exception e) {
            throw new RuntimeException("Error deserializing", e);
        }
    }
}
  • The serializer is generic (<T>), so it can handle any object: Order, Payment, etc.
  • Because of that, the deserializer must be told the target type to convert into — hence Class<T> targetType.
3 · JsonSerde.java — both in one objectjava
import org.apache.kafka.common.serialization.Serde;

public class JsonSerde<T> implements Serde<T> {

    private final JsonSerializer<T> serializer;
    private final JsonDeserializer<T> deserializer;

    public JsonSerde(Class<T> targetType) {
        this.serializer = new JsonSerializer<>();
        this.deserializer = new JsonDeserializer<>(targetType);
    }

    @Override
    public JsonSerializer<T> serializer() {
        return serializer;
    }

    @Override
    public JsonDeserializer<T> deserializer() {
        return deserializer;
    }
}

Like this, we can create any custom SerDe. Kafka also has a shortcut, Serdes.serdeFrom(serializer, deserializer), which wraps an existing pair. Now let's use it:

SourceTypesTopology.java — typed Order streamjava
@Configuration
public class SourceTypesTopology {

    @Autowired
    public void kstreamDemo(StreamsBuilder builder) {

        Serde<Order> orderSerde = new JsonSerde<>(Order.class);

        KStream<String, Order> orders = builder.stream("order-events",
                Consumed.with(Serdes.String(), orderSerde));

        orders.filter((key, order) -> order.getTotalAmount() > 100)
              .to("order-events-output",
                      Produced.with(Serdes.String(), orderSerde));
    }
}

Compare this with Chapter 15, where each processor parsed a JSON String with objectMapper.readValue again and again. With a JsonSerde the stream is typed as KStream<String, Order>, so order.getTotalAmount() is used directly.

✎

The notes import Serdes in JsonSerde without using it; that import is dropped. In the filter, order.getTotalAmount() > 100 throws a NullPointerException if the amount is null (the field is a Double), so production code should check for null as in Chapter 15.

6What If Serialization or Deserialization Fails?

Deserialization fails (reading)

Use case 1: wrong SerDe type

Topic has {"orderId": "001", "amount": 150} (a JSON string). We read with Consumed.with(Serdes.String(), Serdes.Long()). Result: it tries to read JSON bytes as an 8-byte Long → exception.

Use case 2: corrupted data

Topic has garbage bytes that aren't valid JSON. We read with new JsonSerde<>(Order.class). Result: Jackson can't parse → JsonParseException → exception.

Serialization fails (writing)

Use case 1: wrong output SerDe

We have a Long value but write with Produced.with(Serdes.String(), Serdes.String()). Result: serializing a Long as a String → ClassCastException.

Use case 2: object can't be serialized

An Order with a circular reference, written with JsonSerde<>(Order.class). Result: Jackson can't serialize → JsonMappingException.

Deserialization: 3 ways to handle it

HandlerBehaviour
LogAndFailExceptionHandler (default)Logs the error, throws the exception, the stream thread dies. If all threads die, the application dies.
LogAndContinueExceptionHandlerLogs the error, skips the bad record, continues with the next one. The bad record is lost forever.
Custom handlerOur own business logic: continue, fail fast, or insert into a dead-letter topic.
application.properties — pick oneproperties

CustomDeserializationHandler.java — skip up to N bad recordsjava
package com.eda.streams.errorhandling;

import org.apache.kafka.clients.consumer.ConsumerRecord;
import org.apache.kafka.streams.errors.DeserializationExceptionHandler;
import org.apache.kafka.streams.processor.ProcessorContext;
import java.util.Map;
import java.util.concurrent.atomic.AtomicLong;

public class CustomDeserializationHandler implements DeserializationExceptionHandler {

    private long maxErrors;
    private static final AtomicLong errorCount = new AtomicLong(0);

    @Override
    public DeserializationHandlerResponse handle(ProcessorContext context,
                                                 ConsumerRecord<byte[], byte[]> record,
                                                 Exception exception) {
        long errors = errorCount.incrementAndGet();
        // STRATEGY: skip bad records, if limit not crossed
        if (errors > maxErrors) {
            return DeserializationHandlerResponse.FAIL;
        }
        return DeserializationHandlerResponse.CONTINUE;
    }

    @Override
    public void configure(Map<String, ?> configs) {
        // we can read stream config properties here if needed
        Object value = configs.get("stream.max.deserialization.errors");
        if (value != null) {
            maxErrors = Long.parseLong(value.toString());
        } else {
            maxErrors = 100;
        }
    }
}
✎
  • The notes call Long.parseLong(value.toString()) before the null check, which throws a NullPointerException when the property is missing; that line is removed, and If is fixed to if.
  • stream.max.deserialization.errors is our own property; pass it as spring.kafka.streams.properties[stream.max.deserialization.errors]=100 and it reaches configure().
  • The errorCount is static, so it is shared by all stream threads and never resets; a real handler might count per time window instead.
  • In Kafka 3.9+ this handle(ProcessorContext, …) signature is deprecated in favour of handle(ErrorHandlerContext, …); it still works.

Serialization / production: 2 ways to handle it

HandlerBehaviour
DefaultProductionExceptionHandler (default)Always fails: the stream thread dies; if all threads die, the application dies.

what the default does (conceptual)java
public class DefaultProductionExceptionHandler
        implements ProductionExceptionHandler {

    @Override
    public ProductionExceptionHandlerResponse handle(
            ProducerRecord<byte[], byte[]> record,
            Exception exception) {
        return ProductionExceptionHandlerResponse.FAIL;
    }

We don't need to write this; it shows what the built-in handler does.

CustomProductionHandler.javajava
package com.eda.streams.errorhandling;

import org.apache.kafka.clients.producer.ProducerRecord;
import org.apache.kafka.streams.errors.ProductionExceptionHandler;
import java.util.Map;

public class CustomProductionHandler implements ProductionExceptionHandler {

    @Override
    public ProductionExceptionHandlerResponse handle(
            ProducerRecord<byte[], byte[]> record,
            Exception exception) {

        if (exception.getClass().getSimpleName().contains("RecordTooLarge")) {
            return ProductionExceptionHandlerResponse.CONTINUE;
        }
        return ProductionExceptionHandlerResponse.FAIL;
    }

    @Override
    public void configure(Map<String, ?> configs) {
    }
}

# or custom

⚠

Which failures reach which handler? The handle(ProducerRecord<byte[], byte[]> …) method shown above receives records that were already serialized and then failed to be sent, e.g. RecordTooLargeException from the broker. A ClassCastException or JsonMappingException during serialization happens before that. Kafka 3.5+ routes those through a separate method, handleSerializationException(...), which also defaults to FAIL — override it too if you want to skip unserializable records.

Exceptions thrown inside your own processor code (e.g. a NullPointerException in a filter) are handled by neither of these; since Kafka 3.9 there is a third hook, processing.exception.handler, for that.

✅
Summary
  • A SerDe converts both ways; Kafka Streams needs one at source, sink, repartition, RocksDB write and RocksDB read.
  • Built-in SerDes cover primitives and Strings; a JsonSerde (built in, or your own) handles custom classes.
  • Explicit SerDes in code override the default.key.serde / default.value.serde properties.
  • Bad input: LogAndFail (default), LogAndContinue, or a custom handler. Failed output: DefaultProductionExceptionHandler (fail) or a custom one.

Test Yourself

5 quick interview-style questions on this chapter. Try to answer before revealing.

1
What is a SerDe, and why does Kafka Streams need one? SDE1

A serializer + deserializer in one object. Streams both reads and writes bytes (topics and RocksDB), often for the same type.

2
Name the five places in a topology that need SerDes. SDE1

Source, sink, repartition topics, RocksDB writes, and RocksDB reads (e.g. in joins).

3
Which wins: default.value.serde or Consumed.with(...)? SDE1

The explicit SerDe passed in code always overrides the default from properties for that step.

4
What does LogAndContinueExceptionHandler do, and what is the risk? SDE2

It logs and skips records that cannot be deserialized, keeping the app running — but those records are lost unless you also send them to a dead-letter topic.

5
Why does count() often fail with a String default value SerDe? SDE2

Its output values are Long; writing them with a String SerDe causes a ClassCastException, so pass Serdes.Long() explicitly.
