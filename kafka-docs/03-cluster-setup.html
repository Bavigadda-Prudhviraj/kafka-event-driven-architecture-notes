Cluster Setup

Hands-on: build a real KRaft-based Kafka cluster on one machine — two controllers and two brokers — from the Kafka 4.2.0 binary. Every configuration property is explained, then we format the storage, start the nodes, verify the quorum and finally produce and consume messages from the CLI.

✎ Author: Bavigadda Prudhviraj 📅 Source notes: Thursday, 26 February 2026 ⏱ ~20 min read 📄 Source: 3.Cluster Setup.pdf
💡
What we will build

In Kafka Architecture we learned what brokers, controllers and KRaft do. Today we set up that cluster for real: 2 KRaft controllers (node ids 1 and 2) and 2 brokers (node ids 3 and 4), all running locally, and then test it with the console producer and consumer.

1The Cluster We Will Set Up

Target Kafka clusterarchitecture diagram

Components

  • Kafka Broker-1 and Kafka Broker-2 store the partitions of topic order-events. Each partition has a leader on one broker and a follower on the other (P0 leader on Broker-1, P1 leader on Broker-2, and so on).
  • Controller1 (Active) and Controller2 (Stand-by) form the KRaft quorum and manage the cluster metadata. They exchange heartbeats with each other.
  • The brokers exchange heartbeats with the controllers and receive metadata updates from them.
  • Producer1 writes into the cluster and a Consumer Group reads from it.

2Step 1: Download the Latest Kafka Binary

🐳
Note: Binary vs Docker

Instead of downloading the binary, we can also use the Kafka Docker image. Since Docker hasn't been covered yet, this setup uses the binary download. It is also a good way to understand things — once understood properly, running via a Docker image is no different and would be very easy.

  1. Download the latest Kafka binary from https://kafka.apache.org/community/downloads/.
  2. Version used here: 4.2.0 — the latest, released on 17th Feb 2026.
  3. Binary download: kafka_2.13-4.2.0.tgz (the page also offers its asc and sha512 files to verify the download). 2.13 is the Scala version the binary is built with, 4.2.0 is the Kafka version.

Extract the archive and move into the Kafka folder — all later commands are run from here:

extract — macOS / Linuxbash
$ tar -xzf kafka_2.13-4.2.0.tgz
$ cd kafka_2.13-4.2.0
extract — Windows (Command Prompt)cmd
REM tar is built into Windows 10 and later. Extract to a SHORT path such as C:\kafka

> ren kafka_2.13-4.2.0 kafka
> cd C:\kafka
🪟
Windows tips

Keep Kafka in a short folder path without spaces (for example C:\kafka). The .bat scripts build a long classpath, and a deep path can fail with “The input line is too long”. Run every command from a Command Prompt opened in that folder. Kafka on Windows is fine for learning and local development; production clusters normally run on Linux.

These configuration files need to be put in the /config folder.

config/controller2.propertiesproperties
process.roles=controller
node.id=2
listeners=CONTROLLER://:9193
controller.listener.names=CONTROLLER
controller.quorum.voters=1@localhost:9093,2@localhost:9193

The two files differ only in node.id (1 vs 2), the listener port (9093 vs 9193) and log.dirs. Everything that describes the cluster — the voter list, listener name and security map — is identical.

/tmp/... is a macOS/Linux path. On Windows point every node to its own folder and use forward slashes (a single backslash is an escape character inside .properties files):

What each property means

process.roles

Tells Kafka what role this node should perform:

ValueMeaning
controllerOnly performs controller tasks
brokerOnly performs broker tasks
controller,brokerPerforms the tasks of both controller and broker

node.id

A unique id for the node within a cluster.

listeners

The list of ports which are running on this node; for each port we can give a logical name. Internally it does something like new ServerSocket(9093) — a TCP socket waiting for connections.

anatomy of a listenertext
listeners=CONTROLLER://:9093
          ^^^^^^^^^^   ^^^^
          |            port; IP omitted -> Kafka listens on every IP address on the machine
          logical name (label) for this socket

Specific IP address:  CONTROLLER://192.168.1.10:9093

Multiple listeners open multiple sockets. For example:

two listenersproperties
listeners=CONTROLLER://:9093,BROKER://:9092

This tells Kafka to open 2 sockets: one named CONTROLLER and one named BROKER.

controller.listener.names

choosing the controller listenerproperties
listeners=CONTROLLER://:9093, INTERNAL://:9092, EXTERNAL://:9094
controller.listener.names=CONTROLLER

This tells Kafka: among all the listeners defined, use the one named “CONTROLLER” for controller-to-controller communication.

controller.quorum.voters

Each controller maintains a static list of the nodes which act as controllers, in the format nodeId@host:port:

votersproperties
controller.quorum.voters=1@localhost:9093,2@localhost:9193
⚠

Quorum with 2 controllers: using the formula from the architecture chapter, quorum = (2 / 2) + 1 = 2. So with two voters, both controllers must be up to elect a leader or commit metadata — if one stops, there is no majority. Two controllers are fine for learning on a laptop; production clusters normally use an odd number (3 or 5) so that one (or two) controllers can fail.

listener.security.protocol.map

For which listener, which security protocol needs to be used:

  • PLAINTEXT — no encryption, no authentication; used for local.
  • SSL — TLS encryption; used in production.
security mapproperties
# For the CONTROLLER listener, use the PLAINTEXT security protocol.
listener.security.protocol.map=CONTROLLER:PLAINTEXT

Remaining properties

PropertyMeaning
log.dirsDirectory where the node stores its data.
num.partitionsDuring topic creation, if the producer or CLI does not say how many partitions, the controller uses this default value.
default.replication.factorDefault value for RF — how many replicas for each partition.
offsets.topic.replication.factorDefault replication factor for the __consumer_offsets topic (set in the broker files below).

5Step 4: Write the Configuration for the Brokers

These configuration files also need to be put in the /config folder.

config/broker1.propertiesproperties
process.roles=broker
node.id=3

# WHERE to fetch metadata from (which controllers to connect to)
controller.quorum.voters=1@localhost:9093,2@localhost:9193

# This is where our Spring Boot apps (producer/consumer) will connect
listeners=BROKER://:9092

# passed this address to controller to store in their cluster metadata
advertised.listeners=BROKER://localhost:9092

# internally when follower broker try to fetch from leader, what listener they need to use.
inter.broker.listener.name=BROKER

# when broker try to communicate with controller what listener they need to use.
controller.listener.names=CONTROLLER

listener.security.protocol.map=CONTROLLER:PLAINTEXT,BROKER:PLAINTEXT

log.dirs=/tmp/broker1-logs

# Keep messages for 7 days (168 hours)
log.retention.hours=168

# Max size of a single log segment file (1GB)
log.segment.bytes=1073741824

# __consumer_offsets topic RF
offsets.topic.replication.factor=2

What each broker property means

  1. controller.quorum.votersEach broker also maintains the static list of controller nodes — this is where it fetches cluster metadata from.
  2. listeners=BROKER://:9092Opens up port 9092 and names it BROKER. This is where our Spring Boot producer/consumer apps will connect.
  3. advertised.listeners=BROKER://localhost:9092

    This address is passed to the controller, and the controller stores it in its metadata.

    When a producer wants to push to Topic-A, Partition0, it asks any broker → the broker goes to the controller → the controller returns the metadata, which has all the details like which broker is the leader of which topic partition, and this address — so that the producer can directly call that specific broker.

  4. inter.broker.listener.name=BROKERAmong all the listeners defined, use the one named “BROKER” for broker-to-broker communication. As we know, a follower broker talks to the leader broker to fetch the data.
  5. controller.listener.names=CONTROLLER

    This has 2 uses:

    • The broker uses this controller listener name to map the security protocol (via listener.security.protocol.map).
    • It is used to pick the controller's listener from the metadata.
  6. log.dirs=/tmp/broker1-logsDirectory in which this node's data will persist.
  7. log.retention.hours=168Keep messages for 7 days. Kafka deletes whole segments once they are older than 168 hours (7 days).
  8. log.segment.bytes=1073741824Each segment size is fixed at 1 GB. After that, a new segment is created for the partition.
  9. offsets.topic.replication.factor=2Replication factor of the internal __consumer_offsets topic.

How controller.listener.names picks the controller endpoint

Let's say this information is present in the cluster metadata:

controller registration (cluster metadata)json
{
  "controllerId": 1,
  "endPoints": [
    {
      "name": "CONTROLLER",
      "host": "localhost",
      "port": 9093,
      "securityProtocol": 0
    },
    {
      "name": "INTERNAL",
      "host": "localhost",
      "port": 9097,
      "securityProtocol": 1
    }
  ]
}

Say the broker has decided it needs to communicate with the controller with ID 1 (as it is ACTIVE). It will pick the endpoint whose name matches controller.listener.names, i.e. the listener named “CONTROLLER” (port 9093). And that's one reason why all the different controllers have the same listener name.

ℹ

Precise retention rule: time-based retention looks at the newest record in a closed segment — a segment is deleted once even its latest record is older than 168 hours. Since retention works per segment (see Retention is applied per segment), the bigger log.segment.bytes is, the longer some records can live beyond 7 days.

Explanation

  • Clients → brokers use the BROKER listener, reached through the address in advertised.listeners.
  • Broker → broker (a follower fetching from the leader) uses the listener named by inter.broker.listener.name — also BROKER.
  • Broker → controller and controller ↔ controller use the listener named by controller.listener.names — CONTROLLER.

6Step 5: Map All Node IDs (2 Brokers + 2 Controllers) to One Kafka Cluster

Generate a cluster ID using the script present in the bin/ folder:

terminal — macOS / Linuxbash
$ bin/kafka-storage.sh random-uuid
zJVVVZAkS9aIBfjY0BlYJA
terminal — Windows (Command Prompt, from the Kafka folder)cmd
> bin\windows\kafka-storage.bat random-uuid
zJVVVZAkS9aIBfjY0BlYJA

Sample output: zJVVVZAkS9aIBfjY0BlYJA. Now map each node to this cluster id:

terminal — macOS / Linuxbash
# 1. Controller1
$ bin/kafka-storage.sh format -t zJVVVZAkS9aIBfjY0BlYJA -c config/controller1.properties
# 2. Controller2
$ bin/kafka-storage.sh format -t zJVVVZAkS9aIBfjY0BlYJA -c config/controller2.properties
# 3. Broker1
$ bin/kafka-storage.sh format -t zJVVVZAkS9aIBfjY0BlYJA -c config/broker1.properties
# 4. Broker2
$ bin/kafka-storage.sh format -t zJVVVZAkS9aIBfjY0BlYJA -c config/broker2.properties
terminal — Windows (Command Prompt, from the Kafka folder)cmd
REM 1. Controller1
> bin\windows\kafka-storage.bat format -t zJVVVZAkS9aIBfjY0BlYJA -c config\controller1.properties
REM 2. Controller2
> bin\windows\kafka-storage.bat format -t zJVVVZAkS9aIBfjY0BlYJA -c config\controller2.properties
REM 3. Broker1
> bin\windows\kafka-storage.bat format -t zJVVVZAkS9aIBfjY0BlYJA -c config\broker1.properties
REM 4. Broker2
> bin\windows\kafka-storage.bat format -t zJVVVZAkS9aIBfjY0BlYJA -c config\broker2.properties
  • -t — the cluster id (the same for every node, so they all belong to one cluster).
  • -c — the node's configuration file; the script reads its log.dirs and node.id.

This creates a meta.properties file within each log.dirs path (e.g. /tmp/controller1-logs/meta.properties, next to bootstrap.checkpoint):

/tmp/controller1-logs/meta.propertiesproperties
#
#Thu Feb 26 22:04:56 IST 2026
cluster.id=zJVVVZAkS9aIBfjY0BlYJA
directory.id=LYSuEbfGps8gnV7YsC9JHA
node.id=1
version=1

The node will refuse to join a cluster whose id does not match this file — that is how the four independent processes know they belong together.

⚠

Formatting is a one-time step per data directory. Since the data directories here are under /tmp, they may be cleared when the machine restarts — in that case, format again before starting the nodes.

↓

Order matters: start the controllers first and then the brokers, because a broker calls the controller to load the cluster metadata information.

__cluster_metadata-0/quorum-statejson
{"clusterId":"","leaderId":1,"leaderEpoch":1,"votedId":-1,"appliedOffset":0,"currentVoters":[{"voterId":1},{"voterId":2}],"data_version":0}
FieldValueMeaning
leaderId1Controller with ID 1 is the leader (active controller).
leaderEpoch1The election “term” — it increases every time a new leader is elected.
votedId-1This node has not cast a vote in the current epoch.
currentVoters1, 2The controllers taking part in the quorum — matches controller.quorum.voters.

sequenceDiagram participant B as Broker (node 3) participant C as Active Controller (node 1) Note over B: Waiting for the broker to be unfenced B->>C: register and heartbeat over the CONTROLLER listener C-->>B: broker unfenced Note over B: RECOVERY to RUNNING Note over B: Endpoint BROKER is READY, request processing enabled Note over B: Awaiting socket connections on 0.0.0.0:9092 Note over B: STARTING to STARTED - Kafka Server started (version 4.2.0)

What each log line tells us

  1. Waiting for the broker to be unfenced — a new broker starts fenced: it is registered but not yet allowed to lead partitions or serve clients until the controller accepts it.
  2. The broker has been unfenced. Transitioning from RECOVERY to RUNNING — the active controller accepted the broker; it is now a full member of the cluster. This only works because the controllers were started first.
  3. authorizerStart completed for endpoint BROKER. Endpoint is now READY and Enabling request processing — the BROKER listener from listeners=BROKER://:9092 is open.
  4. Awaiting socket connections on 0.0.0.0:9092 — because no IP was given in the listener, Kafka listens on every IP (0.0.0.0). Broker2 shows 0.0.0.0:9192.
  5. Transition from STARTING to STARTED, Kafka version: 4.2.0, Kafka Server started — the broker is up. [BrokerServer id=3] / id=4 confirm the node.id of each broker.

Reading the describe output

  • PartitionCount: 3, ReplicationFactor: 2 — the controller's defaults were applied, because the create command did not specify them.
  • Leader — the node.id of the broker leading that partition: node 3 (Broker1) leads P0 and P2; node 4 (Broker2) leads P1. Leadership is spread across both brokers.
  • Replicas — the brokers holding a copy, the preferred leader first (3,4 or 4,3).
  • Isr — the in-sync replicas: both copies of every partition are caught up with the leader.
  • Configs — segment.bytes=1073741824 comes from our log.segment.bytes; min.insync.replicas=1 is the default (we did not set it).
  • Elr / LastKnownElr — Eligible Leader Replicas fields shown by newer Kafka versions; empty here because nothing has failed.

--from-beginning makes the consumer start from the earliest offset, so it receives the three messages that were produced before it started — the streaming model's replay in action. The consumer keeps running and prints new messages as they arrive.

ℹ

Here the messages came back in the same order they were sent. Across multiple partitions Kafka only guarantees order within a partition (see Ordered), so with more traffic the console consumer may print messages from different partitions interleaved.

The topic is created through a broker, which forwards the request to the active controller; the controller applies the defaults and decides the leaders. The console producer then writes three messages and the console consumer, reading from the beginning, receives all of them — the cluster works end to end.

Test Yourself

4 quick interview-style questions on this chapter. Try to answer before revealing.

1
In the docs’ cluster, which nodes are controllers and which are brokers, and on which ports? SDE1

Controllers: node 1 (:9093) and node 2 (:9193). Brokers: node 3 (:9092) and node 4 (:9192).

2
Why must every node be formatted with the same cluster id? SDE2

kafka-storage format writes meta.properties with the cluster id into each log dir; nodes with different ids refuse to join the same cluster.

3
What is the difference between listeners and advertised.listeners? SDE2

listeners is where the node binds; advertised.listeners is the address it tells clients to use in metadata. If the advertised address is wrong, clients connect to the bootstrap server but then fail to reach the leaders.

4
Why set offsets.topic.replication.factor=2 in a two-broker cluster? SDE2

Its default is 3. With only two brokers the internal __consumer_offsets topic could not be created, so consumer groups would not work.
