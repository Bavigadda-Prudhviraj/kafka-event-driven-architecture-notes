1Foundations

1
What is an event in Event Driven Architecture? SDE1

A record of something that already happened (e.g. “OrderPlaced”), published so that any interested service can react. The producer does not know or wait for who consumes it.

Chapter: 01

2
Why do synchronous REST call chains become a problem as systems grow? SDE1

Every call blocks and couples the caller to the callee: latency adds up along the chain, one slow or failing service breaks the whole request, and adding a new consumer means changing the caller.

Chapter: 01

3
Push vs pull — which model does Kafka use, and why? SDE1

Pull. Consumers fetch at their own pace, so a slow consumer is never overwhelmed; the broker just stores data and serves fetch requests.

Chapter: 01

4
How does Kafka decide which partition a record goes to? SDE1

If the record has a key: hash(key) % partitions, so the same key always lands in the same partition (ordering per key). Without a key, the sticky partitioner fills one partition’s batch, then moves on.

Chapter: 02

5
What happens if a group has more consumers than the topic has partitions? SDE1

Each partition is read by only one consumer of the group, so the extra consumers sit idle (useful only as standbys).

Chapter: 02

6
What is the key difference between Pub/Sub messaging and event streaming? SDE2

In classic Pub/Sub a message is gone once delivered. In streaming (Kafka) events are kept in a durable log, so a new or late consumer can replay from any retained offset.

Chapter: 01

7
What is the ISR and how does it relate to acks=all and min.insync.replicas? SDE2

The In-Sync Replicas: the leader plus followers that are caught up. With acks=all the leader waits for every ISR member; if the ISR shrinks below min.insync.replicas, writes are rejected (NotEnoughReplicas) instead of risking data loss.

Chapter: 02

8
What is stored in __consumer_offsets, and how is a group’s coordinator found? SDE2

The committed offset per (group, topic, partition). It has 50 partitions; hash(group.id) % 50 picks the partition, and that partition’s leader broker is the group coordinator.

Chapter: 02

9
What role do KRaft controllers play? SDE2

They hold the cluster metadata (brokers, topics, partition leaders) in a Raft quorum, elect partition leaders and push metadata changes to brokers — replacing ZooKeeper.

Chapter: 02

10
Your topic must keep all events for one customer in order, but also scale to many consumers. How do you design the key and partition count? SDE2 Scenario

Key by customerId so each customer stays in one partition (ordering per key), and choose enough partitions for the target parallelism plus headroom — you can only have as many active consumers in a group as partitions. Avoid hot keys (one huge customer) or split them, and remember that adding partitions later changes hash(key) % n, breaking per-key ordering for existing keys.

Chapter: 02

11
An order service calls payment, inventory and notification services synchronously and p99 latency is climbing. How would you move it to an event-driven design, and what new problems do you take on? SDE3 Scenario

Publish an OrderPlaced event and let each service react independently, so the order API returns once the event is durably written. New problems: eventual consistency (the UI must show “processing”), duplicates (consumers must be idempotent), ordering (key by orderId), failure handling via retries/DLT instead of call-stack errors, a schema contract (Schema Registry) and the dual write between the DB and Kafka (Outbox).

Chapter: 01 13

12
Design for “no acknowledged write is ever lost” with RF=3. Which producer, topic and broker settings do you choose, and what availability do you give up? SDE3 Scenario

acks=all + idempotence on the producer, replication.factor=3, min.insync.replicas=2, and unclean.leader.election.enable=false. A write is acknowledged only when 2 replicas have it, and an out-of-sync replica can never become leader. Trade-off: if only one replica is in sync, producers get NotEnoughReplicas and the partition rejects writes rather than risk loss.

Chapter: 02 04

13
A broker that leads several partitions crashes. Walk through what happens until producers and consumers are working again. SDE3 Scenario

The controller notices the missing broker heartbeat, picks a new leader for each affected partition from its ISR, bumps the leader epoch and pushes new metadata. Producers and consumers get NOT_LEADER_OR_FOLLOWER/timeouts, refresh metadata and switch to the new leaders; idempotent producers retry without duplicates. When the old broker returns it truncates to the leader epoch, catches up and rejoins the ISR.

2Cluster & Producer

14
In the docs’ cluster, which nodes are controllers and which are brokers, and on which ports? SDE1

Controllers: node 1 (:9093) and node 2 (:9193). Brokers: node 3 (:9092) and node 4 (:9192).

Chapter: 03

15
Name the five stages of the producer pipeline in order. SDE1

Serializer → Partitioner → Record Accumulator → Compression → Sender thread.

Chapter: 04

16
Is kafkaTemplate.send() synchronous? What does the application thread wait for? SDE1

No. The application thread only serializes, partitions and appends to the accumulator, then returns a future. The sender thread sends batches in the background; call .get()/.join() if you need to wait for the ACK.

Chapter: 04

17
What two problems does the idempotent producer solve? SDE1

Duplicates when a retried batch was actually written (the ACK was lost), and reordering when a later batch succeeds before a retried earlier one.

Chapter: 05

18
Why must every node be formatted with the same cluster id? SDE2

kafka-storage format writes meta.properties with the cluster id into each log dir; nodes with different ids refuse to join the same cluster.

Chapter: 03

19
What is the difference between listeners and advertised.listeners? SDE2

listeners is where the node binds; advertised.listeners is the address it tells clients to use in metadata. If the advertised address is wrong, clients connect to the bootstrap server but then fail to reach the leaders.

Chapter: 03

20
Why set offsets.topic.replication.factor=2 in a two-broker cluster? SDE2

Its default is 3. With only two brokers the internal __consumer_offsets topic could not be created, so consumer groups would not work.

Chapter: 03

21
How do batch.size and linger.ms work together? SDE2

A batch is sent when it reaches batch.size bytes or when linger.ms has passed, whichever comes first. Bigger batches and a small linger give better throughput and compression at a small latency cost.

Chapter: 04

22
What happens when buffer.memory is full? SDE2

send() blocks for up to max.block.ms (60 s) waiting for space, then throws a TimeoutException.

Chapter: 04

23
Why can retries with max.in.flight.requests.per.connection > 1 reorder messages without idempotence? SDE2

If batch 1 fails and batch 2 succeeds, the retried batch 1 is written after batch 2. Idempotence fixes this using sequence numbers.

Chapter: 04

24
Throughput is low and the broker CPU is busy with many tiny requests. Which producer settings do you tune, and what do you watch? SDE2 Scenario

Increase linger.ms (e.g. 10–50 ms) and batch.size so batches fill up, enable compression.type (lz4/zstd/snappy), and make sure buffer.memory is not the limit. Watch batch-size-avg, records-per-request, request latency and compression ratio, and keep p99 latency inside the SLA.

Chapter: 04

25
What do the PID and sequence number mean, and how does the broker use them? SDE2

Each producer gets a Producer ID; every batch carries a per-partition sequence number. The broker accepts only the next expected sequence: a duplicate is acknowledged but not written again, and a gap is rejected.

Chapter: 05

26
Which settings are required for idempotence, and is it on by default? SDE2

acks=all, retries > 0, max.in.flight.requests.per.connection ≤ 5. It has been enabled by default since Kafka 3.0.

Chapter: 05

27
A producer service shows send() calls blocking for up to 60 s and then throwing TimeoutException. What is going on and how do you fix it? SDE3 Scenario

The record accumulator (buffer.memory) is full or metadata cannot be fetched, so send() waits max.block.ms. Usual causes: brokers slow or unreachable, a partition without a leader, or producing faster than the network/brokers accept. Fix the root cause (broker health, leaders, network), add backpressure in the app, tune batching/compression, and size buffer.memory — and never call blocking .get() per message on request threads.

Chapter: 04 05

28
What is the loophole in idempotency alone? SDE3

The PID is not persisted: a restarted producer gets a new PID, so re-sending the same data after a restart creates duplicates. Transactions fix this with a stable transactional.id.

Chapter: 05

29
An exactly-once requirement comes up for a payment pipeline. When is the idempotent producer enough, and when do you need transactions? SDE3 Scenario

Idempotence removes duplicates from retries within one producer session for single-partition writes. You need transactions when a restart must not duplicate (stable transactional.id), when several partitions/topics must be written atomically, or for read-process-write where output and consumed offsets must commit together. Downstream consumers must use read_committed; side effects outside Kafka (DB, emails) still need idempotency or an outbox.

Chapter: 05 10

3Consumer

30
What does Spring Boot create at start-up for a @KafkaListener? SDE1

A ConsumerFactory and a ConcurrentKafkaListenerContainerFactory; then, for each listener method, a listener container with its own KafkaConsumer and a poll loop.

Chapter: 06

31
What does auto-offset-reset=latest mean for a brand-new group? SDE1

With no committed offset, the consumer starts at the end of the partition and only sees records produced after it joined. earliest reads from the oldest retained offset.

Chapter: 06

32
Can one @KafkaListener read from several topics? SDE1

Yes, e.g. topics = {"order-events", "payment-events"}. It is still one consumer; it is assigned partitions from all those topics.

Chapter: 07

33
What does concurrency=3 on a listener do? SDE1

It creates three consumers (threads) in the same group for that listener. At most one consumer per partition is active, so with fewer partitions some consumers are idle.

Chapter: 07

34
Why does a single poison record cause an infinite loop by default? SDE1

Deserialization fails inside poll(), so the offset is never committed and every poll fetches the same record again — even after a restart.

Chapter: 08

35
How many attempts does FixedBackOff(1000L, 2) make? SDE1

Three: the original attempt plus 2 retries, 1 second apart.

Chapter: 08

36
Why does a consumer fail with “is not in the trusted packages”? SDE2

The producer’s JsonSerializer writes a __TypeId__ header with its own class name. The consumer will not instantiate an untrusted class, so either trust the package or disable use.type.headers and set value.default.type.

Chapter: 06

37
Walk through how a consumer finds where to start reading. SDE2

Join the group via the group coordinator → get the partition assignment → fetch the committed offset from __consumer_offsets → fetch from the partition leader starting at that offset.

Chapter: 06

38
How does JsonDeserializer decide which class to create? SDE2

use.type.headers → the __TypeId__ header → type.mapping → trusted packages / class path → otherwise value.default.type.

Chapter: 07

39
Why can one shared ConsumerFactory break listeners that expect different value types? SDE2

Its deserializer config (e.g. a single value.default.type) applies to every listener, so a listener expecting Payment may receive an Order and fail. Use type mapping or a separate factory per type.

Chapter: 07

40
You need to process 10 partitions with strict per-key ordering but heavy CPU work per record. How do you scale? SDE2 Scenario

Run up to 10 consumer threads/instances (one per partition). If that is not enough, process in parallel inside a partition by key (a worker pool where each key maps to one worker), committing an offset only when all earlier records of that partition are done — or increase partitions, accepting a one-time key reshuffle.

Chapter: 07 09

41
What does ErrorHandlingDeserializer do? SDE2

It wraps the real (delegate) deserializer, catches the exception and returns a record with a null value plus the error and raw bytes in headers, so the error handler can deal with it instead of poll() failing.

Chapter: 08

42
What does DeadLetterPublishingRecoverer do, and what topic does it use by default? SDE2

After retries are exhausted it publishes the failed record (with exception headers) to <topic>-dlt, on the same partition number, then the offset is committed.

Chapter: 08

43
Are deserialization errors retried by DefaultErrorHandler? SDE2

No — DeserializationException is classified as non-retryable (the same bytes will always fail), so it goes straight to the recoverer.

Chapter: 08

44
How do session.timeout.ms and max.poll.interval.ms differ? SDE2

The session timeout detects a dead consumer (no heartbeats from the background thread). The max poll interval detects a stuck one (alive, but not calling poll() in time). Both trigger a rebalance.

Chapter: 09

45
The broker returns 2000 records but max.poll.records=500. What happens? SDE2

poll() returns 500 records; the rest stay in the consumer’s internal buffer and are returned by the next polls without a new fetch.

Chapter: 09

46
What is the difference between ack-mode manual and manual_immediate? SDE2

Both commit when you call ack.acknowledge(). manual queues the commits and sends them after the poll’s records are processed; manual_immediate commits right away.

Chapter: 09

47
What does fetch.min.bytes together with fetch.max.wait.ms control? SDE2

The broker replies once at least fetch.min.bytes are available or fetch.max.wait.ms has passed, trading latency for fewer, larger responses.

Chapter: 09

48
Consumer lag keeps growing on one topic. How do you investigate and fix it? SDE2 Scenario

Check lag per partition (kafka-consumer-groups --describe): one hot partition points to key skew; all partitions point to slow processing. Then scale consumers up to the partition count, speed up processing (batching, async I/O, fewer DB calls), tune max.poll.records/fetch sizes, and add partitions if consumers are already maxed — while keeping processing within max.poll.interval.ms.

Chapter: 09

49
With auto-commit enabled, how can you lose or duplicate messages? Which commit strategy would you use for at-least-once? SDE2 Scenario

Auto-commit commits polled offsets on a timer: a crash after a commit but before processing loses records; a crash after processing but before the next commit replays them. For at-least-once, disable auto-commit and commit only after processing (Spring ack-mode record/batch or manual), and make processing idempotent.

Chapter: 09 08

50
Design error handling for a consumer that calls a flaky downstream API: transient failures should retry, permanent failures must not block the partition. SDE3 Scenario

Classify exceptions: retry transient ones with exponential backoff (DefaultErrorHandler), mark validation/deserialization errors non-retryable, and after retries send the record to a DLT with exception headers. For long outages, avoid blocking the partition: use non-blocking retry topics (e.g. Spring @RetryableTopic) with growing delays, plus alerting and a replay tool for the DLT. Keep ordering needs in mind — retry topics break per-key order.

Chapter: 08 09

51
What is the advantage of the CooperativeSticky assignor? SDE3

Rebalances are incremental: consumers keep reading the partitions they retain and only the moved partitions pause, instead of every consumer stopping (“stop the world”).

Chapter: 09

52
Your consumer group rebalances every few minutes and throughput collapses. What are the likely causes and fixes? SDE3 Scenario

Common causes: processing a batch takes longer than max.poll.interval.ms (consumer kicked out), GC pauses or network blips exceeding session.timeout.ms, or rolling restarts/autoscaling. Fixes: smaller max.poll.records or faster processing, a larger poll interval, CooperativeStickyAssignor so rebalances are incremental, and static membership (group.instance.id) so restarts don’t trigger rebalances.

Chapter: 09 07

4Transactions & Patterns

53
Name the three problems Kafka transactions solve. SDE1

Duplicates after a producer restart (new PID), partial writes across topics, and duplicate output in read-process-write.

Chapter: 10

54
What does a read_uncommitted consumer see? SDE1

Every data record — committed, aborted and still open — but not the control (COMMIT/ABORT) records. It is the default.

Chapter: 11

55
Why is plain JSON risky when producer and consumer evolve separately? SDE1

There is no contract: added fields may be ignored, removed or renamed fields silently become defaults/nulls, and type changes fail at runtime — all detected only on the consumer.

Chapter: 12

56
What is a subject, and how is it named by default? SDE1

The registry’s versioned name for a schema. With TopicNameStrategy it is <topic>-value (or -key), e.g. order-events-value.

Chapter: 12

57
What is the dual-write problem? SDE1

Writing to the database and to Kafka are two independent operations with no shared transaction, so a crash or error between them leaves the two out of sync.

Chapter: 13

58
How does the Outbox pattern work? SDE1

Write the business row and an event row to an outbox table in one local DB transaction; a separate process (poller or CDC) reads the outbox and publishes to Kafka.

Chapter: 13

59
How is the transaction coordinator found? SDE2

hash(transactional.id) % 50 picks a partition of __transaction_state; the leader of that partition is the coordinator.

Chapter: 10

60
What is zombie fencing? SDE2

When a new producer initializes with the same transactional.id, the coordinator aborts the open transaction and bumps the epoch. Requests from the old producer still carry the old epoch and are rejected with ProducerFencedException.

Chapter: 10

61
Why should a transactional id be stable, e.g. not ${random.uuid}? SDE2

A new id on every restart means the coordinator cannot link the new instance to its unfinished transaction or fence the old one — the guarantees break.

Chapter: 10

62
What is the LSO? SDE2

The Last Stable Offset: the offset of the first record that belongs to a still-open transaction. A read_committed consumer never reads past it.

Chapter: 11

63
What does sendOffsetsToTransaction achieve? SDE2

It writes the consumed offsets to __consumer_offsets inside the producer’s transaction, so the output records and the offset commit succeed or fail together (exactly-once read-process-write).

Chapter: 11

64
What is the Avro wire format written by KafkaAvroSerializer? SDE2

[magic byte 0][4-byte schema id][Avro binary payload]. The payload holds only values in field order; the schema id is used to look up the writer schema.

Chapter: 12

65
What does BACKWARD compatibility guarantee, and which change does it reject? SDE2

A consumer on the new schema can read data written with the old one. Adding a field without a default is rejected (old data has no value for it).

Chapter: 12

66
When does an incompatible schema change fail? SDE2

On the producer, during serialization (Stage 1) when it tries to register the new schema — error 40901 — so nothing incompatible ever reaches Kafka.

Chapter: 12

67
You must add a field to a widely used Avro event without breaking any consumer. What exactly do you do? SDE2 Scenario

Add the field with a default (often a nullable union with default null), keep the subject on BACKWARD or FULL compatibility, register the schema (the registry rejects incompatible changes), then upgrade consumers before/after producers according to the level. Never rename or retype a field — add a new one and deprecate the old.

Chapter: 12

68
Why doesn’t @Transactional plus rolling back on a Kafka error solve it? SDE2

If Kafka actually wrote the event but the ACK was lost, the app rolls back the DB anyway — the event exists for an order that doesn’t.

Chapter: 13

69
Polling vs CDC — name two drawbacks of polling. SDE2

Any two of: polling delay, constant DB queries, locking/ordering trouble with multiple instances, outbox clean-up, and duplicates when the “published” update fails.

Chapter: 13

70
Why must outbox consumers be idempotent? SDE2

Both polling and CDC are at-least-once: after a crash an event can be published again, so consumers deduplicate, e.g. by the event id.

Chapter: 13

71
Why can’t Kafka transactions solve “update the DB and publish an event atomically”? SDE2 Scenario

Kafka transactions are atomic only across Kafka partitions; the database is not a participant and Kafka does not support XA/2PC. The DB commit and the Kafka commit stay two independent writes — hence the Outbox pattern (single DB transaction, then publish).

Chapter: 13 10

72
Why is PREPARE_COMMIT called the point of no return? SDE3

Once it is replicated in __transaction_state, the coordinator will finish the commit no matter what — writing COMMIT markers to every partition, even after failures.

Chapter: 10

73
How does a read_committed consumer know which records were aborted? SDE3

The broker keeps aborted transaction ranges in the segment’s .txnindex file and sends them in the fetch response; the consumer drops records from that producer between the first offset and the ABORT marker.

Chapter: 11

74
Design an exactly-once “consume orders → enrich → produce enriched-orders” service. What exactly guarantees exactly-once, and where does it stop? SDE3 Scenario

A transactional producer with a stable transactional.id; for each batch: begin, produce outputs, sendOffsetsToTransaction(offsets, consumer.groupMetadata()), commit. Downstream readers use read_committed. This is exactly-once within Kafka (output + offsets atomic, zombies fenced). It stops at external side effects: a DB write or HTTP call inside the loop can still happen twice on retry, so make those idempotent or route them through an outbox.

Chapter: 11 10

75
A read_committed consumer is stuck: lag grows, but the partitions keep receiving data. What could be wrong? SDE3 Scenario

A transaction was left open (producer hung or crashed without abort), so the LSO does not advance and read_committed consumers cannot read past it. It clears when the coordinator aborts the transaction after transaction.timeout.ms. Fix: lower the transaction timeout, keep transactions short, ensure producers abort on error, and use kafka-transactions tooling to find and abort hanging transactions.

Chapter: 11

76
Two teams both produce to the same topic but want different schemas. How do you handle this with Schema Registry? SDE3 Scenario

Options: separate topics (simplest), or one topic with a union/“envelope” schema, or switch the subject naming strategy to RecordNameStrategy / TopicRecordNameStrategy so each record type has its own subject and compatibility history. Consumers then must handle multiple types (e.g. via specific reader or type dispatch).

Chapter: 12

77
Compare the polling outbox and CDC (Debezium) outbox for a high-volume order service. Which would you pick and why? SDE3 Scenario

Polling: simple, no extra infra, but adds latency and constant DB load, needs SKIP LOCKED/ShedLock with many instances, and a clean-up job. CDC: near-real-time, reads the WAL (no polling load), keeps commit order, no “published” flag — but needs logical WAL, Kafka Connect, Debezium and replication-slot monitoring. At high volume, CDC is usually the better choice; both are at-least-once, so consumers deduplicate by event id.

Chapter: 13

78
Your Debezium connector has been stopped for a day and the Postgres disk is filling up. Why, and what do you do? SDE3 Scenario

The replication slot keeps WAL until Debezium confirms it, so WAL accumulates while the connector is down. Restart the connector so it catches up, or drop the slot if the connector is gone for good (then re-snapshot). Prevent it with monitoring on slot lag/retained WAL and limits such as max_slot_wal_keep_size.

Chapter: 13

5Kafka Streams

79
What is the difference between stateless and stateful processing? SDE1

Stateless: the output depends only on the current event. Stateful: it depends on earlier events too (totals, windows, joins), so state must be kept.

Chapter: 14

80
Is Kafka Streams a cluster? SDE1

No — it is a client library (a JAR) inside your application. Instances coordinate through Kafka itself using a consumer group named by application.id.

Chapter: 15

81
KStream vs KTable — how are three records for key 001 treated? SDE1

A KStream treats them as three independent events. A KTable treats them as updates and keeps only the latest value for 001.

Chapter: 16

82
What is a SerDe, and why does Kafka Streams need one? SDE1

A serializer + deserializer in one object. Streams both reads and writes bytes (topics and RocksDB), often for the same type.

Chapter: 17

83
Name the five places in a topology that need SerDes. SDE1

Source, sink, repartition topics, RocksDB writes, and RocksDB reads (e.g. in joins).

Chapter: 17

84
Which wins: default.value.serde or Consumed.with(...)? SDE1

The explicit SerDe passed in code always overrides the default from properties for that step.

Chapter: 17

85
Does a KStream variable contain data? SDE1

No — it is a reference to a stage (node) in the topology, used to keep building from that point. Records flow only when the app runs.

Chapter: 18

86
How does split() with branches differ from several filters? SDE1

Branches are checked in order and each record goes to the first matching branch (if / else-if / else), instead of every filter being evaluated for every record.

Chapter: 18

87
What must be true to merge() streams? SDE1

They must have the same key and value types. There is no ordering guarantee across the merged inputs.

Chapter: 18

88
Are groupByKey and groupBy stateful? SDE1

No — they store nothing. They produce a KGroupedStream (which key to aggregate by) and trigger repartitioning if the key changed.

Chapter: 19

89
What does count() return? SDE1

A KTable<K, Long> backed by a state store, updated every time a key’s count changes.

Chapter: 19

90
Tumbling vs hopping windows? SDE1

Both have a fixed size. Tumbling windows do not overlap, so a record falls in exactly one window. Hopping windows advance by less than their size and overlap, so a record can be in several.

Chapter: 20

91
What breaks if you keep running totals in an in-memory map in a consumer? SDE2

A crash loses the map (replay from offset 0), and with several instances each one holds only the partitions it owns — partial totals that move away on a rebalance.

Chapter: 14

92
Why is a database per event a poor fix? SDE2

One SELECT + UPDATE per event makes the database the bottleneck at high throughput, and the DB write and offset commit are separate (double counting after a crash).

Chapter: 14

93
What must a stream-processing framework provide? SDE2

State management, windowing, joins, crash recovery of state, and scaling with partitions — which is what Kafka Streams does as a library.

Chapter: 14

94
How many tasks does a topology create? SDE2

For each sub-topology, one task per partition of its source topic. Two sub-topologies on 3-partition topics give 6 tasks.

Chapter: 15

95
When does Kafka Streams create a repartition topic? SDE2

When the key was changed (e.g. selectKey, map) and a downstream operation needs data grouped by the new key, such as groupByKey or a join.

Chapter: 15

96
How does local RocksDB state survive a crash or rebalance? SDE2

Every store update is also written to a compacted changelog topic; a task that moves to another instance rebuilds its RocksDB by replaying the changelog before processing.

Chapter: 15

97
How do threads and instances relate to tasks? SDE2

Tasks are the fixed unit of work; stream threads (and instances) just host them. More threads than tasks leaves threads idle.

Chapter: 15

98
What is co-partitioning, and why do KStream–KTable joins need it? SDE2

Both topics have the same number of partitions and the same key and partitioner, so matching keys land in the same partition number — and therefore in the same task, where the join can be done locally.

Chapter: 16

99
When should you use a GlobalKTable? SDE2

For small reference data (countries, currencies, config) that must be joined without co-partitioning. Every instance keeps a full copy, loaded before stream threads start.

Chapter: 16

100
You join a KStream of orders with a KTable of customers and get no output for many orders. List possible reasons. SDE2 Scenario

Keys don’t match (orders not re-keyed by customerId); topics not co-partitioned; the customer record arrived after the order on a fresh start (inner join drops it — use leftJoin); SerDe mismatch on the table; or the customer topic is missing data. Check keys, partition counts and timestamps first.

Chapter: 16 19

101
What does LogAndContinueExceptionHandler do, and what is the risk? SDE2

It logs and skips records that cannot be deserialized, keeping the app running — but those records are lost unless you also send them to a dead-letter topic.

Chapter: 17

102
Why does count() often fail with a String default value SerDe? SDE2

Its output values are Long; writing them with a String SerDe causes a ClassCastException, so pass Serdes.Long() explicitly.

Chapter: 17

103
map vs mapValues — why prefer mapValues when the key doesn’t change? SDE2

map may change the key, so Streams marks the stream for repartitioning; mapValues cannot, so it avoids an unnecessary repartition topic.

Chapter: 18

104
Does selectKey repartition immediately? SDE2

No. Repartitioning happens only before a downstream operation that needs the new key, like groupByKey or a join.

Chapter: 18

105
Your topology creates three repartition topics. How can you reduce them? SDE2 Scenario

Use mapValues/flatMapValues instead of map when the key doesn’t change, re-key once (selectKey) and reuse the stream for several groupings/joins, enable topology optimization (topology.optimization=all), and produce source data already keyed correctly.

Chapter: 18 15

106
What do the initializer and aggregator in aggregate() do? SDE2

The initializer gives the starting value the first time a key is seen; the aggregator combines each new record with the current aggregate read from RocksDB, and the result is stored back.

Chapter: 19

107
Which join combinations are possible, and which is not? SDE2

KStream–KTable, KTable–KTable, KStream–GlobalKTable and windowed KStream–KStream are possible. KTable–KStream (looking up into a stream) is not.

Chapter: 19

108
In a KStream–KTable join, what triggers output? SDE2

Only new stream records; each looks up the latest table value for its key. Updates to the table do not re-emit earlier stream records.

Chapter: 19

109
Event time vs record timestamp vs stream time? SDE2

Event time: when it happened (a field in the payload). Record timestamp: set by the producer or broker, used by windows by default. Stream time: the highest timestamp seen so far; it decides when windows close.

Chapter: 20

110
What is a grace period? SDE2

Extra time after a window ends during which late records are still accepted. A window closes when stream time ≥ window end + grace; records for a closed window are dropped.

Chapter: 20

111
How does a session window differ from the other two? SDE2

It has no fixed size: a session continues while records arrive within the inactivity gap. A late record can even merge two sessions into one.

Chapter: 20

112
How do you make windows use event time instead of the record timestamp? SDE2

Configure a custom TimestampExtractor (default.timestamp.extractor) that returns the event’s own timestamp.

Chapter: 20

113
Tumbling, hopping or session window — which for each: requests per minute, “last 1 hour updated every 5 minutes”, user visit length? SDE2 Scenario

Requests per minute: tumbling 1-minute windows. Rolling last hour every 5 minutes: hopping (size 60, advance 5). Visit length: session windows with an inactivity gap.

114
Design a real-time “orders per product per minute” dashboard with Kafka Streams. Walk through topology, state and scaling. SDE3 Scenario

stream(order-events) → selectKey(productId) → groupByKey (repartition topic) → windowedBy(TimeWindows.ofSizeAndGrace(1 min, grace)) → count into a windowed RocksDB store backed by a changelog → toStream → output topic (optionally suppress until the window closes). Scale with partitions: tasks = sub-topologies × partitions, spread over threads/instances; serve reads via interactive queries or the output topic.

Chapter: 15 19

115
A Kafka Streams instance restarts and takes 20 minutes before processing again. Why, and how do you reduce it? SDE3 Scenario

Its tasks are restoring state from changelog topics because local RocksDB data is missing or stale. Reduce it by keeping a persistent state.dir (no ephemeral disk), using standby replicas (num.standby.replicas) so another instance keeps warm copies, keeping changelogs compacted, and avoiding unnecessary large stores.

Chapter: 15

116
After a rebalance, does a KTable task read its source topic first? SDE3

It first restores its store from the changelog, then processes new records. On a fresh start there is no priority: an order can arrive before its customer.

Chapter: 16

117
KTable vs GlobalKTable for enriching a 50 GB customer table: which do you choose? SDE3 Scenario

A KTable: a GlobalKTable copies the entire topic to every instance (50 GB × instances, long start-up, no partition scaling). Use a KTable and co-partition/re-key the stream by customerId. GlobalKTable fits small reference data (countries, currencies) or when re-keying the stream is impossible.

Chapter: 16

118
A bad record crashes your Kafka Streams app in a restart loop. How do you make it resilient without silently losing data? SDE3 Scenario

Set a custom default.deserialization.exception.handler that logs, sends the raw bytes to a dead-letter topic, and returns CONTINUE (FAIL beyond an error-rate threshold). Use a processing.exception.handler for errors in your own code and a production handler for write failures, and alert on DLT volume so someone replays or fixes the data.

Chapter: 17 08

119
Your count per key is double-counting after crashes. Why, and how do you get exactly-once counts? SDE3 Scenario

With the default at-least-once guarantee, records processed after the last commit are reprocessed after a crash, updating the store and output again. Set processing.guarantee=exactly_once_v2: input offsets, state-store changelog writes and outputs commit in one Kafka transaction; downstream consumers read with read_committed.

Chapter: 19 15

120
Events can arrive up to 10 minutes late, and the business wants one final count per 5-minute window. How do you configure it? SDE3 Scenario

Use event time via a TimestampExtractor, TimeWindows.ofSizeAndGrace(5 min, 10 min), and suppress(untilWindowCloses(...)) so each window emits once after window end + grace. Set store retention ≥ size + grace. Trade-off: results arrive at least 10 minutes late; anything later than the grace period is dropped (track it with metrics).
